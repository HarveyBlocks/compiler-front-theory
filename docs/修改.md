# 修改方案

## 目标

- 改的是文法，不是先改一堆实现细节
- 不走 C/C++ 的复杂左右值体系
- 不走 JavaScript 式无类型方案
- 保留显式类型
- 先做任务1：常量计算
- 再做任务2：函数

## 这次不改什么

- 不引入 `const`
- 不引入 `set`
- 不把语法改成“先天弱类型”
- 不强行把表达式拆成很重的左值/右值体系

## 推荐文法方向

### 1. 变量声明

保留显式类型声明，继续用简单写法：

- `int32 x;`
- `int32 x = 1 + 2;`
- `float64 y = x + 0.5;`

### 2. 赋值

保持普通赋值，不额外造新关键字：

- `x = expr;`
- `arr[i] = expr;`

### 3. 常量计算

常量计算不新增专门关键字，而是扩展表达式文法，让一部分表达式天然可被判定为常量：

- 字面量
- 括号表达式
- 单目表达式
- 双目表达式
- 常量标识符参与的表达式

也就是说，文法负责“长什么样”，常量能不能算由语义层判断。

### 4. 函数

函数作为第二阶段新增，建议直接新增一组文法：

- 函数定义
- 参数列表
- return
- 函数调用

示例：

- `int32 add(int32 a, int32 b) { return a + b; }`
- `x = add(1, 2);`

## 为什么可以直接改 production

原来的 production 如果：

- 不同职责共用同一个左部
- 语义阶段只能靠位置、长度、字符串去猜
- 后续一扩展就会牵一大片分发逻辑

那它本身就是应该调整的。

这次允许改 production，不是为了“破坏兼容”，而是为了把原本糟糕的文法边界重新整理清楚。  
尤其应该避免：

- 声明、赋值、调用、控制流挤在同一种 statement 形态里
- 多个语义完全不同的候选式挂在同一个左部下
- 后续每加一个能力，就继续往旧左部里堆候选

更合理的方向是：

- 用更细的非终结符拆职责
- 让 declaration / assignment / callable / control 等结构边界清楚
- 让语义分发更多依赖“结构类别”，少依赖“字符串匹配”

## 为什么不建议在文法阶段引入 `const_expr`

`const_expr` 在文法阶段看起来很自然，但实际上成本很高。

如果强行在 grammar 里单独做一套 `const_expr`，通常会带来：

- 普通表达式和常量表达式两套平行结构
- 大量重复的优先级与结合性规则
- 更多 production
- 更难排查的语法错误
- 语义错误被伪装成语法错误

所以更稳妥的做法是：

- 文法里只有“表达式”
- 语义阶段再判断这个表达式是不是编译期可计算
- 可计算则做常量传播
- 不可计算则按普通表达式处理

## 文法修改原则

- 语法扩展优先新增 production
- 可以修改 production，本来就不合理的同左部结构应该拆开
- 尽量不改已有 production 的含义
- 通过新增非终结符表达新语法边界
- 让任务1 和任务2 都能独立落地
- 旧功能尽量不改，只做适配

## 建议文法顺序

### 任务1：常量计算

1. 保留现有表达式主干
2. 不在文法阶段强行引入 `const_expr`
3. 在语义阶段判断表达式是否可计算
4. 对常量表达式做约束，不让它依赖运行期值
5. 把常量结果挂到语义属性或符号表上
6. 补测试：能折叠、能传播、不能折叠时不破坏普通表达式

### 任务1 的文法建议

- 可以拆掉原来同左部但职责混杂的 production
- 普通表达式继续保留一套
- 常量性判断不要靠文法分叉太多
- 语法只负责表达“表达式长什么样”
- 是否为常量表达式交给语义层

### 任务2：函数

1. 新增函数定义文法
2. 新增参数/返回值文法
3. 新增函数调用表达式
4. 新增 return 语句文法
5. 补测试：定义、调用、递归、返回类型、参数个数

## 结论

这次正确的方向不是“从 C/C++ 跳到 JS”，而是：

- 保留类型
- 保留简单赋值
- 先把文法边界画清楚
- 再用语义层补常量计算
- 再用新文法模块加函数
- 不用 `const/set` 这类会把系统带偏的设计
