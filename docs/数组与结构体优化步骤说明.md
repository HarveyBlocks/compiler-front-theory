# 数组与结构体优化步骤说明

## 目标

为后续的数组与结构体能力扩展，先整理一份面向对象的实施步骤说明。

这份说明只描述：

- 文法如何扩展
- 语义规则如何约束
- 类型系统要增加哪些对象
- `new / null / 引用对象 / 值传递` 应如何统一
- 中间代码里 `address` 与 `reference` 应如何区分

这份说明不直接要求立即改代码，也不主张继续堆过程式分支。

## 总原则

### 1. 尽量面向对象，不继续堆面向过程分支

数组、结构体、`new`、`null` 都不是“再加几个 case”就能长期维护的能力。

应优先补齐这些对象抽象：

- 类型对象
- 初始化对象
- 引用对象语义对象
- 空值对象
- 成员访问/索引访问对象

不要把它们继续压成：

- 大 `switch`
- 大量字符串判断
- 到处散落的静态工具函数

### 2. 对增加开放，对修改关闭

数组与结构体是新能力，优先做法应当是：

- 新增新的文法层级或新的语义对象
- 让旧的标量、表达式、声明逻辑尽量少改
- 用适配而不是重写原有已有功能

> 不是全部都是对增加开放， 对修改关闭， 对于你自己写的代码， 可以进行修改， 对别人写的代码（已经merge到main/master的代码， 要保守修改！）
>
> 如果修改更好更有必要， 向上报告， 而不是静默完成增加导致大量无用代码

### 3. 文法负责结构，语义负责合法性

尤其要注意：

- 文法不必提前穷尽所有类型合法性
- `void`、`null`、引用对象可赋值性这类规则，可以更多放在语义阶段
- 结构体字段默认值、数组长度表达式是否可接受，也主要在语义阶段落地

## 设计目标

这次需要支持的核心语义有四组。

### 1. 数组

支持示意：

```text
int[] arr = new int[expr];
int[][] arr2 = new int[expr1][expr2];
```

约束：

- 数组长度表达式可以是一般表达式，也可以是常量表达式
- 数组长度声明只要求结果类型是 `int`
- 数组的类型检查与比较，按“维度链”处理，不再把“长度值”当成类型的一部分

这里要明确为：

- 数组类型本质是“基类型 + 维度层级链”
- 所谓二维、三维，不额外单列一套特殊规则
- 只需要统一处理“有几层维度、每层对应一个数组层级”

也就是说，不建议把“维度”单独再造一个概念系统。

### 2. 结构体

支持示意：

```text
struct StructObject {
    int value;
    int value2;
    StructObject obj;
}
```

约束：

- 字段暂不支持显式初始化
- 字段在实例化时按默认值补齐
- 字段类型可以是基础类型
- 字段类型也可以是结构体类型

结构体实例化形式：

```text
StructObject obj = new StructObject();
```

这里的重点是：

- 结构体声明与结构体实例化要区分
- 结构体类型本身不是值
- `new StructObject()` 表示创建该结构体类型的一个实例
- 成员字段通过点运算符访问
- 成员访问在中间代码阶段会转换成“对象引用 + 字段偏移量”的访问

### 3. 参数传递与对象语义

虽然这不是狭义“前端文法”问题，但必须先定语义约定。

当前建议统一为：

- 参数传递方式是值传递
- 但数组和结构体本身是引用对象
- 对中间代码来说，所有结构体对象都可归入同一种 `reference` 大类

含义应按类似 Java 的方式理解：

- 传参时复制的是“引用值”
- 不是复制整个数组对象或结构体对象
- 所以函数内外可以指向同一对象

这样有几个好处：

- 不需要前端一开始就设计深拷贝语义
- 与 `null` 语义天然兼容
- 与数组/结构体统一成“引用类型”后，赋值与比较规则更清晰

这里还要额外明确一个命名边界：

- 指向局部变量表槽位的“可寻址位置”，叫 `address / addr`
- 指向堆上或引用对象区域的“对象引用”，叫 `reference / ref`

这两个概念在中间代码设计里不能混用。

### 4. null

引入新关键字：

- `null`

约束：

- 数组可以是 `null`
- 结构体可以是 `null`
- 一般基础标量类型不能直接接收 `null`

因此 `null` 不应被当作普通基础类型字面量，而更适合被看作：

- 一种特殊常量
- 或一种只能赋给引用类型的空引用值

## 类型系统建议

这部分是整个设计里最重要的部分之一。

如果这里继续过程式处理，后面几乎一定会越改越乱。

### 1. 不要只靠现有 `SemanticType` 平铺到底

建议把类型对象分层：

- `ScalarType`
- `ArrayType`
- `StructType`
- `NullType` 或 `NullLiteralType`

即使暂时不真正拆成完整继承层级，也应该在设计上朝这个方向靠拢。

### 2. 数组类型

数组类型至少应包含：

- 元素基类型
- 长度层级信息

这里的“长度层级信息”不是运行时具体值，而是“数组层数结构”。

例如：

- `int[]`
- `int[][]`

都应是统一的数组类型对象，只是层级不同。

如果后面要记录声明时的长度表达式，也应挂在“初始化对象”里，而不是直接塞进类型定义。

### 3. 结构体类型

结构体类型至少应包含：

- 结构体名
- 字段列表
- 字段到字段定义对象的映射

字段定义对象至少应包含：

- 字段名
- 字段类型
- 可选初始化表达式

### 4. null 类型/空引用值

建议不要把 `null` 伪装成某一种具体类型。

更好的做法是：

- 在字面量或常量值层面单独表示 `null`
- 在赋值兼容性判断时，允许它赋给引用类型

这样语义边界更清楚：

- `null` 不是 `int`
- `null` 不是 `boolean`
- `null` 也不是某一个具体结构体类型
- 它只是“可赋给引用类型的空引用值”

### 5. 中间代码命名边界

这一条很重要，必须在设计阶段先定死。

对于中间代码来说，应区分两类“可指向目标”的东西：

1. 局部变量表里的地址

- 这是局部变量槽位的位置语义
- 它服务于标量局部变量、数组变量槽位、结构体变量槽位等“局部表项”
- 命名统一使用 `addr / address`

2. 引用对象的引用

- 这是对象层的引用语义
- 数组对象与结构体对象都属于这一类
- 对中间代码而言，所有结构体对象都可以视为同一种 `reference`
- 命名统一使用 `ref / reference`

因此必须避免下面这种混用：

- 把“局部变量表地址”也叫 `reference`
- 把“对象引用”也叫 `address`

建议统一约定为：

- 局部变量表相关命令，使用 `addr/address`
- 对象访问、成员偏移、数组对象访问相关命令，使用 `ref/reference`

## 文法建议

## 1. 数组类型

建议沿用现有显式类型体系扩展，而不是引入弱类型写法。

例如：

- `type -> type [ ]`

或继续沿用你们现有数组型写法体系，但要把“数组类型”和“数组创建”分开。

不要把下面两种混在一起：

- 类型声明
- `new` 创建表达式

### 2. 数组创建表达式

建议新增独立的创建表达式层级，例如：

- `new_array_expr`

形态类似：

- `new_array_expr -> NEW type [ expr ]`
- `new_array_expr -> NEW type [ expr ] [ expr ] ...`

重点是：

- 方括号里的应是表达式节点
- 这些表达式的结果类型必须在语义阶段检查为 `int`

### 3. 结构体定义

建议新增结构体定义层级，例如：

- `struct_decl`
- `struct_field_list`
- `struct_field`

结构示意：

- `struct_decl -> STRUCT IDENTIFIER { struct_field_list }`
- `struct_field -> type IDENTIFIER ;`

当前先不要支持字段显式初始化，因此不引入：

- `struct_field -> type IDENTIFIER = expr ;`

### 4. 结构体实例化

建议新增独立创建表达式：

- `new_struct_expr -> NEW IDENTIFIER ( )`

这里采用显式类型构造，不再使用无类型名的 `new()`。

原因是：

- 表达式里需要自描述类型，不能依赖左侧上下文猜目标类型
- 像 `func(new Object().value)` 这种场景里，右侧必须天然带着结构体类型信息
- 这样才能把“创建对象”与“读取成员”明确分开

因此统一约定为：

- `StructObject obj = new StructObject()`
- `new StructObject().value`
- 不再保留 `new()` 这种上下文推断写法

### 5. 成员访问

建议新增独立成员访问层级，例如：

- `member_access_expr -> primary OPERATOR_DOT IDENTIFIER`

成员访问语义要点：

- 左侧必须是结构体对象或结构体引用
- 右侧标识符必须是该结构体已声明字段
- 成员访问结果在语义上仍然是一个“字段位置”或“字段值访问”
- 到中间代码生成阶段，应转换为“对象内偏移量访问”

这里的“对象引用”特指 `reference`，不是局部变量表中的 `address`。

也就是说，像：

- `obj.value`

在中间代码阶段不再保留“按名字找字段”，而是变成：

- 先拿到 `obj` 的对象引用 `reference`
- 再根据字段表把 `value` 解析成该结构体中的固定偏移量
- 最终生成“按偏移访问字段”的命令

### 6. null

建议新增：

- `factor -> NULL`

或接入现有字面量层。

但语义上必须单独处理，不能把它混进普通数值/布尔字面量。

## 语义规则建议

## 1. 数组长度表达式

规则：

- 数组长度表达式必须可类型检查
- 结果必须是 `int`
- 是否是常量表达式，不作为语法前提

也就是说：

- `new int[a + 1]` 可以
- `new int[3]` 也可以
- `new int[true]` 不可以

至于是否还要额外限制“长度必须非负”，这是后续可选规则，可以在语义阶段补。

## 2. 数组赋值与兼容性

建议先采用保守规则：

- 只有同元素基类型、同数组层级的数组之间才能直接赋值
- `null` 可赋给任意数组类型

## 3. 结构体字段默认值

规则：

- 结构体字段暂不支持显式初始化
- 结构体实例化时自动补默认值
- 数字类型默认是 `0`
- `boolean` 默认是 `false`
- 结构体与数组默认是 `null`

第一阶段建议：

- 前端只记录字段名与字段类型
- 默认值语义由结构体实例化阶段统一补齐

## 4. 结构体成员访问

规则：

- 成员访问使用点运算符 `.` 
- 左侧必须是结构体类型
- 右侧必须是该结构体已存在字段
- 成员访问的类型等于字段类型

中间代码生成要求：

- 不按字段名字直接生成命令
- 先在语义阶段完成“字段名 -> 字段定义 -> 字段偏移量”的绑定
- 到命令层时，把成员访问翻译成“对象 `reference` + 固定偏移量访问”
- 不要把局部变量表里的 `address` 和对象 `reference` 混成一种命令操作数

## 5. 结构体赋值与兼容性

建议先采用保守规则：

- 同名同定义结构体类型之间可赋值
- 不同结构体类型之间不可赋值
- `null` 可赋给结构体引用

## 6. 参数传递

统一规则：

- 基础类型按值传递
- 数组按引用值传递
- 结构体按引用值传递

这条规则在前端至少应反映在：

- 类型兼容性判断
- 调用参数检查
- `null` 参与调用时的可赋值性判断

## 面向对象的实施步骤

建议按下面顺序推进。

### 阶段1：先补类型对象，而不是先补 case

先定义清楚这些对象：

- 数组类型对象
- 结构体类型对象
- 字段定义对象
- 空引用值对象

这一阶段不要急着写完整 translator。

### 阶段2：补文法骨架

新增但尽量不破坏旧系统：

- 数组创建表达式
- 结构体定义
- 结构体字段定义
- 结构体实例化
- 成员访问
- `null`

### 阶段3：补语义注册中心

需要新增：

- 结构体类型表
- 字段解析能力
- 字段偏移量分配能力
- 数组/结构体/`null` 的赋值兼容性判断

### 阶段4：补初始化语义

分别处理：

- 数组 `new`
- 结构体字段默认值
- 结构体 `new StructObject()`
- 成员访问到字段偏移量的映射

### 阶段5：补函数参数与返回值兼容性

尤其检查：

- 数组参数
- 结构体参数
- `null` 传参
- `null` 返回

### 阶段6：最后再补命令层

不要一开始就纠缠底层命令字符串。

应先把：

- 类型
- 语义
- 绑定关系

这些对象整理好，再决定命令层如何表达：

- 局部变量表 `address`
- 对象 `reference`
- 引用对象创建
- 空引用

并且在命名上统一成：

- 局部变量表相关操作使用 `addr/address`
- 对象相关操作使用 `ref/reference`

## 第一阶段不建议做的事

- 不要一上来就支持结构体方法
- 不要一上来就支持成员函数调用
- 不要一上来就支持结构体构造参数
- 不要一上来就做深拷贝语义
- 不要把 `null` 扩展到基础标量类型
- 不要为了无类型名构造，把整个表达式系统改乱
- 不要在字段语法里继续加入显式初始化

## 建议的最小可交付版本

第一版建议只做到：

1. 支持数组类型与数组创建
2. 支持结构体定义
3. 支持结构体字段默认值
4. 支持 `StructObject obj = new StructObject();`
5. 支持成员点访问
6. 支持 `null`
7. 支持数组/结构体作为函数参数
8. 统一成“值传递，但对象是引用值”

## 结论

这次数组与结构体扩展，不应继续走“堆 case”的过程式路线。

更合理的推进方式是：

- 先抽类型对象
- 再补文法骨架
- 再补语义约束
- 最后接命令层

尤其要先统一三条底层约定：

- 数组和结构体是引用对象
- 参数传递仍然是值传递
- `null` 是引用对象的空值，而不是普通标量

再补一条中间代码约定：

- 局部变量表位置叫 `address`
- 对象位置叫 `reference`

如果这三条先统一，后续实现会顺很多。
