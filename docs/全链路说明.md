## 2. 输入资源链路

输入层解决的问题，是把“外部资源”统一抽象成后续前端可消费的字符流，同时保留错误位置。

这里的设计重点有两个：

1. 资源与读取器分层
- `Resource` 代表“某种输入来源”
- `SourceReader` 代表“按字符读取并携带位置信息的读取器”

2. 一开始就把错误上下文带进去
- 这样字符层出错时，不需要临时拼装额外上下文

当前 Program / Demo 常用的是字符串输入，因此落地成：

- `AsciiStringResource`
- `AsciiStringSourceReader`

关键代码片段：

```java
public SourceCharacter read() throws IOException, CompileException {
    offset++;
    int ch = reader.read();
    if (ch == -1) {
        return SourceCharacter.EOF;
    }
    if ((ch & 0xff_ff_ff_00) > 0) {
        errorContext.addError(new IoErrorMessage(offset, "ascii only"));
        throw new CompileException();
    }
    return new AsciiCharacter((byte) ch);
}
```

这个实现说明：

- offset 在最底层就开始累计
- ASCII 限制不是词法阶段才检查，而是输入阶段就直接保证
- 非法字符既写错误，也会中断读取

`peek()` 通过 `mark/read/reset` 实现，这意味着读取器本身支持有限前瞻，而不需要上层每次手工缓存字符。

一个最小例子：

```text
int32 a;
```

输入层不会关心这是关键字还是标识符，它只负责把每个字符按顺序交给词法系统。  
但如果文本里出现非 ASCII 字符，例如中文分号或全角空格，那么错误会先在这里暴露，而不是拖到词法或语法阶段。

如何扩展：

- 如果以后支持文件输入，可以新增 `FileResource`
- 如果以后支持 UTF-8，就应当替换或扩展 `AsciiStringSourceReader`，而不是把字符编码问题留给词法阶段兜底


## 3. 错误对象链路

错误系统的重点不是“有几种异常类”，而是这个项目把**错误消息**和**控制流中断**分开了。

也就是说：

- 有些问题会写入 `ErrorContext`
- 有些问题还会额外抛异常或中止当前流程

这两件事不是一回事。

`ErrorContext` 的作用是：

- 在整个编译链路中统一收集错误
- 让测试、报告、demo 都能在最后看到同一份错误集合

`DefaultErrorContext` 只是最简单的内存实现：

```java
private final List<CompileErrorMessage> errors;

public void addError(CompileErrorMessage message) {
    errors.add(message);
}
```

它刻意不做复杂逻辑，例如：

- 不去重
- 不排序
- 不分类聚合

因为它的职责就是“稳定收集”，而不是“智能处理”。

当前错误消息大致分四层：

- `IoErrorMessage`
- `LexicalErrorMessage`
- `SyntaxErrorMessage`
- `SemanticErrorMessage`

这使得一个全链路报告可以同时看见：

- 输入层失败
- 词法层失败
- 语法层失败
- 语义层失败

一个最小例子：

- 输入里有中文字符，输入层写 `IoErrorMessage`
- 词法无法匹配某个字符序列，写 `LexicalErrorMessage`
- `continue` 出现在 loop 外部，语义层写 `SemanticErrorMessage`

如何扩展：

- 如果以后要做 IDE 集成，可以保留 `ErrorContext` 接口不变，单独增加支持范围、分组、严重级别的实现


## 4. 词法规则构造链路

- `D:\IT_study\source\temp\compiler-front-theory\src\main\java\org\harvey\vie\theory\demo\LexicalDemo.java`

## 5. 词法自动机构造链路

这一层的重点不是“会 NFA/DFA 这套教材流程”，而是项目把这套流程做成了可替换的构造管线：

- regex 解析
- regex 树转 NFA
- NFA 转 DFA
- DFA 最小化
- 产出状态表

`DefaultLexicalDirector` 就是在协调这条管线。

关键代码片段：

```java
for (LexicalPattern pattern : patterns) {
    pairs.add(new RegexTypePair(regexParser.parse(pattern.getRegex()), pattern.getType()));
}
NfaStatusGraph<AlphabetCharacter, TokenType> nfaStatusGraph = regexNfaAdaptor.adapt(pairs);
DfaStatusGraph<AlphabetCharacter, TokenType> dfaStatusGraph = nfaDfaAdaptor.adapt(nfaStatusGraph);
return dfaMinimizer.minimize(regexDfaStatusTableFactory, dfaStatusGraph);
```

这段代码清楚地说明了一个设计技巧：  
**词法规则不是直接解释执行，而是先编译成状态机。**

这样做的好处是：

- 扫描阶段更快
- 规则集合可以持久化
- 正则设计与扫描实现分离

一个最小例子：

- `if`
- `identifier`

这两条规则在模式层可能存在前缀关系，但经过统一自动机构造后，最终由状态表来决定最长匹配和类型归属，而不是靠一串手写 `if-else` 判断。

如何扩展：

- 如果以后要支持不同字母表，可以换 `AlphabetCharacterFactory`
- 如果以后要支持不同正则语法，可以换 `RegexParser`
- 不需要碰 `DefaultLexicalAnalyzer` 本体

`direct(List<LexicalPattern> patterns)` 的步骤可以概括为：

1. 对每个 `LexicalPattern`：
   - `regexParser.parse(pattern.getRegex())`
   - 构造 `RegexTypePair`
2. `regexNfaAdaptor.adapt(pairs)`
3. `nfaDfaAdaptor.adapt(nfaStatusGraph)`
4. `dfaMinimizer.minimize(regexDfaStatusTableFactory, dfaStatusGraph)`
5. 返回 `RegexDfaStatusTable`


## 6. 词法扫描链路

扫描阶段的职责，是把输入字符流按 DFA 状态表切成 token 流。

这一层的关键不是“写一个 next()”，而是三件事同时成立：

1. 扫描器不再理解正则，只理解状态表
2. 扫描器要能处理最长匹配结束点
3. 扫描器要把词法错误写进统一 `ErrorContext`

当前入口很简单：

```java
new StatusTableTokenIterator(errorContext, resource.toReader(errorContext), saca, table)
```

真正的核心在 `StatusTableTokenIterator.next0()` 的主循环。可以简化理解成：

```java
read character
  -> adapt to alphabet
  -> move DFA state
  -> if cannot continue, try split current token
  -> reset to start state and continue
```

其中最关键的设计技巧是：**不是每读一个字符就马上产出 token，而是一直推进到“再也走不下去”为止，再回头把前一段切成一个 token。**

这正是自动机扫描的本质。

一个最小例子：

```text
int32 a;
```

扫描过程大致是：

- 读到 `i n t 3 2`，DFA 落在 `TYPE_INT32` 的接受态
- 继续读空格时发现不能再延伸
- 于是把前面的 `int32` 切成一个 token
- 然后从起始态重新开始读 `a`

如果切分点没有接受态，例如：

```text
"unfinished
```

那么 `trySplitToken()` 就会发现当前状态不可接受，于是写入 `LexicalErrorMessage`。

如何扩展：

- 一般不需要碰扫描器本身
- 绝大多数扩展都应该通过“新增词法规则 + 重建状态表”完成
- 只有当字母表模型或错误恢复策略要变时，才需要改这一层


## 7. token 过滤链路

过滤链路存在的原因，是词法层会产出“语法上无意义但诊断上有价值”的 token。

最典型的就是：

- 空白
- 行注释
- 块注释

如果词法层一开始就彻底忽略它们，会有两个问题：

- 不利于调试词法规则是否正确
- 某些诊断或格式化需求以后可能拿不到原始 token

所以当前设计是：

1. 词法层把它们照常产出
2. 语法层之前再按策略过滤

这样“是否保留某类 token”变成一个可配置决策，而不是写死在词法扫描器里。

Program 语言当前过滤掉：

- `SPACE`
- `COMMENT_LINE`
- `COMMENT_BLOCK`

这意味着 Program 语法规则完全不需要为这些噪声 token 留位置。

一个例子：

```text
int32 a;   // comment
```

词法层会先产生注释 token；  
进入语法分析前，过滤层把它丢掉，所以 parser 看到的仍然只是声明语句所需的 token 序列。

如何扩展：

- 如果某种语言保留换行有语义，就不要在这里过滤换行
- 如果要做注释保留或格式化工具，就可以调整过滤策略而不是推翻词法规则


## 8. token 类型链路

`ProgramTokenType` 不只是一个枚举清单，它同时承担了三件事：

1. 给词法规则一个稳定的 token 身份
2. 给错误提示和调试输出提供可读名字
3. 给状态表持久化提供可存储、可加载的编号

因此 token 类型不是“为了写 switch 好看”，而是整个词法/语法系统共享的公共字典。

其中 `priority` 的存在，说明项目允许某些模式发生竞争时按优先级裁决。  
这在关键字与标识符、不同字面量类别之间尤其重要。

一个最小例子：

- `continue` 与普通标识符都能匹配字母串
- 但因为有专门的关键字 token 类型和对应规则，最终它会被识别成 `CONTROL_STRUCTURES_CONTINUE`

如何扩展：

- 新增 token 时，不要只加正则规则
- 必须同时把对应的 `ProgramTokenType` 枚举值加进去，否则持久化、提示和后续语法层都无从对接


## 9. 文法构造链路

文法构造层的目标，是把“人写的 grammar”转成一个统一的内部表示，供 FIRST/FOLLOW、LL、LR、语义注册等多处共用。

这里没有直接手写大文本 parser，而是设计了一套 builder 风格 DSL：

- `define("head")`
- `alternate...`
- `concatenate...`

这套 DSL 的价值在于：

- 写文法时比较接近产生式本身
- 同时又能直接生成结构化对象
- 后续算法不需要重新解析文法字符串

一个典型片段是：

```java
contextBuilder.define("block")
    .alternateTerminal(ProgramTokenType.OPERATOR_BRACE_OPEN)
    .concatenateDefinitionLast("block_items")
    .concatenateTerminalLast(ProgramTokenType.OPERATOR_BRACE_CLOSE);
```

这就等价于：

```text
block -> { block_items }
```

设计技巧在于：

- 左部通过 `define(...)` 建立
- 每个 `alternate...` 开启一个新的候选体
- `concatenate...` 则在当前候选体后继续拼接符号

因此文法不是字符串拼接，而是结构化构造。

如何扩展：

- 新增一个非终结符时，从 `define("...")` 开始
- 新增一个分支时，用新的 `alternate...`
- 如果是 Program 语言扩展，优先改 `ProgramSyntaxDemo.buildGrammar0()`

## 11. FIRST 集链路

FIRST 集的作用，不只是给教科书例题服务，而是后面多个算法的公共基础：

- FOLLOW 计算要用它
- LL 表构造要用它
- LR lookahead 传播也要用它

当前项目在实际链路里选用的是迭代不动点实现，而不是朴素递归实现。  
原因很实际：

- 更适合统一处理 epsilon、拼接串、相互递归
- 更容易作为后续算法的稳定基础

它的核心思想就是：

1. 先给所有终结符建立最初 FIRST
2. 再反复扫全部产生式
3. 直到整个 FIRST 映射不再变化

这是一种典型的不动点求解。

如果读者要扩展 grammar，通常不需要改 FIRST 算法本身；  
真正重要的是理解：**只要 grammar 结构合法，这套 FIRST 计算会自动跟上。**


## 12. FOLLOW 集链路

FOLLOW 主要服务两件事：

- LL 表中 epsilon 产生式的落点
- 某些语法分析相关的后继决策

当前实现同样走的是结构化算法，而不是从文法文本上做字符串推导。

可以把它理解成三步：

1. 起始符先拿到输入结束标记
2. 每条产生式内部，把后继串的 FIRST 往前传播
3. 如果后继可空，再把 head 的 FOLLOW 往前传播

这本质上也是一个不动点传播过程。

例子：

```text
A -> B C
```

那么：

- `FIRST(C)` 会影响 `FOLLOW(B)`
- 如果 `C =>* ε`，则 `FOLLOW(A)` 也会继续影响 `FOLLOW(B)`


## 13. LL 预测分析表链路

项目同时保留 LL 预测分析表链路，不是因为 Program 语言靠它运行，而是因为这个仓库本身既是前端工程，也是语法分析算法实验场。

LL 表构造体现的是另一种思想：

- 在分析前把“看到某个输入符号时该选哪条产生式”预先算好

它依赖：

- FIRST
- FOLLOW

填表原则就是经典规则：

- `FIRST(α)` 里的终结符指向 `A -> α`
- 如果 `α` 可空，再用 `FOLLOW(A)` 补表

这一层的价值主要在于：

- 验证 grammar 是否适合预测分析
- 给 TD demo 提供一条独立于 LR 的参考链路


## 14. LR 项集族链路

项集族是 LR 链路的骨架。

它解决的问题是：

- parser 在某个状态下，当前究竟“正在识别哪些产生式的哪一段”

每个 item 可以理解成：

```text
A -> α · β
```

表示：

- `α` 已经看过了
- `β` 还没看

项集族构造的本质，就是不断做：

- `closure`
- `goto`

直到所有状态都被发现。

这里采用 BFS 去扩整个项集族，是因为：

- 状态图天然就是从初始项集不断外扩
- 每个新项集都可能再产生新的 goto 目标

这一层一旦理解，后面的 LR ACTION/GOTO 表就不再神秘，本质上只是“把状态图和规约条件编码成查表数据”。


## 15. Lookahead 链路

lookahead 这层的作用，是把“什么时候可以规约”说得更精确。

如果只有 LR(0) 项，那么：

- 只要看到 `A -> α·`
- 就可能尝试规约

但这通常不够，因为还要知道：

- **在什么输入符号下** 规约才合法

于是项目又显式构造 lookahead 集合，并在项之间传播。

读法可以很朴素：

- 项集族决定“状态长什么样”
- lookahead 决定“这个状态里哪些规约在当前输入下才允许发生”

这层不是 Program 扩展时最常改的地方，但它是 LR 表正确性的关键来源。


## 16. LR 分析表构造链路

LR 分析表是把前面的理论结构最终压成工程上可执行的查表器。

可以把它理解成两张表：

- ACTION：看到某个终结符时做什么
- GOTO：规约出某个非终结符后转到什么状态

其中 ACTION 只有三类核心动作：

- shift
- reduce
- accept

而表项来源很清楚：

- `A -> α·aβ` 说明遇到 `a` 可以 shift
- `A -> α·` 且 lookahead 包含当前终结符，说明可以 reduce
- 增广起始项完成时说明 accept

这层一旦构好，parser 运行时就不需要再理解文法推导细节了，只要查表。

所以 LR 表构造本质上是在做一件事：

- 把 grammar 的结构知识离线计算掉
- 换成运行时可直接查询的状态机表


## 17. LR 分析表持久化链路

分析表持久化的目的很直接：表构造太重，不能每次都从头算。

当前序列化的不是一段“可读文本 grammar”，而是已经编好的表数据，包括：

- 终结符池
- 非终结符池
- ACTION
- GOTO
- 产生式池

因此持久化后的文件更像“编译产物”，而不是源码。

这里的设计取舍是：

- 平时运行可以优先加载已有表，提高速度
- 但在测试或 grammar 改动时，可以强制刷新，保证和当前 grammar 一致

这也是为什么项目里同时保留：

- `buildShiftReduceParsingTable(...)`
- `loadShiftReduceParsingTable(...)`

前者带“必要时重建”的能力，后者则是纯加载。

序列化内容之所以必须包含：

- 起始/接受状态
- 终结符与非终结符池
- 产生式池
- ACTION / GOTO 表

是因为运行期 parser 查表时需要的全部信息都在这里。  
加载之后，`ShiftReducePhaserImpl` 就可以直接调用：

- `activeNext(...)`
- `gotoNext(...)`
- `getProduction(...)`
- `matchTerminal(...)`

而不必重新理解 grammar 的原始构造过程。


## 18. `SyntaxDemo`

`SyntaxDemo` 是前半段算法设施汇流的地方。

它同时扮演三种角色：

1. demo 驱动器
- 给 TD / BU 两条语法分析链路提供可执行入口

2. 表构造器
- 统一封装 FIRST、项集族、lookahead、分析表的构造流程

3. 表缓存门面
- 决定何时直接加载已有表，何时按当前 grammar 强制刷新

关键代码片段：

```java
if (FLUSH_TABLE) {
    table = buildShiftReduceParsingTable0(startHead, context);
    storeTable(table, filename);
}
return loader.load(is);
```

这说明 `SyntaxDemo` 不是单纯的测试壳，而是一个工程入口：  
**既要照顾算法正确性，也要照顾构表成本。**

`buildShiftReduceParsingTable0(...)` 会把前面几节的算法真正串起来：

1. 先算 FIRST
2. 再构造项集族
3. 再传播 lookahead
4. 最后产出 LR 表

而 `buildPredictiveParsingTable(...)` 则走另一条 TD 流程，用来支撑预测分析 demo。

如果读者想验证一套新 grammar 最终能不能跑起来，这一节就是最关键的桥梁。


## 19. 自顶向下语法分析链路

TD 链路在这个项目里的定位，不是 Program 的主执行路径，而是：

- 给 LL 预测分析提供可运行实现
- 作为 LR 链路的对照组
- 帮助读者理解“同一套 grammar 思想换一种分析方式会怎样工作”

它的核心结构比 LR 更直接：

- 一个符号栈
- 一个当前输入 token
- 一张预测分析表

预测分析主循环本质上只做三种事：

1. 栈顶是终结符
- 就和当前输入 token 比较，匹配则消费

2. 栈顶是非终结符
- 就查预测分析表，决定展开哪条产生式

3. 栈顶是结束标记
- 决定是否 accept

这条链路的好处是直观，坏处是对 grammar 约束更强。  
因此它更适合作为教学、对照和局部验证工具，而不是当前 Program 全链路的主承载者。


## 20. 自底向上语法分析链路

BU 链路才是当前 Program 模式真正跑语义分析的主路径。

它的核心分层很清楚：

1. `ShiftReducePhaseContext`
- 保存 LR 状态栈、过滤后的 token 迭代器、错误上下文

2. `ShiftReducePhaserImpl`
- 依据 LR 表驱动 shift / reduce / accept

3. `ShiftReduceSemanticContext`
- 在相同的 shift/reduce 时机上挂接语义系统

关键代码片段：

```java
while (true) {
    SourceToken current = ctx.currentToken();
    int top = ctx.peek();
    ActiveTableElement element = table.activeNext(top, table.matchTerminal(current));
    if (element == null) {
        context.onError(ShiftReduceErrorType.UNDEFINED_ACTION);
    } else if (element.isShift()) {
        onShift(context, element, current);
    } else if (element.isReduce()) {
        onReduce(context, element);
        if (element.isAccept()) {
            break;
        }
    }
}
```

这段循环本质上只做一件事：  
**查表决定动作，然后把动作时机交给语义系统。**

它自己不负责：

- 建语法树
- 做类型
- 生成命令

这些都留给后面的 callback 总线去做。

一个最小例子：

```text
a = 1;
```

在 LR 主循环里会经历：

- 若干次 shift：接收 `a`、`=`、`1`、`;`
- 若干次 reduce：规约出 `loc`、表达式、语句
- 最后 accept

而每次 shift/reduce 又会同步驱动后面的语义系统，所以语法分析和语义分析并不是两个完全断开的阶段，而是**同一条事件流上的两层工作**。


## 21. 语义回调注册链路

这一层解决的问题，是把 LR 的事件时机和不同语义职责拆开。

在当前实现里，Program 模式的 shift-reduce 语义总线至少挂了这些通道：

- `TreeBuildCallback`
- `IdentifierScopeCallback`
- `TypeBuildCallback`
- `ConstantValueBuildCallback`
- `FunctionSemanticCallback`
- `SemanticResultCallback` 或 `SemanticCommandPrintCallback`
- `CommandBuildCallback`
- `IdentifierTableBuildCallback`
- `IdentifierConstantStateCallback`
- `PassiveErrorCallback`

测试入口 `SemanticDemo.buildShiftReduceTestRegister()` 的实际顺序是：

```java
register.add(new TreeBuildCallback());
register.add(instanceIdentifierScopeCallback());
register.add(new TypeBuildCallback());
register.add(new ConstantValueBuildCallback());
register.add(new FunctionSemanticCallback());
register.add(new SemanticResultCallback());
register.add(instanceSyntaxDirectedTranslationCallback());
register.add(instanceIdentifierTableBuildCallback());
register.add(new IdentifierConstantStateCallback());
register.add(new PassiveErrorCallback());
```

这个顺序不是随便排的。

- 先建树，后面的语义都要对准稳定节点
- 再做作用域、类型、常量、函数约束，因为命令生成和标识符登记都要读这些属性
- 最后才是命令收束与结果导出

一个简单例子：

```text
int32 add(int32 a, int32 b) {
  return a + b;
}
```

在函数头和函数体各次 reduce 上，会并行发生：

- 建树：得到函数头、参数、return、block 等节点
- 类型：给 `int32`、`a+b`、`return` 的值节点绑定类型
- 常量：这里没有常量结果，所以大多节点不绑定常量属性
- 函数：登记函数签名，检查 `return` 是否与返回类型一致
- 命令：生成参数引用、求和、return 指令


## 22. `ShiftReduceSemanticContext`

`ShiftReduceSemanticContext` 不是“万能对象”，而是这些语义通道的共享会合点。

它保存的是三类东西：

1. parser 运行时公共状态
- 当前 shift/reduce 上下文
- 当前语法树顶点

2. 多条语义通道共享的中间态
- 树上下文
- 命令上下文
- 类型绑定
- 常量绑定
- 标识符表
- 函数表与当前函数体状态

3. 纯服务能力
- `TypeResolver`
- 隐式转换判断
- 常用类型比较与字面量解析

当前 translator 与 `type / constant / function` 模块的耦合方式，也正是通过这个上下文完成：

- translator 从 context / node 取类型属性
- translator 从 context / node 取常量属性
- translator 从 context 取函数记录或函数管理器

也就是说，translator 并不自己重做类型推导、常量折叠、返回流分析；  
它只消费前面已经绑定好的语义属性。


## 23. 语法树链路

语法树在这里不是调试产物，而是后续所有语义属性的附着点。

`TreeBuildCallback` 做的事情很直接：

- shift token 时压入 `TokenNode`
- reduce 时按产生式弹出孩子，组装成 `HeadNode`

一旦当前 reduce 的头节点建立完成，其他 callback 就都可以对准同一个对象工作：

- `TypeBuildCallback` 把 `TypeRegister` 绑到它上面
- `ConstantValueBuildCallback` 把 `ConstantValue` 绑到它上面
- `CommandBuildCallback` 根据它的孩子结构生成命令 register

例子：

```text
a = 1 + 2;
```

当 `1 + 2` 规约成表达式节点后：

- 类型通道可以得出这是数值表达式
- 常量通道可以得出它的值是 `3`
- 命令通道可以直接装载常量，而不是真的保留一次运行时加法


## 24. 节点属性链路

当前最重要的语义属性有两类：

- 类型属性
- 常量属性

两者都绑定在语法树节点上，而不是放在“与树平行的一条额外栈”里。

这样做的好处是：

- reduce 后的稳定对象就是节点
- 任何后续阶段都能重新按节点取回属性
- 不会出现“第几个槽位对不上第几个节点”的错位问题

这里必须严格区分两种情况：

- 这个节点本来就没有该属性
- 这个节点在当前位置必须有该属性，但实际没取到

前者是合法的，例如：

- `block`
- `break ;`
- `while (...) stmt`

后者则是语义规则缺失或前置阶段漏绑定，必须立刻失败。

这也是为什么当前读取辅助类会区分：

- 读取：允许拿到 `null`
- `require...`：必须有值，否则直接抛错


## 25. 作用域链路

作用域链路的重点，是把“块的开始”和“块的完成”对准 LR 的真实时机。

当前实现用的是：

- shift `{` 时进入作用域：`scopeIntoBlock()`
- reduce 整个 `block` 时退出作用域：`scopeExistBlock()` + `finishBlockScope()`

对应代码形态是：

```java
public void onShift(ShiftReduceSemanticContext context, int nextStatus, SourceToken token) {
    if (scopeIntoPredicate.test(token)) {
        context.scopeIntoBlock();
    }
}

private void onReduce0(ShiftReduceSemanticContext context, SimpleGrammarProduction production)
        throws CompileException {
    if (!scopeExistPredicate.test(production)) {
        return;
    }
    IdentifierRecord[] scope = context.scopeExistBlock();
    context.finishBlockScope();
}
```

这背后的设计点是：

- token 只负责告诉系统“边界开始了”
- 真正的块内容只有在 reduce 完整个 `block` 后才算定型

当前 `IdentifierScopeCallback` 还顺带承担了一个函数体出口检查：

- 如果当前 block 是函数体
- 且函数返回类型不是 `void`
- 且 `FunctionManager.guaranteesReturn(...)` 判断不保证返回
- 就直接拒绝这个函数体


## 26. 标识符表链路

标识符链路分成两件事：

1. 使用点检查
2. 声明点登记

当前 `IdentifierTableBuildCallback` 用两个 predicate 分开触发：

- `IDENTIFIER + USE` 时检查是否可见
- `DECLARATION` 时登记一条新的标识符记录

声明登记并不是只记名字。它实际会读取：

- 声明名字
- 是否初始化
- 类型节点上的 `TypeRegister`
- 初始化表达式上的常量值（如果有）

也就是说，标识符表不是孤立模块，它依赖前面的类型和常量属性。

一个声明例子：

```text
int32 x = 1;
```

登记时会同时形成：

- 名字：`x`
- 声明类型：`int32`
- `initialized = true`
- `constantValue = 1`


## 27. `IdentifierTableBuilder`

`IdentifierTableBuilder` 本质上是一个作用域栈，但它不只是保存“有哪些名字”，还区分了两种编号：

- `no`：全局记录号
- `offset`：当前作用域内偏移

这让输出报告时可以同时看见：

- 这条记录在整个编译过程中的唯一编号
- 它在所在作用域里的相对位置

当前查找策略也很直接：

- 从栈顶作用域向外查
- 找到第一条同名记录就返回

所以内层遮蔽外层是天然成立的，不需要额外规则。


## 28. 命令构建链路

命令构建通道分成两层：

1. token translator
2. production translator

`CommandBuildCallback` 只负责把 LR 的 shift/reduce 事件交给这两层策略，不自己写具体语义。

入口代码是：

```java
private static ShiftReduceCallback instanceSyntaxDirectedTranslationCallback() {
    return new CommandBuildCallback(shiftStrategies(), reduceStrategies0());
}
```

这里的设计重点不是“又包了一层”，而是把两种完全不同的判断时机分开：

- 单个 token 就能决定的叶子语义，放在 shift
- 必须等孩子都规约好才能决定的组合语义，放在 reduce

例如：

- `break`、`continue`、字面量、标识符引用适合在 shift 建立局部 register
- 赋值、函数调用、`if`、`while`、二元表达式适合在 reduce 组合


## 29. token translator 链路

当前 token translator 只处理“单个 token 足以成立”的语义单元。

Program 模式里比较关键的有：

- `LoadIdentifierReferenceTokenTranslator`
- `SimpleStringTokenTranslator`
- `TypeTokenTranslator`
- `BreakTokenTranslator`
- `ContinueTokenTranslator`

它们分别解决：

- 读取变量引用
- 直接装载字面量
- 为类型 token 提供占位 register
- 为 `break` / `continue` 生成未决跳转

这一层有意保持很薄，因为它不该去推断兄弟节点关系。

例如 `IDENTIFIER` 在 shift 时只能知道“这里有一个标识符 token”，  
但它是不是函数调用、是不是数组访问、是不是左值，要等 reduce 到更完整结构后才能判。


## 30. production translator 链路

production translator 才是真正承载组合语义的地方。

当前 reduce 分发不再靠：

- 孩子个数
- 产生式打印字符串
- head 名字字符串

而是通过 `TagStrategyCompose.stringCommand()` 构造的 `ProductionTagStrategy<CommandTranslator>`，按 `ProgramSemanticTag` 组合分发。

例如当前注册关系里有：

```java
.when(returnTranslator, ProgramSemanticTag.RETURN)
.when(functionCallTranslator, ProgramSemanticTag.FUNCTION, ProgramSemanticTag.CALL)
.when(declarationWithInitializationTranslator, ProgramSemanticTag.DECLARATION, ProgramSemanticTag.INITIALIZED)
.when(ifElseStatementTranslator, ProgramSemanticTag.CONDITIONAL, ProgramSemanticTag.ELSE_BRANCH)
.when(whileStatementTranslator, ProgramSemanticTag.LOOP)
```

这意味着 translator 关心的是“这个 reduce 产物的语义标签组合”，而不是“这个产生式打印出来像不像某个字符串”。

这里还有一个关键分工：

- tag 决定由哪个 translator 接手
- translator 再通过 context / children 读取已经存在的类型、常量、函数信息

所以 tag 解决的是“语法结构如何对接语义组件”，  
而不是替代源码 token 本身。


## 31. `CommandNodeRegister`

`CommandNodeRegister` 是命令系统里最重要的中间对象。

它同时承担两类责任：

1. 输出命令结构
- `register(CommandNodeBuilder outer)`

2. 携带这棵子树尚未解决的控制流信息
- 未绑定的 `break`
- 未绑定的 `continue`

这使得一个子树不只是“几条命令”，而是“几条命令 + 尚未被外层循环吸收的跳转问题”。

这点对常量条件裁剪尤其重要。  
即使某个分支因为常量条件被消掉，不输出命令，也不能把该分支中非法的 `break / continue` 静默吞掉。


## 32. 命令树链路

当前系统不是 reduce 一次就往最终 `List<String>` 里拼文本，而是先建立命令树。

原因很实际：

- label 的最终行号在拍平前不知道
- `if / while / do-while` 天然是嵌套结构
- `break / continue` 的绑定依赖更外层 loop translator
- 常量裁剪会影响哪些命令真正留下

所以命令系统分两步：

1. 先建结构
- `TerminalNode`
- `LabelNode`
- 组合节点

2. 最后统一拍平
- 收集 label 最终索引
- 输出稳定的三地址命令序列

这和语法树、类型属性、常量属性的设计是一致的：  
先保留结构，最后再线性化。


## 33. 常量链路

常量系统当前也是节点属性系统。

`ConstantValueBuildCallback` 在 reduce 时按 tag 分发规则，给“可在编译期确定值的节点”绑定 `ConstantValue`。

当前覆盖的核心情况包括：

- 标量字面量中的 `boolean / int32 / float64`
- 一元 `-`、`!`
- 二元算术
- 二元逻辑
- 相等 / 不等
- 大小比较
- 常量标识符引用
- 括号与部分转发节点

这里有两个需要明确的边界：

1. 并不是所有字面量都会绑定 `ConstantValue`
- 当前 `string / character` 字面量不会在这个回调里生成 `ConstantValue`
- 但 token translator 仍然可以直接为它们生成装载命令

2. “没有常量值”不等于错误
- 它只表示当前表达式不能在编译期折叠
- 例如 `a + 1` 如果 `a` 不是常量，就不会绑定常量值

常量系统的直接收益有两类：

- 表达式常量折叠
- 条件常量裁剪

例如：

```text
if (1 < 2) {
  x = 1;
} else {
  x = 2;
}
```

在当前链路里：

- `1 < 2` 会先绑定常量布尔值 `true`
- `IfElseStatementTranslator` 再通过 `ConstantConditionSupport` 读取这个常量
- 最终只保留 then 分支命令


## 34. translator 与属性协作

当前 translator 与 `type / constant / function` 模块的正确耦合点，是“读取节点属性与上下文服务”，不是直接把各模块内部逻辑重新抄一遍。

这在当前代码里表现得很明显：

- `AssignStatementTranslator` 用 `TypeAttributes.childType(...)` 取左右类型，再决定是否插入 `st_top_cast`
- `DeclarationWithInitializationTranslator` 也是先取类型属性，再做赋值兼容性判断
- `FunctionReturnTranslator` 用 `production.containsTag(ProgramSemanticTag.VALUE)` 判断是否有返回值，再通过 `ConstantAttributes` 决定直接装常量还是注册子命令
- `IfStatementTranslator` / `IfElseStatementTranslator` / `WhileStatementTranslator` 通过 `ConstantConditionSupport` 判断条件是否是编译期常量

可以把它理解成两层：

- 上游 callback 负责“把语义事实算出来并绑定到节点”
- translator 负责“消费这些事实，把命令正确拼出来”

一个赋值例子：

```text
float64 x;
x = 1;
```

流程不是 translator 自己重新推类型，而是：

1. `TypeBuildCallback` 先把左值类型和右值类型都绑好
2. `AssignStatementTranslator` 取出这两个类型
3. `SemanticDiagnostics.requireAssignable(...)` 检查是否允许赋值
4. `context.requiresImplicitCast(...)` 判断是否需要插入编码转换
5. 真正需要时生成 `st_top_cast`


## 35. `break / continue` 链路

`break` 和 `continue` 在 shift 时先生成未决跳转，在 reduce 时随子树向上传递，到真正的 loop translator 再绑定目标。

当前关键步骤是：

1. shift `break` / `continue`
- 建立带未决 label 的命令 register

2. 子树合并
- `NormalCommandNodeRegister` 聚合所有孩子未决跳转

3. loop translator 绑定
- `while` 把 `continue` 绑到循环头，把 `break` 绑到循环尾
- `do-while` 把 `continue` 绑到条件检查点，把 `break` 绑到循环尾

4. 顶层兜底
- `ProgramCommandTranslator` 检查程序顶层是否还残留未绑定跳转

这个设计的要点不是“列表往上传一传”，而是：

- 未决跳转与子树绑定
- 目标绑定只在知道完整循环骨架的那一层发生

这能正确处理：

- 单层循环
- 嵌套循环
- 常量裁剪后的死分支中的非法控制流


## 36. 类型链路

类型系统当前最核心的设计，是“类型是节点属性，不是平行栈”。

`TypeBuildCallback` 在每次 reduce 时按 `ProgramSemanticTag` 组合分发规则，决定当前头节点是否绑定一个 `TypeRegister`。

`TypeRegister` 当前保存三件事：

- `type`
- `instructionType`
- `anchorToken`

三者的语义不同：

- `type`：这个节点作为值时的最终类型
- `instructionType`：做运算时应采用的指令类型
- `anchorToken`：报错时应定位到哪个源码 token

例如关系表达式：

```text
1 < 2.0
```

它的：

- `type` 是 `boolean`
- `instructionType` 是提升后的公共数值类型 `float64`

这就是为什么当前实现不能只存一个“结果类型”。

另一个关键点是“无值”和“缺类型”分开：

- `result == null` 只表示这个节点本来没有类型属性
- 真正需要类型的地方，必须显式 `requireType(...)`

当前 `TypeAttributes` 提供的读取方式也是这个思路：

- `child(...)` / `result(...)`：读取 register
- `childType(...)` / `childInstructionType(...)`：强制要求存在
- `childAnchor(...)` / `resultAnchor(...)`：读取定位 token

目前覆盖的类型规则包括：

- 基本类型与数组类型
- 声明标识符
- 标识符引用
- 数组下标访问
- 函数调用
- 一元逻辑 / 一元数值
- 二元逻辑 / 算术 / 比较 / 相等
- 赋值
- `void` 函数头

赋值与初始化的实际流程是：

1. 先取左右类型
2. 检查是否可赋值
3. 若允许但编码不同，则插入 `st_top_cast`
4. 最后生成赋值命令

例如：

```text
float64 x;
x = 1;
```

当前行为是：

- 允许赋值
- 但仍然显式插入一次从 `int32` 到 `float64` 的栈顶转换命令


## 37. 函数链路

函数语义当前分成两部分：

1. `FunctionSemanticCallback`
2. `FunctionManager` / `FunctionReturnFlowAnalyzer`

### 37.1 函数声明、调用、return 检查

`FunctionSemanticCallback` 负责三件事：

- 函数头 reduce 时登记函数签名
- `return` reduce 时检查返回值是否合法
- 函数调用 reduce 时检查实参与形参是否匹配

它当前同样通过 `ProductionTagStrategy` 分发：

```java
.when((context, head, production) -> prepareFunction(context, head),
        ProgramSemanticTag.FUNCTION,
        ProgramSemanticTag.HEAD)
.when((context, head, production) -> validateReturnValue(
        context, head, production.containsTag(ProgramSemanticTag.VALUE)
), ProgramSemanticTag.RETURN)
.when((context, head, production) -> validateCall(context, head),
        ProgramSemanticTag.FUNCTION,
        ProgramSemanticTag.CALL)
```

这里最重要的改动点，是 `return` 是否带值不再靠孩子个数判断，而是直接看 `ProgramSemanticTag.VALUE`。

### 37.2 参数与实参列表

当前参数表和实参表不再在 callback 里递归 DFS 抽取，而是通过一个通用的语法树列表迭代器完成：

- `SyntaxTreeListIterator<T>`
- `Stepper<T>`
- `SequnceStep<T>`

`SyntaxTreeListIterator` 自己不懂 `param` 或 `arguments`，它只做一件事：

- 持有当前列表节点
- 每次 `next()` 后，把游标替换到由 stepper 指定的“下一个尾部”

`ParameterStepper` 和 `ArgumentStepper` 只提供“如何从当前节点迈到下一项”的规则：

- `EMPTY` 表示停止
- `FORWARD` 表示继续向下转发
- `SEQUENCE` 表示产出当前项并把 tail 交给下一轮

这样 `FunctionSemanticCallback` 就能用统一迭代方式收集：

- 形参 `List<FunctionParameter>`
- 实参 `List<TypeRegister>`

而不需要为每一种列表结构单独写一套递归抽取逻辑。

### 37.3 返回流检查

函数体是否“保证返回”，当前由 `IdentifierScopeCallback` 在 block reduce 时触发检查，具体判定委托给：

- `FunctionManager`
- `FunctionReturnFlowAnalyzer`

`FunctionManager` 当前很薄，它只是把这个能力挂到 context 上，实际规则都在 `FunctionReturnFlowAnalyzer` 里。

当前返回流分析已经不再靠 head 名字字符串或孩子长度识别结构，而是基于 tag 分发：

- `BLOCK + COMMAND`
- `BLOCK + LIST + EMPTY`
- `BLOCK + LIST + SEQUENCE`
- `FORWARD`
- `RETURN`
- `CONDITIONAL + ELSE_BRANCH`

当前规则的语义是：

- `return` 本身保证返回
- block 列表只要前项或后项保证返回，则整个序列保证返回
- `if-else` 若条件是编译期常量，则只看实际会走的那一支
- `if-else` 若条件不是常量，则两支都保证返回时才算保证返回

例如：

```text
int32 f(bool c) {
  if (c) {
    return 1;
  } else {
    return 2;
  }
}
```

这里返回流分析会判定函数体保证返回。  
但如果去掉 `else`，当前非 `void` 函数就会在函数体 block 退出时被拒绝。


## 38. 结果提取链路

`SemanticResultCallback` 的职责，是把内部命令树和符号表收束成稳定对外结果。

它不在中间阶段过早导出，而是在 accept 前处理，原因很简单：

- 顶层命令树此时才完整
- label 的最终索引此时才稳定
- 标识符表也已经完成块级进出

最终对外暴露的是 `SemanticAnalysisResult`，而不是内部所有中间状态。


## 39. `SemanticAnalysisResult`

`SemanticAnalysisResult` 当前只暴露最终结果：

- 命令列表
- 标识符记录数组

它不把语法树、类型绑定、常量绑定、未决跳转之类的中间结构继续向外泄露。  
这让测试与报告关注的是“最终行为”，而不是内部过程快照。


## 40. 测试链路

`ProgramSyntaxTestRunner` 当前是完整的 Program 全链路测试入口。

它实际做的事情是：

1. 从 `src/main/resources/program-tests` 读取测试用例
2. 用 `SyntaxDemo.buildShiftReduceParsingTable(...)` 构造分析表
3. 用 `ShiftReducePhaserImpl(...)` 跑完整的词法、语法、语义链路
4. 写单用例报告和汇总报告

当前测试入口实际会用到这些配置：

- `syntax_table.data`
- 系统属性 `program.testCase`

它们的意义分别是：

- `syntax_table.data`：LR 分析表的序列化文件名
- `program.testCase`：只运行指定 basename 的单个用例

例如：

- 不传 `program.testCase` 时跑全部 `.txt` 用例
- 传 `-Dprogram.testCase=text31-function-return` 时，只跑 `text31-function-return.txt`

当前观察结果并不只看“有没有抛异常”，而是明确区分：

- `Expected`
- `Observed`
- `Matched`

对应核心判断是：

```java
boolean expectedFailure = caseName.contains("invalid");
boolean hasErrors = !errorContext.isEmpty();
boolean observedRejected = failure != null || hasErrors;
boolean observedAccepted = executedSuccessfully && !hasErrors;
boolean matchedExpectation = expectedFailure ? observedRejected : observedAccepted;
```

所以一个用例即使没有抛异常，只要 `errorContext` 里写入了语义错误，也会被算作 reject。


## 41. 报告输出链路

当前测试报告不是只有一个 PASS / FAIL，而是把可审计信息完整写出来。

单用例报告包括：

- 源码
- 生成命令
- 符号表
- 错误列表
- 异常

汇总报告包括：

- 本次 run id
- 总用例数、通过数、失败数
- 每个 case 的观察结果、错误数、命令数、符号数、报告路径

这样测试不只是验证“断言是否通过”，还可以复盘：

- 跳转目标是否正确
- 常量裁剪后命令顺序是否合理
- 标识符记录是否落在预期作用域
- 函数 return 检查是否符合预期


## 42. Program 主链路

把 Program 模式压成一条主线，就是：

1. 输入层把源码文本读成字符流
2. 词法层把字符流切成 token 流
3. 语法层用 LR 分析表驱动 shift / reduce
4. 同一次 shift / reduce 事件广播给多条语义回调
5. 这些回调逐步建立：
- 语法树
- 作用域
- 标识符表
- 类型属性
- 常量属性
- 函数记录与返回约束
- 命令树
6. accept 前再把命令树拍平成最终命令列表
7. 输出 `SemanticAnalysisResult`
8. 测试入口把结果与错误上下文写成报告

如果从扩展角度看，比较实用的顺序仍然是：

1. 增加 token
2. 增加 grammar 与 tag
3. 给需要的 reduce 接上合适的 translator / callback 规则
4. 补类型规则或常量规则
5. 补全链路测试

例如新增一个“会产生值的表达式结构”时，通常至少要考虑：

- `ProgramSyntaxDemo` 里给产生式打哪些 tag
- `TypeBuildCallback` 是否要给它绑定类型
- `ConstantValueBuildCallback` 是否能对它做编译期求值
- `TagStrategyCompose` 是否要给它接命令 translator
- `program-tests` 里是否有覆盖它的正反例
