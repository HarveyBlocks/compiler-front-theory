## 第一阶段：明确数组与结构体的设计边界

### 1. 先确认数组的类型语义

这一阶段首先确认，数组类型不应该把“长度”编码进类型本身，而应该只保留：

- 基础元素类型
- 维度层数

对应结论是：

- `int[]`
- `int[][]`

属于不同类型；

但：

- `new int[10]`
- `new int[n + 1]`

只是在创建时长度表达式不同，不会形成两种不同类型。

这一步的意义是把“数组类型”和“数组创建参数”彻底拆开，避免后续出现：

- 类型检查混入长度值
- 赋值兼容性过度复杂化
- 锯齿数组无法表达

### 2. 再确认结构体的对象语义

这一阶段确认结构体不是值对象语义，而是引用对象语义，和数组归入同一大类：

- 结构体变量本身放在局部变量表里
- 变量槽位里保存的是对象引用
- 真正的结构体实例在对象区

这个决策直接影响后面三件事：

1. `null` 合法性
2. 参数传递方式
3. 中间代码命名

### 3. 确认 `null` 的定位

这里没有把 `null` 当作普通基础字面量，而是明确为：

- 一种特殊常量
- 只对引用类型可赋值

这一步解决的是后续语义判断的边界问题，避免把：

- `null -> int`
- `null -> boolean`

这种本不该允许的路径混进去。

### 4. 确认中间代码命名边界

当时专门统一了一条很重要的约定：

- 局部变量表槽位位置叫 `addr/address`
- 对象引用叫 `ref/reference`

这一步看起来只是命名，其实是在提前避免语义污染。  
如果不先把这两个概念拆开，后面数组和结构体做起来会越来越乱。

### 5. 这一阶段产出

这一阶段主要产出的是设计文档与统一约定，核心文档是：

- `docs/数组与结构体优化步骤说明.md`

这一步还不是为了直接让代码跑通，而是先把方向钉住，避免后面一边改一边重定义问题。

## 第二阶段：把数组与结构体的文法骨架补起来

### 1. 数组相关文法目标

数组部分的目标是让文法能表达：

- 数组类型声明
- 数组创建表达式
- 数组索引访问

并且把：

- 类型层
- 创建层
- 访问层

分开，不用一个产生式硬承担所有语义。

### 2. 结构体相关文法目标

结构体部分的目标是让文法能表达：

- 结构体声明
- 结构体字段列表
- 结构体实例化
- 成员点访问

这里一个关键选择是：

- 结构体声明放在顶层
- 结构体使用放进表达式和语句

也就是把：

- `struct_decl`
- 普通 `block_item`

有意分开。

这一步不是“保守”，而是为了不让顶层定义和块内执行语句混成一个层级，避免后面扩展函数、结构体类型表、作用域时继续纠缠。

### 3. `new StructName()` 的设计收敛

这里还确认了一条很重要的文法方向：

- 放弃 `new()`
- 改成 `new StructName()`

原因很明确：

- `new()` 在表达式环境中没有自描述类型能力
- `func(new().value)` 这类场景会完全失去结构体类型来源

所以这一阶段确定：

- 结构体创建表达式必须显式带类型名

## 第三阶段：把结构体语义注册链路补起来

### 1. 结构体声明不只是“能 parse”

结构体声明真正要成立，不只是语法通过，还要在语义层完成：

- 注册结构体名
- 收集字段
- 检查字段重名
- 检查字段类型是否合法
- 为字段分配稳定偏移

所以这一阶段实际上补的是“结构体类型表”与“字段布局”这两个核心对象能力。

### 2. 字段偏移的意义

成员访问最终不会保留“按字段名访问”这种高层形式，而要落成：

- 先拿对象引用
- 再根据字段偏移做访问

所以字段收集时就不能只记名字，还要记：

- 字段类型
- 字段顺序
- 字段偏移

这一步的意义，是让中间代码在成员访问阶段不再依赖名字查找，而是依赖已经绑定好的布局信息。

---

## 第四阶段：把对象访问与命令层约定对齐

### 1. 数组访问与结构体访问统一思路

数组和结构体在命令层最终都采用：

- 先得到对象引用
- 再得到元素/字段偏移
- 再做引用位置读写

也就是说，这两个功能虽然语义不同，但在命令层被统一为“引用对象访问”。

### 2. 左值与右值边界继续保持

这一步延续了前面你一直强调的原则：

- 左值位置不能被当常量值替换
- 引用位置和取值位置必须分清

所以成员访问、数组访问在命令层也必须区分：

- 这是一个位置
- 还是一个值

这一点直接影响后续：

- `assign_from_st_top_to_addr_xxx`
- `assign_from_st_top_to_ref_xxx`
- `st_top_addr_to_val_xxx`
- `st_top_ref_to_val_xxx`

这些命令的分流。

## 第六阶段：测试第一次暴露的问题

### 问题 1：结构体声明写在普通块里，语法直接失败

第一次写测试时，我把：

```text
{
    struct Point { ... }
    ...
}
```

写进了普通块。

结果：

- 直接语法失败

这里暴露的不是实现 bug，而是我测试样例写错了层级。  
因为当前文法里：

- `struct_decl` 只能出现在 `top_item`
- 不能作为 `block_item` 出现在普通块内部

### 处理方式

测试改成：

- 顶层先声明 `struct`
- 后面再进入 `{ ... }` 普通块使用

这一步虽然没有改代码，但很重要，因为它确认了：

- 当前文法边界是什么
- 结构体定义和普通执行代码的关系是什么

## 第七阶段：测试第二次暴露的问题

### 问题 2：`new Point()` 语法失败

当测试改成顶层结构体声明后，`new Point()` 仍然失败。

这一次就不是测试层级问题，而是文法和词法分类的真实接缝问题：

- 词法阶段会把结构体类型名在 `new` 后归类成 `TYPE_IDENTIFIER`
- 但 `new_struct_expr` 文法原先接的是 `IDENTIFIER`

所以会出现一种很怪的现象：

- `Point p;` 能通过
- `new Point()` 却语法失败

### 修正内容

把 `new_struct_expr` 从：

- `KEYWORD_NEW IDENTIFIER (...)`

改为：

- `KEYWORD_NEW TYPE_IDENTIFIER (...)`

### 这一步的意义

这一步不是为了让 `text41` 特判通过，而是把：

- 词法阶段的结构体类型重分类
- 文法阶段的结构体实例化入口

真正对齐。

## 第八阶段：测试第三次暴露的问题

### 问题 3：结构体字段列表在 `TypeBuildCallback` 里没有规则

修完 `new Point()` 之后，测试继续往后走，又暴露出新的真实问题：

- 结构体字段列表能被语法规约
- 但规约到类型构建阶段时，`TypeBuildCallback` 没有覆盖 `struct_field_list / struct_fields`

结果直接抛出：

- `unhandled production in TypeBuildCallback`

### 修正内容

把结构体字段列表相关产生式加入 `TypeBuildCallback` 的 `NONE` 规则范围：

- `LIST + STRUCT_FIELD + EMPTY`
- `LIST + STRUCT_FIELD + FORWARD`
- `LIST + STRUCT_FIELD + SEQUENCE`

### 这一步的意义

这不是“为了别报错瞎塞规则”，而是明确：

- 这些节点本身不应该生成表达式类型
- 但它们必须被类型构建框架识别为合法中间层

否则结构体声明链路永远无法通过。

## 第十阶段：确认语法表缓存问题并修正测试方式

### 问题

在修改文法后，如果直接跑测试，项目会继续加载：

- `src/main/resources/serial/syntax_table.data`

也就是旧的序列化语法表。

这会造成一种假象：

- 代码已经改了
- 但测试还表现成旧语法

### 处理方式

后续测试统一改成带刷新参数：

```powershell
mvn --% -q -Dsyntax.flushTable=true test
```

单个 case：

```powershell
mvn --% -q -Dsyntax.flushTable=true -Dprogram.testCase=text41-struct-declare-and-access test
```

### 这一步的意义

这一步不是功能代码修改，但它非常重要，因为如果不写进报告，后面任何人看见“文法明明改了却没生效”，都会误判问题位置。

## 这 7 个小时主要花在哪里

如果只看最后落在代码里的 diff，确实不算大。  
但这段时间实际消耗主要在下面这些工作上：

### 1. 梳理边界，而不是乱改

花时间确认：

- 数组类型是否和长度绑定
- 结构体是否按引用对象处理
- `null` 应该落在什么语义层
- `address` 和 `reference` 应怎么区分

这些事情如果不先明确，后面很容易出现大面积返工。

### 2. 反复验证“当前实现到底支持到哪”

不是直接写测试，而是先确认：

- 结构体语义回调在不在
- 结构体成员访问 translator 在不在
- `new_struct` 命令在不在
- `AppTest` 入口怎么挂进去

这部分花的是读代码和定位链路的时间。

### 3. 用测试把真实缺口逼出来

这次不是靠猜问题，而是逐步让测试把问题一个个暴露出来：

1. 测试层级写错
2. `new_struct_expr` 词法/文法不一致
3. `TypeBuildCallback` 漏规则
4. 语法表缓存导致假失败

每一步都不是一眼能看出的，需要跑、看报告、再定位。

### 4. 最后才是代码修改本身

真正改代码的行数不算很多，但前面的时间主要消耗在：

- 找边界
- 排假问题
- 定位真实缺口
- 反复验证

所以“花了很久但最后 diff 不大”在这次是正常现象，不是没有做事，而是主要时间花在了把事情做对。
