# 项目说明

## 1. 这个项目到底在做什么

这个仓库的核心价值，不是“有一个能跑通的 Demo”，而是把编译前端里几件通常分散讲解的事情，真正做成了一套可以组合、可以替换、可以实验的实现：

- 词法规则不是手写 `if-else` 扫描，而是先定义规则，再编译成自动机。
- 文法不是写死在解析器里，而是先构造成统一文法对象，再拿这份对象去算 FIRST/FOLLOW、建预测表、建移进归约表。
- 语义分析不是等语法树全出来后再做一个大遍历，而是跟着 shift/reduce 事件同步发生。
- 语义结果也不是只剩一串字符串命令，而是保留了结构体表、函数段、入口段、标识符记录这些真正有分析价值的结果。

如果把它理解成“一门 Program 小语言的编译器”，会漏掉很多东西。  
更准确的理解是：

它先是一套前端实验框架，Program 语言只是这套框架上目前最完整的一种配置。

## 2. 这套实现最重要的设计思路

这个仓库里最重要的设计思路，不是某条具体文法，也不是某个测试入口，而是下面三件事。

### 2.1 先把“描述”做成对象，再把“算法”建立在描述之上

无论是词法还是语法，这个项目都尽量避免“规则直接写进执行逻辑”。

词法这边先有：

- token 类型
- 正则模式
- 字母表

然后才有：

- regex 解析
- NFA
- DFA
- 最小化 DFA
- 运行时词法扫描

语法这边先有：

- 文法符号
- 产生式
- 文法上下文

然后才有：

- FIRST / FOLLOW
- 左递归消除
- 左因子提取
- 预测分析表
- LR 项集族
- lookahead
- ShiftReduce 表

这件事的价值很大，因为它把“语言描述”和“算法实现”分开了。  
一旦分开：

- 同一套词法引擎可以服务不同 token 配置
- 同一套语法算法可以服务不同文法
- Program 语言不会绑死整个仓库

### 2.2 语义阶段不单做“检查”，而是做“增量构建”

很多教学实现会把语义分析写成“语法分析完后，遍历一次 AST 再干活”。  
这个仓库不是这个方向。

这里的语义层是事件驱动的：

- shift 一个 token 时，某些语义信息就已经开始建立
- reduce 一条产生式时，类型、常量、命令片段、函数表、结构体表、作用域等都可能同步更新

这样设计的好处是：

- 语义逻辑和语法结构天然对齐
- 某些信息不必等全树完成后再推导
- 命令生成可以直接利用规约点上的结构信息

换句话说，这套实现不是“语法树先建完，再慢慢想怎么解释它”，而是“一边规约，一边把语义世界搭起来”。

### 2.3 结果保留结构，而不是过早拍扁

这个仓库很多地方都刻意避免“太早线性化”。

例如命令生成不是立刻往 `List<String>` 里拼文本，而是先保留：

- 命令节点
- 未绑定跳转
- 标签节点
- 函数段

等到真正需要输出时，再 flatten 成线性命令。

这样做的价值在于：

- `break` / `continue` 这类控制流问题，不会被过早抹平
- 函数体可以和入口段分离
- label 位置可以在最后统一确定
- 报告输出时可以区分“入口代码”和“函数代码”

这是一种非常工程化的取舍：  
先保留结构，最后再打印。

## 3. 仓库的整体组织方式

这个仓库不能按“某个类是不是主入口”来理解，而应该按“哪些层提供能力”来理解。

### 3.1 输入与错误层

这一层解决的不是“编译原理问题”，而是所有上层都依赖的两个前提：

1. 源码如何稳定读进来
2. 错误如何被统一记录

当前输入抽象不是裸字符串，而是 `Resource -> SourceReader -> SourceCharacter` 这一套。

这样做的意义是：

- 上层词法分析器不关心输入来自哪里
- 错误位置信息从最底层就开始跟踪
- 如果以后要从字符串换到文件、换到其他编码，改动会局限在输入层

当前默认读取器是 ASCII 约束的。  
这说明作者选择的是“尽早约束输入”，而不是把字符编码问题拖到词法阶段再兜底。

错误系统同样是统一抽象：

- IO 错误
- 词法错误
- 语法错误
- 语义错误

都进入同一个 `ErrorContext`。

这样做比“到处 throw exception”更适合实验工程，因为：

- 报告输出需要统一收集错误
- 某些阶段即使中断，也希望保留已经发现的问题
- 测试要区分“程序崩了”和“程序被正确拒绝了”

## 4. 词法层到底是怎么设计的

### 4.1 词法规则不是扫描器的一部分，而是扫描器的输入

这套词法实现的关键点，在于扫描器本身不知道“关键字”“整数”“注释”这些概念。  
它只知道：

- 当前状态
- 当前字符
- 下一个状态
- 当前状态是否可接受

真正描述语言 token 的，是规则集合。

这种设计比手写一大堆分支更有价值，因为它让词法系统变成了一个“编译器前端里的编译器”：

- 先把正则规则编译成状态表
- 再用状态表去识别源码

### 4.2 `DefaultLexicalDirector` 的价值

`DefaultLexicalDirector` 的意义，不是“又多了一层包装”，而是把一条本来容易混在一起的流程明确拆开：

```text
regex 解析
-> NFA
-> DFA
-> DFA 最小化
-> 状态表
```

这个拆法有两个直接好处：

1. 词法规则的复杂度被集中在构造阶段，而不是运行阶段。
2. 任何一步都可以单独替换或实验，比如不同的 regex parser、不同的 DFA 最小化策略。

所以这个类的真正用途，不是“为了面向对象好看”，而是把词法系统做成可实验的流水线。

### 4.3 运行时扫描器为什么是 DFA 驱动

`StatusTableTokenIterator` 的核心思路是最长匹配。

这意味着：

- 它不会一读到可接受状态就立刻产出 token
- 而是继续向前走，直到再也走不下去
- 然后再回头把刚才那一段切成一个 token

这正是自动机词法分析器和手写 token 分支的根本区别。

更重要的是，扫描器只依赖状态表，不依赖语言概念。  
因此 Program 语言也好，其他实验 token 集也好，本质上都只是在喂不同的状态表。

### 4.4 这个仓库为什么要持久化词法表

因为这里的词法规则不是几条很简单的手工分支，而是经过完整自动机构造的结果。  
构造状态表的代价不低，所以项目选择支持持久化。

这件事的意义不只是“加速”：

- 开发时可以重用旧表
- 调 grammar 或 regex 时可以强制刷新
- 自动机构造和运行时扫描被彻底分离

这说明作者把“构造时成本”和“执行时成本”明确分开看待，而不是把它们糊成一个过程。

## 5. 语法层到底是怎么设计的

### 5.1 文法不是字符串，而是结构

这个仓库里一个非常重要、但容易被忽略的判断是：

文法一旦被真正使用，就不应该只是文本。

所以当前实现不是靠不断解析 `grammar.txt` 来驱动整个系统，而是用 builder API 把文法构造成统一对象。

这样做之后，FIRST/FOLLOW、预测分析表、移进归约表这些算法，面对的就不再是原始文本，而是结构化文法对象。

这会直接提升两件事：

1. 算法实现更稳定，因为不用反复从文本重新解释结构。
2. 语义标签、终结符映射、文法变换都更容易接进去。

### 5.2 为什么同时保留 LL 和 LR

从代码看，这个项目不是只押注一种语法分析技术。

预测分析链路保留着，是因为：

- 它适合实验 FIRST/FOLLOW 和 LL 表
- 它能体现另一种完全不同的语法驱动方式

移进归约链路保留着，是因为：

- Program 这类左递归表达式和更复杂结构更适合这条路线
- 语义动作跟规约点结合得更自然

所以这不是重复实现，而是刻意保留两种编译原理里的不同路线。

### 5.3 `ShiftReducePhaserImpl` 的真正意义

`ShiftReducePhaserImpl` 真正重要的不是“它会跑 LR 表”，而是：

它把“语法执行”和“语义回调”绑成了一个节奏一致的事件系统。

也就是说，语法分析器不是干完自己的事再把结果丢给语义层，  
而是在：

- start
- shift
- reduce
- beforeAccept
- accept
- error

这些关键节点上，持续通知语义层。

这就是为什么这个仓库的语义层能做成“增量构建”，而不是后处理遍历。

### 5.4 `PanicSourceTokenIterator` 说明了什么

它说明作者没有把“语法分析器的输入”简单理解成一个完美 token 流。

在实际工程里，词法阶段可能留下错误，语法阶段仍然要决定怎么面对它们。  
`PanicSourceTokenIterator` 的设计思路是：

- 继续读取
- 跳过出问题的 token
- 把错误写进上下文

这不一定是最强的错误恢复，但它体现了一个重要态度：

语法层并不是假设下游世界一定干净，而是准备好和不完美输入打交道。

## 6. 语义层为什么是这套样子

### 6.1 语义层的核心不是 translator，而是共享上下文

如果只看某几个 translator，很容易误以为语义层只是“给产生式配动作”。  
但从整体实现看，真正的中心其实是共享上下文。

`ShiftReduceSemanticContext` 把很多本来会散落在不同模块的信息集中起来：

- 语法栈相关信息
- 语法树
- 命令构建栈
- 类型绑定
- 常量绑定
- 标识符表
- 函数表
- 结构体表

这种设计最大的好处是：  
不同语义子系统不必彼此直接耦合，只需要通过上下文读写共享事实。

例如：

- 类型系统先把某个节点的类型算出来
- 命令翻译器稍后直接从上下文读取这个类型
- 不需要在命令翻译里再推一遍类型

这让每个模块都更像“做自己该做的事”，而不是互相抄逻辑。

### 6.2 作用域为什么挂在 shift/reduce 上

当前作用域进入和退出，不是靠事后遍历 block 树，而是直接跟语法事件同步。

这个做法很自然，因为：

- 进入 `{` 的那一刻，就是新作用域真正开始的时刻
- 一个 block 规约完成时，就是作用域真正闭合的时刻

这样做的好处是：

- 标识符声明与可见性天然跟解析时机一致
- 参数、局部变量、块作用域可以统一处理
- 后面的类型检查和命令生成可以立刻用到作用域结果

这里还体现出一个细腻的点：  
结构体体和函数体虽然也长得像 block，但它们的语义不是普通语句块。  
所以实现里专门区分了：

- 普通块作用域
- 函数体块
- 结构体体

这说明作者不是按语法形状机械处理，而是在作用域层面区分了不同块的语义。

### 6.3 类型系统为什么要做成节点属性

类型系统不是为了“报个错”这么简单。

在当前实现里，类型至少承担三件事：

1. 验证语言规则
2. 指导隐式转换
3. 指导后续命令生成

如果只存一个“节点最终类型”，很多信息会丢掉。  
例如：

- 结果类型可能是 `boolean`
- 但运算时需要用提升后的 `float64` 指令类型

所以这里做成 `TypeRegister` 这种结构，是合理的。  
它不是多余包装，而是在表达一个现实：  
“节点是什么类型”和“这一步运算该用什么机器语义”不一定是同一件事。

### 6.4 常量系统为什么值得单独存在

常量系统如果只做字面量转值，其实没什么价值。  
当前实现更重要的地方在于：

- 它把常量也当作节点属性
- 它允许后续模块透明消费这些属性

这样一来，常量系统的收益就不只是一点表达式折叠，而是会直接影响：

- 赋值初始化
- 条件分支裁剪
- 返回值处理
- 标识符常量传播

也就是说，这个常量系统不是一个“附带优化”，而是已经参与了语义正确性和命令生成策略。

### 6.5 函数系统为什么不只是函数表

当前函数子系统真正解决的是三个层面的问题：

1. 声明层  
函数名、返回类型、参数列表是否合法。

2. 使用层  
函数调用时，目标是否存在，参数个数和类型是否匹配。

3. 控制流层  
非 `void` 函数是否真的保证返回。

尤其第三点很关键。  
如果函数系统只登记签名，那它只是个符号表。  
而现在它还接入了返回流分析，这说明作者把函数看成“带控制流约束的语义单元”，而不是单纯的名称映射。

### 6.6 结构体系统为什么不只是“支持一个关键字”

很多简化实现里，`struct` 只是语法上接受一下，后面没多少真实语义。

当前实现不是这样。  
结构体一旦声明，就会形成真正的结构体记录，其中包括：

- 名称
- 字段序列
- 字段 offset

这件事的意义是：

- 成员访问不再靠字符串匹配临时处理
- `new struct` 也不只是语法糖
- 结构体已经成为类型系统和命令系统都认识的一类真实类型

更关键的是，字段 offset 是按声明顺序稳定分配的。  
这意味着结构体不是停留在“语言表面支持”，而是已经进入运行表示层。

## 7. 命令生成为什么是当前这种结构

### 7.1 为什么不直接拼字符串

因为直接拼字符串会很快遇到几个问题：

- label 位置还不知道
- `break` / `continue` 目标还不知道
- if/while 嵌套结构还没展开
- 函数体是否该并入当前段还没定

所以这个项目先生成命令节点和命令 register，而不是直接生成文本。

这背后的设计思路很清楚：

先保留“控制流结构”和“未决信息”，最后再拍平成文本。

### 7.2 `CommandBuildCallback` 的作用

它不是简单的“语义动作入口”，而是把两类时机分开处理：

- shift 时只处理 token 级别能立刻知道的东西
- reduce 时才处理结构化语义组合

这个拆分非常重要，因为 token 自己知道的事情很少：

- 一个标识符 token 并不知道自己以后是左值、函数名还是类型名
- 一个 `break` token 也不知道自己该跳到哪里

真正有结构意义的信息，只有在规约时才完整。

所以当前实现没有犯一个常见错误：  
它没有把 token 阶段做得过重。

### 7.3 为什么 translator 不能自己重新做一遍类型推导

命令 translator 最合理的职责，是消费上游已经算好的事实。  
如果 translator 自己再推一遍类型、再找一遍函数、再判断一遍常量，那语义层就会出现重复逻辑和不一致。

当前实现比较正确的地方就在于：

- 类型系统先算类型
- 常量系统先算常量
- 函数系统先登记调用信息
- translator 只在需要时读取这些结果，并据此发命令

这让命令系统更像“结果消费者”，而不是“全能补丁层”。

## 8. Program 语言为什么是当前最完整的一套配置

Program 并不是整个仓库的同义词，但它确实是当前把这套前端框架用得最完整的一套实例。

原因不在于它有多少关键字，而在于它同时覆盖了：

- 词法层的复杂 token 集
- 文法层的完整 grammar0
- 语义标签体系
- 类型解析
- 常量解析
- 结构体
- 函数
- 控制流
- 命令生成
- 测试与报告

也就是说，Program 的价值不是“这门语言本身有多高级”，而是它把仓库里的大部分核心能力都真正串起来用了。

### 8.1 `ProgramStructAwareTokenIterator` 为什么重要

它代表了一个很有意思的设计选择：

结构体类型名歧义没有被简单丢给语法层，也没有拖到语义层才硬判断，  
而是在 token 流阶段做了一次上下文化改写。

这样做的好处是：

- 文法里可以明确区分普通标识符和类型标识符
- 结构体类型支持不会把语法规则搞得很脏

这说明 Program 配置不是“往通用框架里硬塞关键字”，而是在认真地处理语言设计带来的歧义。

### 8.2 `ProgramSyntaxDemo.buildGrammar0()` 的意义

它的意义不是“把 grammar0 翻译成 Java 代码”，而是：

- 给 Program 提供一份结构化、可参与算法构造、可挂语义标签的文法对象

这里最关键的不是产生式数量，而是：

- 顶层支持结构体、函数和普通条目
- 语句层显式处理 dangling-else
- 表达式层次清晰
- `new`、成员访问、函数调用、数组访问都已经进入统一语法系统

这说明 grammar0 早就不是最初那个只覆盖基础语句的小实验文法了。

## 9. 测试和报告层为什么不是可有可无

`ProgramSyntaxTestRunner` 的价值，不是因为它“能跑测试”，而是因为它把这套系统的输出做成了可检查、可复盘的报告。

当前报告不只是告诉你 PASS/FAIL，而是尽量把真正有诊断价值的结果写出来：

- 源代码
- 结构体表
- 入口段命令
- 函数段命令
- 局部变量表
- 错误列表
- 异常
- 对部分实验用例补充词法/语法阶段输出

这对一个编译前端实验项目非常重要。  
因为很多 bug 不是“挂了”，而是：

- 绑定错了
- offset 错了
- 函数段混进入口段了
- 条件裁剪不对
- 参数顺序反了

没有这种报告，很多问题只能靠猜。

## 10. 这份说明真正想帮助读者理解什么

如果只看文件目录，你能知道：

- 有哪些类
- 有哪些包

但你不会知道：

- 为什么词法规则要先编译成状态表
- 为什么文法要先变成对象
- 为什么语义层要跟 shift/reduce 同步
- 为什么命令生成不能直接拼字符串
- 为什么函数、结构体、类型、常量都要做成节点属性或上下文事实

这些才是这份文档该讲的东西。

所以理解这个仓库，最重要的不是记住有哪些类，而是记住下面这几句话：

1. 这不是一个围绕单个入口类展开的程序，而是一组前端能力和它们的装配实例。
2. 这里所有重要能力都在努力把“规则描述”和“执行算法”分开。
3. 语义阶段的核心不是后处理遍历，而是与 shift/reduce 同步的增量构建。
4. 结果层刻意保留结构，避免过早线性化。
5. Program 是当前最完整的一套语言配置，但不是整个仓库的全部。

## 11. 最后的总结

这个项目真正值得看的地方，不是它“支持了多少语法点”，而是它把编译前端里几件常见但容易互相缠死的事情拆开了：

- 词法规则和词法执行拆开
- 文法描述和语法算法拆开
- 语法驱动和语义构建同步起来
- 语义事实和命令输出分层
- 通用框架和具体语言实例分开

因此，这个仓库更像一套“可以实验的编译前端骨架”，而不是一个只为某个 Demo 写死流程的小项目。  
Program 语言之所以重要，不是因为它是唯一入口，而是因为它把这套骨架的大部分关键能力都真正用起来了。
