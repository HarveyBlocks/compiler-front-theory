# 三地址码与中间代码机制设计详解

本文面向“实验项目三：语法制导翻译与生成中间代码实验”，专门说明本项目中三地址码及其相关机制的设计与实现。重点不是贴代码，而是把编译器怎样从语法归约一步步得到中间代码、每一层为什么这样设计、各模块之间如何配合讲清楚。

本文对应的核心源码主要集中在：

- `src/main/java/org/harvey/vie/theory/semantic/command`
- `src/main/java/org/harvey/vie/theory/semantic/type`
- `src/main/java/org/harvey/vie/theory/semantic/value`
- `src/main/java/org/harvey/vie/theory/semantic/function`
- `src/main/java/org/harvey/vie/theory/semantic/structure`
- `src/main/java/org/harvey/vie/theory/semantic/array`
- `src/test/java/org/harvey/vie/theory/AppTest.java`

## 0. 先按这条源码路线读

如果目标是看懂“代码到底怎么运作”，建议不要从某个 translator 随机点进去，而是按下面这条运行主线读。项目的三地址码不是一个孤立模块，它是在 LR 语法分析推进过程中一点点被构造出来的。

### 0.1 程序入口：测试如何启动整条链路

测试入口在 `AppTest`。它会调用 `ProgramSyntaxTestRunner.run()` 跑 `src/main/resources/program-tests` 下的用例。真正执行单个程序文本的是：

```text
ProgramSyntaxTestRunner.executeSemanticTest(...)
```

这里做了几件事：

1. 创建词法分析器 `ProgramLexicalDemo.lexicalAnalyzer()`。
2. 构造 LR 分析表 `SyntaxDemo.buildShiftReduceParsingTable(...)`。
3. 创建 `ShiftReducePhaserImpl`。
4. 传入语义回调注册表 `SemanticDemo.buildShiftReduceTestRegister()`。
5. 传入命令工厂 `SyntaxDemo.STRING_COMMAND_FACTORY`。
6. 调用 `phaser.phase(iterator, errorContext)`，开始语法分析和语义翻译。

所以，如果读者想从“程序怎么跑起来”开始看，第一站是：

```text
AppTest
  -> ProgramSyntaxTestRunner.run()
  -> ProgramSyntaxTestRunner.executeSemanticTest()
  -> ShiftReducePhaserImpl.phase()
```

### 0.2 `ShiftReducePhaserImpl.phase`：驱动所有语义动作的主循环

`ShiftReducePhaserImpl.phase(...)` 是运行时最核心的循环。它每次读取当前 token 和状态栈栈顶，然后查 LR 分析表：

```text
当前状态 top + 当前 token
  -> 查 ACTION 表
  -> shift / reduce / accept / error
```

如果 ACTION 是 shift：

```text
ShiftReducePhaserImpl.onShift(...)
  -> context.onShift(nextStatus, token)
```

如果 ACTION 是 reduce：

```text
ShiftReducePhaserImpl.onReduce(...)
  -> context.onReduce(production)
```

如果是 accept：

```text
context.beforeAccept(production)
context.onAccept(production)
```

也就是说，语法分析器本身不直接生成三地址码。它只不断发出“我 shift 了一个 token”“我 reduce 了一个产生式”“我要 accept 了”这些事件。真正的命令生成，是这些事件被语义回调接收到之后发生的。

### 0.3 `ShiftReduceSemanticContext`：事件如何传给每个回调

`ShiftReduceSemanticContext` 里保存了一个回调迭代器 `callbackIter`。当外部调用：

```text
context.onShift(...)
context.onReduce(...)
context.beforeAccept(...)
```

它不会只通知一个模块，而是按 `SemanticDemo.buildShiftReduceTestRegister()` 里注册的顺序，一个一个调用回调。测试模式下的关键顺序是：

```text
TreeBuildCallback
IdentifierScopeCallback
TypeBuildCallback
ConstantValueBuildCallback
StructSemanticCallback
FunctionSemanticCallback
IdentifierTableBuildCallback
SemanticResultCallback
CommandBuildCallback
IdentifierConstantStateCallback
PassiveErrorCallback
```

这个顺序解释了为什么命令生成器能读到类型、常量、结构体、函数和标识符信息：这些信息由前面的回调在同一个 reduce 事件中先准备好，然后 `CommandBuildCallback` 再使用。

这里有一个容易误解的点：`SemanticResultCallback` 在注册顺序上排在 `CommandBuildCallback` 前面，但它真正构造最终结果是在 `beforeAccept`。由于 `beforeAccept` 对 accept 产生式有特殊处理，命令栈顶部已经包含可用于收集的归约结果，测试也验证了最终结果能正确拿到 entry commands 和 function segments。

### 0.4 `CommandBuildCallback`：命令生成真正开始的位置

命令生成入口是：

```text
CommandBuildCallback
```

它继承：

```text
BuildStackContextCallback<CommandNodeRegister>
```

可以把它理解成“命令属性栈维护器”。它做的事情非常机械，但很关键：

```text
onShift(token):
  tokenTranslator.translate(context, token)
  得到 CommandNodeRegister
  压入 context.getCommandContext()

onReduce(production):
  按产生式右部长度弹出若干 CommandNodeRegister
  reduceTranslator.translate(context, production, children)
  得到新的 CommandNodeRegister
  压回 context.getCommandContext()
```

所以命令生成和语法归约是一一同步的。语法栈 reduce 出一个表达式，命令栈也 reduce 出这个表达式的命令子树。

### 0.5 `TagStrategyCompose.stringCommand`：一个产生式该找哪个 translator

`CommandBuildCallback` 自己不写任何语义规则。它只负责调度。具体某个产生式该用哪个 translator，由：

```text
TagStrategyCompose.stringCommand()
```

决定。

例如：

```text
ProgramSemanticTag.ASSIGNMENT
  -> AssignStatementTranslator

ProgramSemanticTag.ACCESS
  -> ArrayAtExpressionTranslator

ProgramSemanticTag.MEMBER_ACCESS
  -> MemberAccessTranslator

ProgramSemanticTag.CONDITIONAL
  -> IfStatementTranslator

ProgramSemanticTag.LOOP + DO_LOOP
  -> DoWhileStatementTranslator
```

因此看代码时要记住：不是 `CommandBuildCallback` 直接写 if/while/assignment 的生成逻辑，而是它通过语义标签找到对应 translator。

### 0.6 一条命令如何从 translator 变成最终文本

以赋值 translator 中的一条命令为例：

```text
context.getCommandFactory().assignFromStTopToAddr(...)
```

它的调用链是：

```text
AssignStatementTranslator
  -> ShiftReduceSemanticContext.getCommandFactory()
  -> DefaultCommandFactory.assignFromStTopToAddr(...)
  -> TypedStringCommandFactory.assignFromStTopToAddr(...)
  -> new StringCommand("assign_from_st_top_to_addr_int32")
```

translator 得到 `SemanticCommand` 后，不会直接写入最终列表，而是包装成：

```text
new TerminalNode(command)
```

再放入：

```text
CommandNodeListBuilder
```

最后返回：

```text
NormalCommandNodeRegister
```

到 accept 前，`SemanticResultCallback` 才会调用：

```text
CommandSegmentSupport.flatten(topRegister)
```

把 register 里的命令树拍平成 `List<SemanticCommand>`。最后 `ThreeAddressCodePrinter.print(...)` 调每条命令的 `toString()`，才得到报告里看到的文本。

完整链路可以写成：

```text
translator 语义动作
  -> CommandFactory 创建 SemanticCommand
  -> TerminalNode 包装命令
  -> CommandNodeRegister 挂到命令属性栈
  -> CommandSegmentSupport.flatten 扁平化
  -> ThreeAddressCodePrinter.print 输出字符串
```

### 0.7 跳转命令为什么不能创建时就知道目标

普通命令创建时文本已经确定，例如：

```text
st_plus_int32
return
call 0
```

但跳转命令不一样。生成：

```text
ifn_goto ifEnd
```

时，`ifEnd` 还不知道是第几条指令。项目把这个问题拆成两个对象：

```text
DefaultSemanticLabel
LabelNode
```

translator 创建 label，然后把 label 交给跳转命令：

```text
context.getCommandFactory().ifnGoto(ifEndLabel)
```

`TypedStringCommandFactory.ifnGoto(...)` 返回的不是固定字符串，而是：

```text
StringSupplierCommand(() -> "ifn_goto " + label.getIndex())
```

等 flatten 走到 `LabelNode` 时：

```text
label.setIndex(result.size())
```

label 的编号才真正确定。之后跳转命令 `toString()` 时读到的就是最终编号。

所以“回填”没有发生在字符串层，而是发生在 label 对象的 index 字段上。

### 0.8 中间代码生成的完整步骤

本项目的“中间代码生成”不是最后简单打印三地址码，而是一个贯穿语法分析全过程的构造流程。它从源码 token 开始，经过语法节点、语义属性、命令 register、命令树、函数命令段，最后才变成报告中的三地址码文本。下面按真实代码执行顺序展开。

#### 第 1 步：创建语义上下文

入口：

```text
ProgramSyntaxTestRunner.executeSemanticTest(...)
  -> new ShiftReducePhaserImpl(...)
  -> ShiftReducePhaserImpl.phase(...)
```

`ShiftReducePhaserImpl.phase(...)` 会创建：

```text
ShiftReduceSemanticContext context = new ShiftReduceSemanticContext(
    register,
    syntaxContext,
    commandFactory,
    typeResolver,
    constantResolver,
    functionManager
)
```

这一步的输入是：

- LR 分析表。
- token iterator。
- 语义回调注册表。
- 命令工厂。
- 类型解析器。
- 常量解析器。
- 函数管理器。

这一步的输出是 `ShiftReduceSemanticContext`。后续所有模块都通过它共享数据，包括：

- `treeContext`：语法树节点栈。
- `commandContext`：命令 register 栈。
- `typeContext`：语法节点到类型属性的映射。
- `constantValueContext`：语法节点到常量值的映射。
- `identifierTableBuilder` 和 `identifierRecords`：标识符表。
- `structContext`：结构体表。
- `functionContext`：函数表。
- `functionCommandSegmentContext`：函数中间代码段。
- `commandFactory`：命令对象创建入口。

所以中间代码生成从一开始就不是一个独立列表，而是依赖这个上下文里的多套语义信息。

#### 第 2 步：语法分析主循环产生 shift/reduce 事件

入口：

```text
ShiftReducePhaserImpl.phase(...)
```

主循环每次做：

```text
current = ctx.currentToken()
top = ctx.peek()
element = table.activeNext(top, table.matchTerminal(current))
```

然后根据 `element` 类型分支：

```text
shift  -> context.onShift(nextStatus, token)
reduce -> context.onReduce(production)
accept -> context.beforeAccept(production) + context.onAccept(production)
error  -> context.onError(...)
```

中间代码生成不会主动遍历源码，而是被这些事件驱动。语法分析器每读进一个 token，命令系统就有机会生成 token 级 register；语法分析器每归约一个产生式，命令系统就有机会把子 register 合成父 register。

#### 第 3 步：回调链按顺序处理同一个事件

入口：

```text
ShiftReduceSemanticContext.onShift(...)
ShiftReduceSemanticContext.onReduce(...)
ShiftReduceSemanticContext.beforeAccept(...)
```

`ShiftReduceSemanticContext` 的 `invokeNext(...)` 会把事件依次传给注册表中的回调。测试模式下，回调顺序来自：

```text
SemanticDemo.buildShiftReduceTestRegister()
```

顺序是：

```text
TreeBuildCallback
IdentifierScopeCallback
TypeBuildCallback
ConstantValueBuildCallback
StructSemanticCallback
FunctionSemanticCallback
IdentifierTableBuildCallback
SemanticResultCallback
CommandBuildCallback
IdentifierConstantStateCallback
PassiveErrorCallback
```

中间代码生成依赖这个顺序。对于同一次 reduce：

1. `TreeBuildCallback` 先把产生式归约成 `HeadNode`。
2. `TypeBuildCallback` 给这个 `HeadNode` 绑定 `TypeRegister`。
3. `ConstantValueBuildCallback` 尝试给这个 `HeadNode` 绑定 `ConstantValue`。
4. 结构体、函数、标识符模块更新对应表。
5. `CommandBuildCallback` 最后读取这些属性，生成命令 register。

如果没有前面的类型和符号信息，命令生成就无法知道：

- `a` 是 `int32` 还是 `ref`。
- `arr[i]` 的元素类型是什么。
- `student.age` 的字段 offset 是多少。
- `foo()` 是函数表第几个函数。
- `1 + 2 * 3` 能不能直接折叠成常量。

#### 第 4 步：语法树节点同步构造

相关类：

```text
TreeBuildCallback
BuildStackContextCallback<ShiftReduceSyntaxTreeNode>
TreeContext
TokenNode
HeadNode
```

`TreeBuildCallback` 和命令生成类似，也使用 `BuildStackContextCallback`。它维护的是语法树节点栈：

```text
shift token:
  new TokenNode(token)
  push treeContext

reduce production:
  pop k 个 ShiftReduceSyntaxTreeNode
  new HeadNode(production.getHead(), production, children)
  push treeContext
```

这一步对中间代码生成非常重要，因为后面的 translator 经常需要读取“当前刚归约出来的语法树头节点”：

```text
context.getTreeContext().peek().toHead()
```

例如：

- `IdentifierUseTranslator` 从当前 `HeadNode` 找标识符 token。
- `DeclarationWithInitializationTranslator` 从当前 `HeadNode` 找声明变量 token。
- `FunctionCallTranslator` 从当前 `HeadNode` 找函数名 token。
- `NewArrayTranslator` 从当前 `HeadNode` 找数组维度节点。
- `MemberAccessTranslator` 从当前 `HeadNode` 找字段名 token。

所以，命令生成不是直接从 token 字符串猜结构，而是依赖语法树节点定位上下文。

#### 第 5 步：类型属性生成

相关类：

```text
TypeBuildCallback
TypeContext
TypeRegister
TypeAttributes
SemanticType
LocationKind
TypeConversionRule
```

`TypeBuildCallback` 在 reduce 时根据 `ProgramSemanticTag` 选择类型规则。它把结果绑定到当前 `HeadNode`：

```text
context.bindType(head, typeRegister)
```

`TypeContext` 内部是：

```text
IdentityHashMap<ShiftReduceSyntaxTreeNode, TypeRegister>
```

也就是说，类型属性不是按字符串名保存，而是绑定到具体语法树节点对象。

`TypeRegister` 保存四类信息：

- `type`：源码语义类型，例如 `int32`、`boolean`、`struct Student`、`int32[]`。
- `instructionType`：真正执行运算时使用的类型，例如关系表达式结果是 boolean，但比较指令可能用 float64。
- `anchorToken`：错误定位用 token。
- `locationKind`：如果它是左值，记录是 `ADDRESS` 还是 `REFERENCE`。

命令生成器通过 `TypeAttributes` 读取这些信息：

```text
TypeAttributes.childType(context, 0)
TypeAttributes.child(context, 0).getLocationKind()
TypeAttributes.childAnchor(context, 1)
```

因此，中间代码生成中的每条带类型命令，例如：

```text
st_plus_int32
assign_from_st_top_to_ref_boolean
bias_from_st_top_to_ref_ref
```

都不是 translator 临时猜出来的，而是来自 `TypeBuildCallback` 预先绑定的类型属性。

#### 第 6 步：常量属性生成

相关类：

```text
ConstantValueBuildCallback
ConstantValueContext
ConstantValue
ConstantAttributes
ConstantCommandSupport
ConstantConditionSupport
IdentifierConstantStateCallback
```

`ConstantValueBuildCallback` 在 reduce 时尝试计算当前语法节点是否是编译期常量。若是，就执行：

```text
context.bindConstantValue(head, value)
```

`ConstantValueContext` 内部同样用：

```text
IdentityHashMap<ShiftReduceSyntaxTreeNode, ConstantValue>
```

常量值绑定在具体语法节点上。

命令生成中有两个重要读取点：

1. 表达式命令生成前：

```text
ConstantCommandSupport.constantOrNull(context, production, children)
```

如果当前表达式已有常量值，就直接生成：

```text
load_st_<type>_static <value>
```

而不再生成左右操作数和运算命令。

2. 控制流命令生成前：

```text
ConstantConditionSupport.booleanValue(context, childIndex)
```

如果 `if/while/do-while` 的条件是编译期 boolean，就可以剪枝：

- `if(true)` 保留 then。
- `if(false)` 删除 then 命令。
- `while(false)` 删除循环。
- `do-while(false)` 保留一次循环体但删除回边。

`IdentifierConstantStateCallback` 则负责在普通赋值后清除简单标识符的常量状态，避免后续错误传播旧值。

#### 第 7 步：符号表、结构体表、函数表准备

中间代码必须知道变量 offset、结构体字段 offset、函数 table index。这些不是命令模块自己计算的，而是前面的语义回调准备。

标识符表：

```text
IdentifierTableBuildCallback
  -> context.registerIdentifier(...)
  -> IdentifierRecord(no, offset, type, declaredType, lexeme, initialized, ownerFunction, constantValue)
```

命令生成读取它：

```text
IdentifierUseTranslator
DeclarationWithInitializationTranslator
TypedStringCommandFactory.loadIdentifierAddress
```

结构体表：

```text
StructSemanticCallback
  -> collectFields(...)
  -> new StructRecord(tableIndex, nameToken, fields, declarationNode)
  -> StructField(nameToken, type, offset)
```

命令生成读取它：

```text
NewStructTranslator
MemberAccessTranslator
TypedStringCommandFactory.newStruct
biasFromStTopToRef(fieldType, offset)
```

函数表：

```text
FunctionSemanticCallback
  -> new FunctionRecord(tableIndex, signature, parameters, head)
  -> context.registerFunction(...)
```

命令生成读取它：

```text
FunctionCallTranslator
FunctionDefinitionTranslator
SimpleStringCommandFactory.callFunction
```

因此，中间代码生成的输入不是单纯语法树，而是“语法树 + 类型属性 + 常量属性 + 标识符表 + 结构体表 + 函数表”。

#### 第 8 步：命令属性栈同步构造

相关类：

```text
CommandBuildCallback
BuildStackContextCallback<CommandNodeRegister>
CommandContext
TokenTranslatorStrategy
CommandTranslatorStrategy
```

`CommandBuildCallback` 与 `TreeBuildCallback` 的结构完全平行，只是它维护的不是语法树节点，而是命令 register。

shift 时：

```text
TokenTranslator tokenTranslator = shiftStrategies.get(token.getType())
CommandNodeRegister register = tokenTranslator.translate(context, token)
context.getCommandContext().push(register)
```

reduce 时：

```text
children = pop production body length from commandContext
CommandTranslator translator = reduceStrategies.get(production)
CommandNodeRegister result = translator.translate(context, production, children)
context.getCommandContext().push(result)
```

这里的 `children` 与产生式右部一一对应。比如赋值产生式右部大致包含：

```text
loc '=' bool ';'
```

那么 `AssignStatementTranslator` 中的：

```text
children[0]
children[2]
```

就分别对应左值和右值表达式。

#### 第 9 步：token 级命令生成

相关类：

```text
SimpleStringTokenTranslator
LoadIdentifierAddressTokenTranslator
TypeTokenTranslator
BreakTokenTranslator
ContinueTokenTranslator
DoNothingTokenTranslator
```

token 级翻译只处理单个 token 就能确定的动作：

- 字面量 token 可以生成静态加载命令。
- 类型 token 不产生命令。
- 标识符 token 当前先占位，等归约为“标识符使用”后再处理。
- `break/continue` 可以生成未决 goto。
- 分号、括号、逗号等语法符号不产生命令。

典型输入输出：

```text
token: CONSTANT_INTEGER("1")
  -> SimpleStringTokenTranslator
  -> TokenCommandRegister(StringCommand("load_st_int32_static 1"))

token: CONTROL_STRUCTURES_BREAK("break")
  -> BreakTokenTranslator
  -> StringUncertainLabelGotoCommand(label=null)
  -> TokenCommandRegister(command, uncertainBreaks=[command])

token: IDENTIFIER("a")
  -> LoadIdentifierAddressTokenTranslator
  -> PlaceholderNodeRegister
```

这里解释了为什么标识符 token 不是一出现就生成地址命令：它可能是声明名、函数名、类型名或变量使用名，必须等归约标签明确后再处理。

#### 第 10 步：产生式级命令生成

相关类：

```text
TagStrategyCompose
ProductionTagStrategy<CommandTranslator>
各种 CommandTranslator
```

产生式级翻译负责真正的语义结构：

- 赋值。
- 声明初始化。
- 表达式运算。
- 左值取值。
- 数组访问。
- 结构体字段访问。
- if / if-else。
- while / do-while。
- 函数调用。
- 函数定义。
- return。
- 程序顶层非法控制流检查。

每个 translator 的基本模式是：

```text
读取当前 HeadNode 或 children register
读取 TypeAttributes / ConstantAttributes / 符号表
做语义校验
创建 CommandNodeListBuilder
按语义顺序 children[i].register(builder)
必要时插入额外 TerminalNode
返回 NormalCommandNodeRegister / MergedCommandNodeRegister / PlaceholderNodeRegister
```

例如赋值：

```text
AssignStatementTranslator:
  targetType = TypeAttributes.childType(context, 0)
  sourceType = TypeAttributes.childType(context, 2)
  requireAssignable(sourceType, targetType)
  children[0].register(builder)
  children[2].register(builder)
  optional cast
  append assign_to_addr/ref
  return NormalCommandNodeRegister
```

这就是“语法制导翻译”的核心：每个产生式根据自己的孩子属性和当前语义属性，生成当前语法结构对应的中间代码片段。

#### 第 11 步：命令对象由工厂统一创建

相关类：

```text
CommandFactory
DefaultCommandFactory
TypedCommandFactory
SimpleCommandFactory
TypedStringCommandFactory
SimpleStringCommandFactory
StringCommand
StringSupplierCommand
StringUncertainLabelGotoCommand
```

translator 不直接拼接最终命令文本，而是调用：

```text
context.getCommandFactory()
```

工厂分层如下：

```text
CommandFactory
  -> DefaultCommandFactory
       -> TypedCommandFactory / TypedStringCommandFactory
       -> SimpleCommandFactory / SimpleStringCommandFactory
```

带类型的命令由 `TypedStringCommandFactory` 创建，例如：

```text
load_st_int32_address 0
st_plus_int32
assign_from_st_top_to_ref_boolean
new_array_ref 1 1
ifn_goto <labelIndex>
```

简单命令由 `SimpleStringCommandFactory` 创建，例如：

```text
call 0
return
```

这个步骤的输出是 `SemanticCommand` 对象，而不是普通字符串。后续它会被包进 `TerminalNode`。

#### 第 12 步：命令树构造

相关类：

```text
CommandNode
TerminalNode
LabelNode
HeadNode
CommandNodeBuilder
CommandNodeListBuilder
CommandNodeRegister
NormalCommandNodeRegister
TokenCommandRegister
MergedCommandNodeRegister
PlaceholderNodeRegister
```

命令生成的中间产物是“命令树”，不是平铺列表。

节点含义：

- `TerminalNode`：一条真实命令。
- `LabelNode`：一个位置标记，不输出命令。
- `HeadNode`：多个命令节点的组合。

register 含义：

- `TokenCommandRegister`：token 级命令包。
- `NormalCommandNodeRegister`：普通产生式命令包。
- `MergedCommandNodeRegister`：输出 primary 命令，但合并 extras 的未决控制流。
- `PlaceholderNodeRegister`：空命令包。

为什么不直接输出列表？因为：

1. label 编号要等所有前置命令数量确定后才能知道。
2. 常量条件可能删除某个分支。
3. 函数定义要单独收集，不混进入口段。
4. `break/continue` 要延迟绑定到循环。

#### 第 13 步：未决跳转和 label 回填

相关类：

```text
SemanticLabel
DefaultSemanticLabel
LabelNode
StringSupplierCommand
UncertainLabelGotoCommand
StringUncertainLabelGotoCommand
WhileStatementTranslator.bindLoopLabels
ProgramCommandTranslator
```

有两类延迟：

第一类是普通 label 延迟。比如 `ifn_goto ifEnd` 创建时还不知道 `ifEnd` 是第几条指令，所以：

```text
TypedStringCommandFactory.ifnGoto(label)
  -> StringSupplierCommand(() -> "ifn_goto " + label.getIndex())
```

等 `LabelNode.flat(result)` 执行时：

```text
label.setIndex(result.size())
```

跳转命令打印时就能读到最终 index。

第二类是 `break/continue` 目标延迟。它们 token 阶段就生成：

```text
StringUncertainLabelGotoCommand(label=null)
```

循环归约时：

```text
WhileStatementTranslator.bindLoopLabels(body, continueLabel, breakLabel)
```

把未解析的 goto 绑定到当前循环 label。顶层程序归约时：

```text
ProgramCommandTranslator.rejectUnresolved(...)
```

检查是否还有没绑定的 `break/continue`，如果有就报错。

#### 第 14 步：函数命令段生成

相关类：

```text
FunctionDefinitionTranslator
FunctionCommandSegment
FunctionCommandSegmentContext
CommandSegmentSupport
SemanticAnalysisResult
```

函数定义不是入口段执行语句，因此不能把函数体命令直接输出到全局命令列表。

当归约到函数定义时：

```text
FunctionDefinitionTranslator.translate(...)
```

它会：

```text
commands = CommandSegmentSupport.flatten(children[1])
segment = new FunctionCommandSegment(function, commands)
context.registerFunctionCommandSegment(segment)
return new PlaceholderNodeRegister()
```

这一步的结果是：

- 函数体命令进入 `FunctionCommandSegmentContext`。
- 函数定义本身在当前命令流中表现为空。

所以最终结果里有：

```text
entryCommands
functionSegments
```

两个不同区域。

#### 第 15 步：accept 前收集中间代码结果

相关类：

```text
SemanticResultCallback
CommandSegmentSupport
SemanticAnalysisResult
```

当语法分析走到 accept，`SemanticResultCallback.beforeAccept(...)` 会构造最终语义结果：

```text
CommandNodeRegister top = commandContext.peek()
List<SemanticCommand> entryCommands = CommandSegmentSupport.flatten(top)
List<FunctionCommandSegment> functionSegments = context.getFunctionCommandSegmentContext().snapshot()
List<StructRecord> structTable = context.structRecords()
IdentifierRecord[] identifierRecords = context.identifierRecords()
new SemanticAnalysisResult(entryCommands, functionSegments, structTable, identifierRecords)
```

这一步完成的不是“打印”，而是“生成完整中间表示结果对象”。该对象包含：

- 入口中间代码。
- 函数中间代码段。
- 结构体布局表。
- 标识符表。

#### 第 16 步：中间代码打印和测试报告

相关类：

```text
ThreeAddressCodePrinter
ProgramSyntaxTestRunner.writeReport
SemanticDisplaySupport
```

`ThreeAddressCodePrinter.print(...)` 很简单：

```text
for command in commands:
  lines.add(command.toString())
```

真正组织报告的是 `ProgramSyntaxTestRunner.writeReport(...)`。它把 `SemanticAnalysisResult` 拆成：

- Struct Table。
- Global Segment Commands。
- Global Local Variables。
- Function Segment Commands。
- Function Local Variables。
- Errors。

因此，报告中看到的三地址码文本只是中间代码生成流程的最后一层展示。其背后完整对象链是：

```text
SourceToken
  -> ShiftReduceSyntaxTreeNode
  -> TypeRegister / ConstantValue / IdentifierRecord / StructRecord / FunctionRecord
  -> CommandNodeRegister
  -> CommandNode tree
  -> SemanticCommand list
  -> SemanticAnalysisResult
  -> ThreeAddressCodePrinter lines
  -> markdown report
```

## 1. 总体设计结论

项目的中间代码不是传统教材里完全显式的 `t1 = a + b` 形式，而是一套“栈式三地址风格”的文本命令。它仍然表达三地址码的核心含义：每条命令完成一个很小的中间动作，变量、常量、运算、跳转、函数调用、数组偏移和结构体字段定位都被拆成可顺序执行的简单指令。区别在于临时变量没有显式命名为 `t1/t2/t3`，而是隐含在语义栈中。

例如一个普通赋值：

```text
a = b + 1;
```

会被组织成类似：

```text
load_st_int32_address <a_offset>
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
assign_from_st_top_to_addr_int32
```

这里的设计含义是：

1. 先把左值 `a` 的地址压入栈中，保留写回目标。
2. 再计算右侧表达式 `b + 1`，把结果放到栈顶。
3. 最后一条赋值命令根据“栈顶是源值，前面保留的是目标地址”完成写回。

这种设计避免了显式生成临时变量表，也让表达式翻译、数组访问、结构体访问、函数调用都可以统一成“先把参与计算的东西按顺序压入栈，再发出一条具体动作命令”的模式。

## 2. 端到端链路

三地址码生成不是单独发生的，而是嵌入在语法分析的 shift/reduce 流程里。整体链路如下：

1. 词法分析器把源码切成 `SourceToken`。
2. LR 语法分析器不断触发 `onShift`、`onReduce`、`beforeAccept` 等事件。
3. 多个语义回调共享同一套 shift/reduce 事件：
   - `TreeBuildCallback` 建语法树。
   - `IdentifierScopeCallback` 管理作用域进出。
   - `TypeBuildCallback` 为语法节点绑定类型属性。
   - `ConstantValueBuildCallback` 为可折叠表达式绑定编译期常量。
   - `StructSemanticCallback` 建结构体表。
   - `FunctionSemanticCallback` 建函数表并检查调用、返回。
   - `IdentifierTableBuildCallback` 建标识符表。
   - `CommandBuildCallback` 构造中间代码命令树。
   - `IdentifierConstantStateCallback` 维护标识符常量状态。
   - `PassiveErrorCallback` 收集错误状态。
4. `CommandBuildCallback` 并不直接输出最终字符串列表，而是构造 `CommandNodeRegister`。
5. `SemanticResultCallback` 在接收前收拢结果，把命令树扁平化为 `List<SemanticCommand>`，同时收集函数命令段、结构体表、标识符表。
6. `ThreeAddressCodePrinter` 最后调用每条 `SemanticCommand.toString()` 输出可读文本。

这条链路最关键的设计点是：命令生成依赖前面几个语义属性回调已经准备好的类型、常量、符号、函数和结构体信息。也就是说，命令翻译器本身不重新查整棵语法树推断语义，而是读取语义上下文中已经绑定好的属性。

## 3. 为什么采用“栈式三地址风格”

传统三地址码常见形式是：

```text
t1 = b + 1
a = t1
```

本项目采用：

```text
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
```

区别在于：

- 传统形式显式给中间结果命名，例如 `t1`。
- 项目形式把中间结果保存在语义栈上，下一条命令默认使用栈顶或栈顶若干元素。

这样设计有几个实际收益：

1. 表达式翻译非常自然。先翻译左操作数，再翻译右操作数，最后追加运算命令。
2. 不需要额外维护临时变量编号、临时变量生命周期和临时变量类型表。
3. 数组、结构体和普通变量可以统一成“定位命令 + 取值命令或写回命令”。
4. 命令文本仍然足够接近三地址码，每条命令都只表达一个小操作，便于测试和报告展示。

项目中命令名前缀里的 `st` 可以理解为 stack。比如 `load_st_int32_static 1` 表示把一个 `int32` 静态值加载到栈中，`st_plus_int32` 表示对栈中两个 `int32` 值做加法。

## 4. 命令抽象层

### 4.1 `SemanticCommand`

所有中间代码命令都实现 `SemanticCommand`。它本身是一个 marker interface，不规定命令内部必须是字符串、对象码还是其他结构。当前 demo 实现使用字符串命令，但上层翻译器只依赖接口。

这个抽象给项目留下了扩展空间：以后如果要从文本三地址码切换到真正可执行的 IR 对象，只需要替换命令实现和工厂，不必重写所有语法制导翻译器。

### 4.2 字符串命令实现

当前实现有三类字符串命令：

- `StringCommand`：保存固定文本，例如 `return`、`new_struct 0`。
- `StringSupplierCommand`：通过 `Supplier<String>` 延迟生成文本，主要服务于标签跳转。
- `StringUncertainLabelGotoCommand`：表示 `break/continue` 产生的未决跳转，目标 label 之后再绑定。

这里的设计非常关键：跳转目标不是在命令创建时直接写死字符串，而是在最终打印时读取 label 的下标。这避免了传统回填中常见的“先输出 `goto ?`，后面再修改字符串”的做法。

### 4.3 `CommandFactory`

命令不由 translator 手写字符串，而是统一经过 `CommandFactory` 创建。接口中覆盖了所有中间代码动作：

- 字面量、常量和标识符地址加载。
- 结构体和数组创建。
- 算术、关系、相等、逻辑、一元运算。
- 地址取值、引用取值。
- 赋值写回。
- 数组或结构体偏移。
- 类型转换。
- 条件跳转、无条件跳转、未决跳转。
- 函数调用和返回。

这种工厂设计让 translator 只描述“要做什么语义动作”，而不关心命令文本长什么样。比如赋值翻译器只调用 `assignFromStTopToAddr(type)` 或 `assignFromStTopToRef(type)`，具体文本由 `TypedStringCommandFactory` 生成。

### 4.4 Typed 与 Simple 的拆分

命令工厂被拆成两部分：

- `TypedCommandFactory`：处理带数据类型的命令，例如 `load_st_int32_static`、`st_plus_float64`。
- `SimpleCommandFactory`：处理不依赖操作数类型的命令，例如 `call 0`、`return`。
- `DefaultCommandFactory`：把二者组合成完整 `CommandFactory`。

这个拆分反映了命令系统的真实差异：多数表达式、赋值、访问命令必须知道数据类别；而函数调用和返回只需要函数编号或固定动作。

## 5. 命令数据类型设计

### 5.1 `SemanticType` 与 `CommandDataType` 的区别

项目中有两套类型概念：

- `SemanticType` 是源语言层面的类型，如 `int32`、`float64`、`boolean`、`struct Student`、`int32[][]`。
- `CommandDataType` 是命令编码层面的数据类别，如 `int32`、`float64`、`boolean`、`ref`。

二者不是一一对应。最重要的规则是：结构体和数组在命令层统一编码为 `REF`。

例如：

- `int32` 存储类别是 `INT32`。
- `float64` 存储类别是 `FLOAT64`。
- `struct Student` 存储类别是 `REF`。
- `int32[]` 存储类别也是 `REF`。

这样命令层不需要知道“这是学生结构体引用”还是“整数数组引用”，只要知道它是一个引用值。具体结构体字段、数组元素类型仍然由语义类型系统保存。

### 5.2 `forStorage` 与 `forValue`

`CommandDataType` 提供两个入口：

- `forStorage(SemanticType type)`：用于变量槽位、数组元素、结构体字段的存储类别。引用类型会折叠成 `REF`。
- `forValue(SemanticType type)`：用于真正参与标量运算的值类别。引用类型不能被当成普通标量参与运算。

这个区分很细，但很重要。它避免把“引用值的存储类别”和“可做算术运算的标量类别”混在一起。

例如：

- 给结构体变量赋值时，需要 `assign_from_st_top_to_addr_ref`，这是存储层面的 `REF`。
- 对 `int32 + float64` 做运算时，需要先把 `int32` cast 到 `float64`，再生成 `st_plus_float64`，这是值运算层面的类型。

### 5.3 `void` 不进入命令类型

`CommandDataType` 明确禁止把 `void` 编码成命令数据类型。因为 `void` 表示没有值，不能被加载、赋值、取值或运算。这条规则能在命令层继续守住语义边界。

## 7. 命令树：为什么不直接输出列表

命令生成没有直接维护一个全局 `List<String>`，而是先构造命令树：

- `TerminalNode`：真正持有一条命令，扁平化时加入结果列表。
- `LabelNode`：不输出命令，只在扁平化时把当前结果列表长度写入 label。
- `HeadNode`：保存若干子命令节点，扁平化时递归展开。
- `CommandNodeListBuilder`：按顺序收集命令节点。
- `CommandSegmentSupport.flatten(...)`：把命令树最终展平成线性命令列表。

这个设计解决了控制流中最麻烦的问题：跳转目标往往只有在整个代码块长度确定后才能知道。

例如：

```text
if (cond) stmt;
```

翻译时可以先创建一个 `ifEndLabel`，然后生成：

1. 条件表达式命令。
2. `ifn_goto ifEndLabel`。
3. 语句体命令。
4. `LabelNode(ifEndLabel)`。

此时 label 还不知道自己是第几条命令。等 `flatten` 时，前面的命令数量已经确定，`LabelNode.flat` 执行 `label.setIndex(result.size())`，跳转命令在 `toString()` 时再读取这个 index。

这里有两个小巧思：

1. `LabelNode` 本身不进入命令列表，所以 label 不占用指令编号。
2. 跳转命令用 `StringSupplierCommand` 延迟读 label，因此不需要修改已经生成的字符串。

## 8. `CommandNodeRegister`：命令子树与未决控制流的载体

每次 shift 或 reduce 后，命令回调栈里保存的不是裸命令节点，而是 `CommandNodeRegister`。它有三个职责：

1. 能把自己注册进外层 `CommandNodeBuilder`。
2. 能携带未绑定的 `break` 跳转。
3. 能携带未绑定的 `continue` 跳转。

主要实现如下：

- `TokenCommandRegister`：token 级命令，例如字面量加载、未决 `break/continue`。
- `NormalCommandNodeRegister`：普通归约结果，包含命令节点数组，并从子节点收集未决跳转。
- `MergedCommandNodeRegister`：命令只采用 primary 分支，但未决跳转同时合并 primary 和 extras。
- `PlaceholderNodeRegister`：不输出任何命令。

其中最有设计价值的是 `MergedCommandNodeRegister`。它用于常量条件剪枝。

例如：

```text
if (false) {
    break;
}
```

从代码生成角度看，`if(false)` 的分支不可达，命令应该被删掉。但从语义诊断角度看，这个 `break` 仍然出现在循环外，应该报错。于是项目使用 `MergedCommandNodeRegister(new PlaceholderNodeRegister(), deadBranch)`：

- 输出命令时只输出 placeholder，也就是不生成死分支代码。
- 收集未决 `break/continue` 时仍然把 deadBranch 的未决跳转带上。
- 最外层 `ProgramCommandTranslator` 会发现这些未解析跳转，报告 `break is not allowed here.` 或 `continue is not allowed here.`。

这就是项目里“优化不吞错误”的关键机制。

## 9. 语法制导翻译的栈式回调

`CommandBuildCallback` 继承 `BuildStackContextCallback<CommandNodeRegister>`。这个泛型基类把 LR 分析中的 shift/reduce 与语义属性栈绑定起来：

- shift 一个 token：调用 token translator，得到一个 `CommandNodeRegister`，压入命令栈。
- reduce 一个产生式：按产生式右部长度弹出若干 child register，保持原顺序传给 production translator，再把新 register 压回栈。
- accept 前：把接受产生式也当作一次特殊 reduce 处理。

这是一种典型的自底向上语法制导翻译。语法分析器每归约出一个非终结符，命令系统就同步归约出这个语法片段对应的命令子树。

好处是：

1. 命令生成顺序与语法结构自然一致。
2. 每个 translator 只关心当前产生式和它的孩子，不需要全局遍历语法树。
3. 类型、常量、符号等属性也使用类似机制绑定到语法树节点，translator 可以通过上下文读取。

## 10. token 翻译器

token 级翻译器处理那些单个 token 就能产生或准备产生中间代码的情况。

| token 类型 | 翻译器 | 作用 |
| --- | --- | --- |
| 整数、浮点、布尔、字符、字符串、null 字面量 | `SimpleStringTokenTranslator` | 生成静态加载命令 |
| 标识符 | `LoadIdentifierAddressTokenTranslator` | 当前实现中主要作为占位，真正绑定符号发生在 `IdentifierUseTranslator` |
| 类型 token | `TypeTokenTranslator` | 类型只参与语义属性，不直接产生命令 |
| `break` | `BreakTokenTranslator` | 生成未绑定 label 的 goto，并放入 unresolved breaks |
| `continue` | `ContinueTokenTranslator` | 生成未绑定 label 的 goto，并放入 unresolved continues |
| 其他符号 | `DoNothingTokenTranslator` | 不产生命令 |

`break/continue` 在 token 阶段就生成未决跳转，是因为它们一出现就代表一条控制转移命令；但此时还不知道所属循环是哪一个，也不知道目标指令编号，所以只能先生成“没有目标的 goto”。

## 11. 产生式翻译器与语义标签分派

产生式翻译器不是按产生式文本硬编码分派，而是通过 `ProgramSemanticTag` 组合分派。分派入口是 `TagStrategyCompose.stringCommand()`，内部用 `ProductionTagStrategy<CommandTranslator>` 把语义标签组合映射到 translator。

例如：

| 语义标签组合 | 翻译器 |
| --- | --- |
| `PROGRAM` | `ProgramCommandTranslator` |
| `FUNCTION + DEFINITION` | `FunctionDefinitionTranslator` |
| `FUNCTION + HEAD` | `FunctionHeadTranslator` |
| `DECLARATION + INITIALIZED` | `DeclarationWithInitializationTranslator` |
| `DECLARATION` | `DeclarationWithoutInitializationTranslator` |
| `IDENTIFIER + USE` | `IdentifierUseTranslator` |
| `LEFT_VALUE` | `PrimaryProduceLeftValueTranslator` |
| `ASSIGNMENT` | `AssignStatementTranslator` |
| `ACCESS` | `ArrayAtExpressionTranslator` |
| `MEMBER_ACCESS` | `MemberAccessTranslator` |
| `NEW_STRUCT` | `NewStructTranslator` |
| `NEW_ARRAY` | `NewArrayTranslator` |
| `FUNCTION + CALL` | `FunctionCallTranslator` |
| `RETURN` | `FunctionReturnTranslator` |
| `CONDITIONAL` | `IfStatementTranslator` |
| `CONDITIONAL + ELSE_BRANCH` | `IfElseStatementTranslator` |
| `LOOP` | `WhileStatementTranslator` |
| `LOOP + DO_LOOP` | `DoWhileStatementTranslator` |
| `PLUS/MINUS/MULTIPLY/DIVIDE/...` | `InSuffixExpressionTranslator` 或 `UnaryExpressionTranslator` |

这套 tag 分派比直接匹配产生式字符串更稳健。语法细节调整时，只要语义标签不变，translator 不必大改。

## 12. 左值设计：`ADDRESS` 与 `REFERENCE`

项目把“能放在赋值左边的位置”分成两类：

- `LocationKind.ADDRESS`：普通标识符变量，命令中表现为变量表 offset 对应的地址。
- `LocationKind.REFERENCE`：由数组访问或结构体成员访问得到的内部引用。

例如：

```text
a
arr[i]
student.age
```

它们都是左值，但定位方式不同：

- `a` 可以直接用 `load_st_int32_address <offset>` 得到地址。
- `arr[i]` 需要先得到数组引用和下标，再用 `bias_from_st_top_to_ref_<type>` 得到元素引用。
- `student.age` 需要先得到结构体引用，再用字段 offset 得到字段引用。

这个区分贯穿三个地方：

1. `TypeBuildCallback` 给语法节点绑定 `TypeRegister`，其中保存 `LocationKind`。
2. `PrimaryProduceLeftValueTranslator` 把左值作为右值使用时，根据 `ADDRESS/REFERENCE` 选择 `st_top_addr_to_val_*` 或 `st_top_ref_to_val_*`。
3. `AssignStatementTranslator` 写回时，根据 `ADDRESS/REFERENCE` 选择 `assign_from_st_top_to_addr_*` 或 `assign_from_st_top_to_ref_*`。

这样，表达式求值和赋值写回都不需要猜测左值来源，类型属性已经把定位方式带了上来。

## 13. 标识符地址加载

标识符使用最终由 `IdentifierUseTranslator` 处理。它会从当前归约出的语法树节点中取出标识符 token，再通过 `context.getIdentifier(token)` 查标识符表，得到 `IdentifierRecord`。

`IdentifierRecord` 中保存：

- 标识符编号 `no`。
- 运行时槽位偏移 `offset`。
- 声明类型 `declaredType`。
- 是否初始化。
- 所属函数 `ownerFunction`。
- 编译期常量值 `constantValue`。

命令生成时只把 `offset` 和存储类别编码进命令：

```text
load_st_int32_address 0
load_st_ref_address 2
```

结构体、数组等引用类型统一使用 `ref` 存储类别。

## 14. 声明与初始化

带初始化的声明由 `DeclarationWithInitializationTranslator` 翻译。设计顺序是：

1. 读取声明目标类型和初始化表达式类型。
2. 调用 `SemanticDiagnostics.requireAssignable` 检查能否赋值。
3. 加载被声明变量的地址。
4. 生成初始化表达式命令。
5. 如果需要隐式转换，追加 `st_top_<from>_cast_<to>`。
6. 生成 `assign_from_st_top_to_addr_<type>` 写回。

例如：

```text
float64 f = i;
```

若 `i` 是 `int32`，命令会包含：

```text
load_st_float64_address <f_offset>
load_st_int32_address <i_offset>
st_top_addr_to_val_int32
st_top_int32_cast_float64
assign_from_st_top_to_addr_float64
```

这里的设计体现出两个细节：

- 目标地址先入栈，确保右值计算完成后仍然知道写回哪里。
- 隐式转换放在写回前，只转换栈顶源值，不影响目标地址。

无初始化声明由 `DeclarationWithoutInitializationTranslator` 处理，不产生命令。变量登记已经由标识符表回调完成。

## 15. 普通赋值

赋值由 `AssignStatementTranslator` 翻译，顺序与声明初始化类似：

1. 生成左值定位命令。
2. 生成右值求值命令。
3. 必要时追加隐式转换。
4. 根据左值定位种类写回地址或引用。

设计重点是“先定位左值，再计算右值”。这在数组和结构体嵌套访问中特别重要：

```text
school.grade[4].class[4].student[2].gender =
school.grade[2].class[3].student[0].gender;
```

左侧会生成一串 `bias_from_st_top_to_ref_*`，最后停在 `gender` 字段引用上；右侧也生成一串定位命令，但随后通过 `st_top_ref_to_val_boolean` 取值；最终用 `assign_from_st_top_to_ref_boolean` 写回左侧引用。

这种顺序让复杂左值不需要被重新计算，也避免丢失写回目标。

## 16. 左值作为右值

语法上 `a`、`arr[i]`、`student.age` 既可以出现在赋值左侧，也可以出现在表达式中。出现在表达式中时，它们必须从“位置”变成“值”。

`PrimaryProduceLeftValueTranslator` 专门负责这个动作：

- 如果当前语法节点已经被常量折叠，则直接生成 `load_st_*_static`。
- 否则先注册左值定位命令。
- 如果位置是 `REFERENCE`，追加 `st_top_ref_to_val_<type>`。
- 如果位置是 `ADDRESS`，追加 `st_top_addr_to_val_<type>`。

这使“定位”和“取值”被清晰拆开。数组访问和结构体字段访问默认产生的是引用位置，只有当它被当作表达式值使用时才读取。

## 17. 表达式与运算命令

二元表达式由 `InSuffixExpressionTranslator` 翻译。流程是：

1. 先尝试 `ConstantCommandSupport`。如果表达式已有编译期常量，直接返回一条常量加载命令。
2. 读取左右操作数类型。
3. 根据运算符类别推断实际指令类型：
   - 逻辑运算要求 boolean。
   - 相等运算允许同类型或可比较数值类型。
   - 关系运算要求数值类型。
   - 算术运算要求数值类型。
4. 生成左操作数命令。
5. 如果左操作数需要提升，追加 cast。
6. 生成右操作数命令。
7. 如果右操作数需要提升，追加 cast。
8. 追加 `st_<operator>_<instructionType>`。

例如：

```text
i < f
```

其中 `i` 是 `int32`，`f` 是 `float64`，会生成：

```text
load_st_int32_address <i_offset>
st_top_addr_to_val_int32
st_top_int32_cast_float64
load_st_float64_address <f_offset>
st_top_addr_to_val_float64
st_less_float64
```

表达式的结果类型是 `boolean`，但执行比较的指令类型是 `float64`。这也是 `TypeRegister` 同时保存 `type` 和 `instructionType` 的原因。

一元表达式由 `UnaryExpressionTranslator` 翻译：

- `!expr` 要求 boolean，生成 `st_logical_not_boolean`。
- `-expr` 要求 numeric，生成 `st_negate_int32` 或 `st_negate_float64`。

## 18. 类型转换规则

隐式转换由 `TypeConversionRule` 管理。当前规则很保守：

- 相同类型可以转换。
- `null` 可以转换为引用类型。
- `int32` 可以隐式转换为 `float64`，并且需要生成 cast 命令。
- `float64` 不能隐式转换为 `int32`。
- 非数值类型之间不允许随意转换。

命令层只在确实需要运行时转换时生成：

```text
st_top_int32_cast_float64
```

`null` 到引用类型不需要 cast，因为它本身就是一个可赋给引用槽位的特殊值。

## 19. 常量折叠与常量传播

项目把常量分析和命令生成拆成两层：

- `ConstantValueBuildCallback` 在语法归约时计算常量属性。
- 命令 translator 通过 `ConstantCommandSupport` 读取常量属性，决定是否直接生成常量加载命令。

当前常量系统支持：

- boolean、int32、float64 字面量。
- null 字面量。
- 一元负号和逻辑非。
- 算术表达式。
- 逻辑表达式。
- 相等和关系比较。
- 从标识符记录中读取已知常量。

字符串和字符字面量当前会被字面量加载命令处理，但不会在 `ConstantValueBuildCallback` 中参与复杂常量折叠。

例如：

```text
int32 a = 1 + 2 * 3;
```

不是生成乘法和加法命令，而是直接生成：

```text
load_st_int32_static 7
```

### 19.1 标识符常量状态

声明初始化时，`IdentifierTableBuildCallback` 会把初始化常量存入 `IdentifierRecord.constantValue`。之后如果某个简单标识符被普通赋值，`IdentifierConstantStateCallback` 会把它的常量状态清掉。

这是一个保守设计：项目没有做路径敏感分析，所以一旦变量被重新赋值，就不再假设它仍然是原来的编译期常量。这样可以避免错误传播旧常量。

## 20. 条件语句

### 20.1 普通 `if`

非编译期常量条件的 `if` 翻译为：

```text
condition.commands
ifn_goto ifEnd
then.commands
ifEnd:
```

其中 `ifEnd` 是 `SemanticLabel`，真正的数字下标在 flatten 时确定。

如果条件是编译期常量：

- `if(true)`：直接保留 then 分支命令，不生成跳转。
- `if(false)`：不输出 then 分支命令，但通过 `MergedCommandNodeRegister` 保留 then 分支中的未决 `break/continue` 以便诊断。

### 20.2 `if-else`

非编译期常量条件的 `if-else` 翻译为：

```text
condition.commands
ifn_goto elseStart
then.commands
goto elseEnd
elseStart:
else.commands
elseEnd:
```

如果条件是编译期常量：

- `if(true)`：输出 then 分支命令，但合并 else 分支未决控制流。
- `if(false)`：输出 else 分支命令，但合并 then 分支未决控制流。

这保证了“代码优化”和“语义错误诊断”同时成立。

## 21. 循环与 `break/continue`

### 21.1 `while`

普通 `while` 翻译为：

```text
whileStart:
condition.commands
ifn_goto whileEnd
body.commands
goto whileStart
whileEnd:
```

循环翻译器还会把循环体中未绑定的控制流绑定到当前循环：

- `continue` 绑定到 `whileStart`，也就是重新检查条件。
- `break` 绑定到 `whileEnd`，也就是跳出循环。

如果条件是编译期常量 `false`，`while(false)` 直接返回 `PlaceholderNodeRegister`，不输出条件、循环体和跳转命令。循环体内部的 `break/continue` 本来就处在循环内部，因此不需要作为非法顶层控制流继续传播。

### 21.2 `do-while`

普通 `do-while` 翻译为：

```text
whileStart:
body.commands
beforeTest:
condition.commands
if_goto whileStart
whileEnd:
```

与 `while` 的差别是 `continue` 不能跳到循环体开头，而应该跳到条件检查点 `beforeTest`。项目专门为 `do-while` 设置这个 label，避免把 `continue` 误翻译成“重新执行循环体”。

如果条件是编译期常量 `false`，`do-while(false)` 仍然保留一次循环体命令，但不生成条件跳转和回边。此时：

- `break` 绑定到循环出口。
- `continue` 也绑定到循环出口。

这是符合 do-while 语义的：循环体执行一次后条件恒 false，不会再进入下一轮。

### 21.3 未决跳转绑定

`break` 和 `continue` 的完整链路是：

1. token 阶段生成 `StringUncertainLabelGotoCommand`，文本暂时可显示为 `goto unknown`。
2. 该命令被放入 `uncertainBreaks` 或 `uncertainContinues`。
3. 普通语句归约时，`NormalCommandNodeRegister` 自动收集子节点的未决跳转。
4. 循环归约时，`WhileStatementTranslator.bindLoopLabels(...)` 把未解析跳转绑定到当前循环 label。
5. 嵌套循环中，内层循环先归约并绑定自己的未决跳转；外层只会看到仍未解析的跳转。
6. 程序顶层 `ProgramCommandTranslator` 检查是否还有未解析跳转，如果有就报错。

这个设计自然支持嵌套循环，因为每个循环只绑定自己循环体里尚未解析的 `break/continue`。

## 22. 函数命令段

函数相关设计有两个层次：

- `FunctionSemanticCallback` 负责函数语义：登记函数签名、参数、返回类型，检查调用参数和返回语句。
- `FunctionDefinitionTranslator` 负责函数体命令：把函数体命令单独 flatten 成一个 `FunctionCommandSegment`。

函数定义本身不会把函数体命令混入全局入口命令流。它会：

1. 找到当前函数的 `FunctionRecord`。
2. 对函数体 child register 执行 `CommandSegmentSupport.flatten(...)`。
3. 构造 `FunctionCommandSegment(function, commands)`。
4. 登记到 `FunctionCommandSegmentContext`。
5. 返回 `PlaceholderNodeRegister`，表示函数定义在入口段不产生命令。

因此，一个只有函数定义的程序可以拥有空的 entry commands，但有函数命令段。

### 22.1 函数调用

函数调用由 `FunctionCallTranslator` 翻译：

1. 先生成实参列表命令。
2. 再追加 `call <functionIndex>`。

实参列表通过 `StatementListTranslator` 和参数列表语法保持源码顺序。测试中验证了多参数调用会按 `arg1, arg2, ...` 的顺序加载实参。

### 22.2 返回语句

`FunctionReturnTranslator` 的当前实现是：

- 如果返回表达式是编译期常量，直接加载常量。
- 否则生成返回表达式命令。
- 最后追加 `return`。

返回值类型检查由 `FunctionSemanticCallback` 完成。当前命令层对普通赋值和声明初始化会显式插入隐式 cast；返回语句本身没有单独补一条 return-value cast，这是后续扩展到真实执行后端时需要重点对齐的地方。

### 22.3 函数结果组织

`SemanticAnalysisResult` 中函数相关结果分开保存：

- `entryCommands`：入口段命令。
- `functionSegments`：每个函数的命令段。
- `getFunctionTable()`：从函数命令段中提取函数表。
- `getEntryLocalVariables()`：全局变量。
- `getFunctionLocalVariables(function)`：指定函数的局部变量。

这使测试报告可以按“Global Segment”和“Function Segment”分开展示。

## 23. 结构体机制

结构体定义由结构体语义模块登记为 `StructRecord`。记录中包含：

- 结构体表编号 `tableIndex`。
- 结构体名 token。
- 字段列表。
- 每个字段的类型和 offset。

### 23.1 创建结构体

`NewStructTranslator` 会根据语法树中的结构体名查 `StructRecord`，然后生成：

```text
new_struct <structIndex>
```

这里使用结构体表编号，而不是结构体名字，是为了让后端或报告可以通过编号查布局。

### 23.2 成员访问

结构体字段访问由 `MemberAccessTranslator` 翻译。流程是：

1. 生成左操作数命令，得到结构体对象的地址或引用。
2. 用类型系统确认它是已声明结构体。
3. 在 `StructRecord` 中查找字段。
4. 取字段 offset。
5. 生成：

```text
bias_from_st_top_to_ref_<fieldType> <offset>
```

成员访问本质上是“基地址 + 固定字段偏移”。项目把它和数组访问统一成 bias 命令，只是结构体字段偏移是编译期固定整数，数组偏移来自运行时下标表达式。

## 24. 数组机制

数组机制分成数组创建和数组访问两部分。

### 24.1 数组类型

`SemanticType` 用 `dimensions` 表示数组维度。数组元素类型通过 `arrayElementType()` 得到。

例如：

- `int32[]` 是 `kind=INT32, dimensions=[0]`。
- `int32[][]` 是 `kind=INT32, dimensions=[0,0]`。
- 对 `int32[][]` 做一次下标访问，结果类型是 `int32[]`。

### 24.2 数组创建维度汇总

数组创建由 `ArrayCreationDimensions` 负责汇总和校验维度。它处理左递归列表时没有简单从当前节点往右读，而是用栈把维度恢复成源码顺序。

它统计三个值：

- `totalDimensions`：总维度数。
- `specifiedDimensions`：显式写出长度表达式的维度数。
- `trailingOmittedDimensions`：尾部省略长度的维度数。

规则是：

1. 至少要有一个显式长度。
2. 显式长度必须出现在省略维度之前。
3. 每个长度表达式必须是 `int32`。

于是以下形式可区分：

```text
new int32[11][12][13]  -> new_array_int32 3 3
new int32[11][12][]    -> new_array_int32 3 2
new int32[11][][]      -> new_array_int32 3 1
```

### 24.3 数组创建命令

`NewArrayTranslator` 的顺序是：

1. 校验元素类型不是 `void`。
2. 汇总维度。
3. 先生成所有显式长度表达式命令。
4. 追加：

```text
new_array_<elementType> <totalDimensions> <specifiedDimensions>
```

数组元素如果是结构体或数组，命令层 element type 会是 `ref`，例如嵌套结构体数组场景会出现 `new_array_ref 1 1`。

### 24.4 数组访问命令

`ArrayAtExpressionTranslator` 翻译 `base[index]`：

1. 生成 base 命令。
2. 生成 index 命令。
3. 校验 base 是数组。
4. 校验 index 是 `int32`。
5. 生成：

```text
bias_from_st_top_to_ref_<elementStorageType>
```

结果是一个 `REFERENCE`，表示数组元素位置。它后续可以被赋值，也可以通过 `st_top_ref_to_val_*` 读取成值。

## 25. 程序顶层与非法控制流诊断

`ProgramCommandTranslator` 主要委托 `SimpleShrinkTranslator` 合并子命令，但额外做一件事：检查顶层是否还有未解析的 `break/continue`。

如果 `break` 没有被任何循环绑定，说明它出现在循环外，报错：

```text
break is not allowed here.
```

如果 `continue` 没有被任何循环绑定，也会报错：

```text
continue is not allowed here.
```

这个兜底检查与前面的未决跳转传播机制配合，覆盖了普通非法控制流和死分支中的非法控制流。

## 26. 结果收集与报告输出

`SemanticResultCallback` 在 accept 前构造 `SemanticAnalysisResult`：

1. 从命令栈顶部取 `CommandNodeRegister`。
2. 调用 `CommandSegmentSupport.flatten(top)` 得到入口段命令。
3. 从 `FunctionCommandSegmentContext` 取函数命令段快照。
4. 从上下文取结构体表和标识符表。
5. 封装为 `SemanticAnalysisResult`。

`ProgramSyntaxTestRunner` 会进一步生成 markdown 测试报告，每个用例包含：

- Source。
- Struct Table。
- Global Segment Commands。
- Global Local Variables。
- Function Segment Commands。
- Function Local Variables。
- Errors。
- Failure。

这套报告机制使三地址码不仅是内部数据，也成为可检查、可展示的实验结果。

## 27. 测试覆盖体现的设计要求

`AppTest` 对中间代码机制做了大量行为断言，覆盖点包括：

- 不应出现未知类型地址加载，例如 `load_st_unknown_address`。
- `if-else` 的 then 分支结束后要跳过 else 分支。
- `while` 的 `continue` 要跳回条件检查点。
- `do-while` 的 `continue` 要跳到条件检查点，而不是循环体开头。
- 嵌套循环中的内层 `break/continue` 不能绑定到外层循环。
- 多个不同层级的 `break` 要有不同跳转目标。
- `int32 -> float64` 赋值要生成 `st_top_int32_cast_float64`。
- 混合数值关系比较要按公共类型生成比较命令。
- 常量表达式要被折叠成 `load_st_*_static`。
- `if(true)`、`if(false)`、`while(false)`、`do-while(false)` 要按常量条件剪枝。
- 死分支中的非法 `break/continue` 仍要诊断。
- 函数体不能混入入口命令段。
- `call <index>` 要引用函数表编号。
- 结构体创建、字段偏移、null 赋值要正确。
- 数组创建要正确记录总维度和显式维度。
- 嵌套结构体数组左值赋值要产生连续 bias 和正确的 ref 写回。
- 结构体数组参数传递和函数调用顺序要正确。

这些测试说明当前中间代码机制不是只打印几个简单表达式，而是覆盖了真实语言子集中的多种组合场景。

## 28. 关键设计巧思总结

### 28.1 用命令树解决 label 回填

传统做法可能需要记录“第几条命令的目标待回填”，最后再修改字符串。项目改用 `LabelNode + StringSupplierCommand`：label 在 flatten 时知道 index，跳转命令在打印时读 index。这样跳转命令对象从创建到输出都不需要被替换。

### 28.2 `break/continue` 先生成，再绑定

`break/continue` 在 token 阶段就生成 goto，但目标 label 留空。循环归约时统一绑定。这样嵌套循环自然正确，循环外非法控制流也能在顶层统一诊断。

### 28.3 死代码剪枝仍保留错误诊断

`MergedCommandNodeRegister` 只输出可达分支命令，却合并不可达分支中的未决控制流。这样 `if(false){break;}` 不生成死代码，但仍能报错。

### 28.4 `ADDRESS/REFERENCE` 把左值来源讲清楚

普通变量、数组元素、结构体字段都是左值，但定位方式不同。用 `LocationKind` 标记之后，取值和写回命令都可以精确选择 addr 或 ref 版本。

### 28.5 `forStorage/forValue` 防止类型层混乱

结构体和数组在存储层是 `ref`，但不能被当成普通标量运算。`CommandDataType.forStorage` 和 `forValue` 的拆分把这个边界固定在 API 上。

### 28.6 语义标签分派降低文法耦合

translator 不是靠产生式字符串匹配，而是靠 `ProgramSemanticTag` 组合匹配。文法结构变化时，只要语义标签稳定，中间代码生成逻辑就能保持稳定。

### 28.7 常量分析与命令生成解耦

常量值先由 `ConstantValueBuildCallback` 绑定到语法树节点，命令翻译器只读结果。这使常量折叠既能服务表达式命令，也能服务条件剪枝和函数返回流分析。

### 28.8 函数段隔离

函数定义被翻译成独立 `FunctionCommandSegment`，入口段只保留全局执行命令。这个设计让函数表、函数局部变量和函数命令天然对应。

### 28.9 数组维度用 Summary 表达

数组创建没有把维度直接拼字符串，而是先用 `ArrayCreationDimensions.Summary` 表示总维度、显式维度和尾部省略维度。这样命令既简洁，又保留了运行时分配需要的信息。

### 28.10 测试报告直接展示 IR

`ProgramSyntaxTestRunner` 把命令、符号表、结构体表、函数段一起输出为 markdown。中间代码机制因此可以被持续回归验证，而不是只在控制台临时查看。

## 29. 从源码角度看一次完整例子

以：

```text
int32 a = 1;
int32 b = a + 2;
```

为例，完整设计链路是：

1. `1` token shift 时，token translator 可以生成字面量加载 register。
2. `ConstantValueBuildCallback` 在归约 literal 时绑定常量 `1`。
3. 声明 `a` 归约时，`IdentifierTableBuildCallback` 登记变量 `a`，offset 例如为 `0`，并记录常量值 `1`。
4. `DeclarationWithInitializationTranslator` 加载 `a` 地址，发现初始化表达式可常量化，生成 `load_st_int32_static 1`，再写回 `a`。
5. 使用 `a` 时，`IdentifierUseTranslator` 根据标识符表生成 `load_st_int32_address 0`。
6. `ConstantValueBuildCallback` 发现 `a` 仍有常量值，因此 `a + 2` 可被折叠为 `3`。
7. 声明 `b` 时，命令层最终只需要加载 `b` 地址、加载常量 `3`、写回。

如果之后出现：

```text
a = a + 1;
```

`IdentifierConstantStateCallback` 会在赋值归约后清除 `a` 的常量状态。后续再用 `a` 时，就不会继续把它当作编译期常量传播。

## 30. 按对象流追踪：`a = b + 1;` 到底怎么跑

这一节专门从代码执行角度追踪一个简单赋值，帮助读者把前面的类和方法串起来。假设 `a` 和 `b` 都已经在标识符表中登记，类型都是 `int32`。

源码片段：

```text
a = b + 1;
```

### 30.1 shift 阶段：token 先变成局部 register

语法分析器读到 token 时会触发 `context.onShift(nextStatus, token)`。所有回调都会依次收到这个事件。对命令生成来说，关键是 `CommandBuildCallback.onShift`，它会调用 token translator。

对字面量 `1`：

```text
SimpleStringTokenTranslator.translate(context, token)
  -> context.getCommandFactory().loadStatic(token)
  -> TypedStringCommandFactory.loadLiteral(token)
  -> StringCommand("load_st_int32_static 1")
  -> TokenCommandRegister(command)
```

于是命令栈里会压入一个 `TokenCommandRegister`。这个 register 还没有进入最终命令列表，它只是表示“这个 token 如果被外层需要，可以注册出一条加载常量命令”。

对标识符 token，当前 `LoadIdentifierAddressTokenTranslator` 返回的是 `PlaceholderNodeRegister`。真正的标识符地址加载不在 shift 阶段完成，而是在归约到 `IDENTIFIER + USE` 后由 `IdentifierUseTranslator` 完成。这样做的原因是：只有归约成“标识符使用”之后，结合语法上下文和标识符表，才能确定它确实是一次变量使用，而不是声明位置、类型名等其他角色。

### 30.2 归约 `b`：标识符使用变成地址加载

当语法分析器把 `b` 归约为带 `IDENTIFIER + USE` 标签的产生式时：

```text
CommandBuildCallback.onReduce(production)
  -> TagStrategyCompose 解析到 IdentifierUseTranslator
  -> IdentifierUseTranslator.translate(...)
```

`IdentifierUseTranslator` 会做：

1. 从当前语法树归约头节点中取出 `b` 的 token。
2. 调用 `context.getIdentifier(token)` 查标识符表。
3. 得到 `IdentifierRecord`，里面有 `declaredType=int32` 和 `offset=<b_offset>`。
4. 调用 `context.getCommandFactory().loadIdentifierAddress(record)`。
5. 生成 `load_st_int32_address <b_offset>`。
6. 包装成 `TerminalNode`。
7. 返回 `NormalCommandNodeRegister`。

此时 `b` 仍然是“位置”，不是值。

### 30.3 归约 `b` 作为表达式因子：地址变值

当 `b` 作为表达式值参与 `b + 1` 时，会归约到 `LEFT_VALUE` 相关产生式，触发：

```text
PrimaryProduceLeftValueTranslator
```

它会先检查当前节点有没有常量值。如果没有，就继续常规翻译：

1. 把 `b` 的地址加载命令注册进 builder。
2. 读取类型属性 `TypeRegister`。
3. 发现 `LocationKind.ADDRESS`。
4. 追加：

```text
st_top_addr_to_val_int32
```

于是 `b` 的表达式值对应命令变成：

```text
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
```

如果这里是 `arr[i]`，类型属性会是 `LocationKind.REFERENCE`，追加的就会是 `st_top_ref_to_val_int32`。

### 30.4 归约 `b + 1`：两个孩子合成一个表达式命令树

当语法分析器归约 `b + 1`，产生式带有 `PLUS` 标签，于是分派到：

```text
InSuffixExpressionTranslator
```

它的工作顺序是：

1. 调 `ConstantCommandSupport.constantOrNull(...)` 看看 `b + 1` 是否已经是编译期常量。
2. 如果不是常量，读取左右孩子类型。
3. 对 `PLUS` 运算要求左右都是数值类型。
4. 通过 `context.commonBinaryType(leftType, rightType)` 得到指令类型。
5. 注册左孩子命令，也就是 `b` 的取值命令。
6. 如有必要插入左操作数 cast。
7. 注册右孩子命令，也就是 `load_st_int32_static 1`。
8. 如有必要插入右操作数 cast。
9. 追加：

```text
st_plus_int32
```

归约完成后，`b + 1` 这个语法节点对应一个新的 `NormalCommandNodeRegister`。它里面保存的是一棵命令子树，而不是已经展开的字符串列表。

### 30.5 归约赋值：左值定位 + 右值求值 + 写回

当整个 `a = b + 1;` 被归约为 `ASSIGNMENT`，分派到：

```text
AssignStatementTranslator
```

它按固定顺序组装：

1. 读取左侧 `a` 的类型。
2. 读取右侧 `b + 1` 的类型。
3. 用 `SemanticDiagnostics.requireAssignable(...)` 检查能不能赋值。
4. `children[0].register(builder)`，注册左侧 `a` 的定位命令。
5. `children[2].register(builder)`，注册右侧表达式命令。
6. 如需隐式转换，追加 `st_top_<from>_cast_<to>`。
7. 看左侧 `LocationKind`：
   - `ADDRESS`：追加 `assign_from_st_top_to_addr_int32`。
   - `REFERENCE`：追加 `assign_from_st_top_to_ref_int32`。

本例中左侧 `a` 是普通变量，所以最后得到：

```text
load_st_int32_address <a_offset>
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
assign_from_st_top_to_addr_int32
```

### 30.6 为什么不是每一步都立即输出

在以上每个阶段，命令都只是被包装进 register。原因是：

1. 控制流 label 还没确定编号。
2. 外层结构可能会剪枝，比如 `if(false)` 直接丢弃分支命令。
3. 函数体需要被单独收集到函数段，不能直接混入全局入口段。

所以项目选择先保留命令树，到最后统一 flatten。

### 30.7 accept 前：命令树变成最终命令列表

程序归约到 accept 前，`SemanticResultCallback.beforeAccept(...)` 会取命令栈顶部：

```text
CommandNodeRegister top = commandContext.peek();
```

然后：

```text
List<SemanticCommand> entryCommands = CommandSegmentSupport.flatten(top);
```

`flatten` 做两层事情：

1. 先调用 `top.register(builder)`，把 register 注册成若干 `CommandNode`。
2. 再递归调用每个 `CommandNode.flat(result)`。

如果遇到：

```text
TerminalNode
```

就把命令加入列表。

如果遇到：

```text
LabelNode
```

就设置 label 的 index，不加入列表。

最终 `SemanticAnalysisResult.getCommands()` 再调用 `ThreeAddressCodePrinter.print(entryCommands)`，把每个命令对象转成字符串。

### 31.1 字面量

```text
ShiftReducePhaserImpl.onShift
```

### 31.2 标识符使用

```text
ShiftReducePhaserImpl.onReduce

  -> DefaultCommandFactory.loadIdentifierAddress
  -> TypedStringCommandFactory.loadIdentifierAddress

```

### 31.3 二元表达式

```text
InSuffixExpressionTranslator.translate
  -> ConstantCommandSupport.constantOrNull
  -> TypeAttributes.childType
  -> SemanticDiagnostics.requireNumeric / requireBoolean
  -> children[0].register(builder)

  -> children[2].register(builder)

  -> TerminalNode("st_<operator>_<type>")
```

### 31.4 if-else

```text
IfElseStatementTranslator.translate
  -> ConstantConditionSupport.booleanValue
  -> 如果常量：MergedCommandNodeRegister 选择可达分支
  -> 如果非常量：
       new DefaultSemanticLabel elseStart
       new DefaultSemanticLabel elseEnd
       condition.register
       TerminalNode(ifnGoto(elseStart))
       then.register
       TerminalNode(gotoCommand(elseEnd))
       LabelNode(elseStart)
       else.register
       LabelNode(elseEnd)
```

### 31.5 while

```text
WhileStatementTranslator.translate
  -> ConstantConditionSupport.booleanValue
  -> false: PlaceholderNodeRegister
  -> normal:
       LabelNode(whileStart)
       condition.register
       TerminalNode(ifnGoto(whileEnd))
       body.register

```

### 31.6 break/continue

```text
BreakTokenTranslator / ContinueTokenTranslator
  -> commandFactory.gotoCommandUncertainLabel(token)

  -> TokenCommandRegister(command, uncertainBreaks/uncertainContinues)
  -> 普通归约时 NormalCommandNodeRegister 收集未决跳转
  -> 循环归约时 bindLoopLabels 设置 label
  -> 顶层 ProgramCommandTranslator 检查仍未 resolved 的跳转并报错
```

```text
FunctionSemanticCallback
```

```text
  -> 校验 index 是 int32
```

```text
  -> struct.field(fieldToken)

  -> commandFactory.biasFromStTopToRef(fieldType, offset)
  -> 结果类型在 TypeBuildCallback 中标记为 LocationKind.REFERENCE
```

## 32. 适合在实验报告中强调的设计重点

写实验三报告时，最值得展开的不是某几段 Java 代码，而是这些设计主题：

1. 中间代码采用栈式三地址风格，隐式临时值减少了临时变量管理复杂度。
2. 命令工厂把语义动作和具体文本编码解耦。
3. 命令树与 label 节点实现无侵入式回填。
4. `CommandNodeRegister` 同时承载命令和未决控制流，是控制流语义的核心。
5. `MergedCommandNodeRegister` 解决了常量剪枝与错误诊断的冲突。
6. 类型属性、常量属性、符号表属性先行构建，命令翻译器只做局部语义动作。
7. `ADDRESS/REFERENCE` 区分让变量、数组元素、结构体字段统一而不混乱。
8. 函数命令段和入口段分离，符合真实编译器的函数代码布局。
9. 数组与结构体都通过 ref 和 bias 机制表达，命令集简洁统一。
10. 测试体系用具体命令序列验证设计，而不是只验证语法能否通过。
