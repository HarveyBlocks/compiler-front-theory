## 第1章 实验概述

### 一、实验目的

本实验的核心目标，是在词法分析和语法分析已经可用的基础上，进一步完成“语法制导翻译”和“中间代码生成”。从编译系统的完整流程看，实验三处在前端后半部分：语法分析器已经能判断 token 序列是否符合文法，而实验三要回答的是：当某个程序语法正确时，如何把它翻译成带类型、带作用域、带控制流关系、带函数与结构体信息的中间表示；当程序语义不正确时，如何在合适的阶段拒绝它并报告原因。

本项目不是简单地在若干产生式上附加几段动作代码，而是实现了一条完整的编译前端链路：

```text
源程序文本
  -> 输入资源与字符读取
  -> 正则表达式驱动的词法分析
  -> LALR 移进-归约语法分析
  -> 多语义回调并行处理 shift/reduce 事件
  -> 语法树、作用域、符号表、类型属性、常量属性
  -> 函数表、结构体表、数组维度信息
  -> 命令树与 label 解析
  -> 栈式三地址风格中间代码
  -> Markdown 测试报告
```

本实验希望达到以下目的：

1. 理解语法制导翻译中“语法结构”和“语义属性”之间的关系，掌握在自底向上分析过程中如何利用归约时机计算综合属性。
2. 掌握符号表、作用域、类型检查、常量折叠、函数签名、结构体布局等语义信息如何协同工作。
3. 设计一种稳定的语义动作分发机制，使语义模块不直接依赖脆弱的产生式字符串，而是依赖明确的语义标签。
4. 生成能够表达变量读写、数组访问、结构体成员访问、函数调用、条件跳转、循环跳转和返回语句的中间代码。
5. 通过全链路测试验证中间代码的顺序、跳转目标、隐式类型转换、函数段拆分、结构体字段 offset 和错误诊断是否符合设计预期。

从工程角度看，本实验还强调可扩展性：新增一个语法结构时，不应当把整个前端推倒重写，而应当沿着“新增 token -> 新增文法与 tag -> 新增类型/常量规则 -> 新增命令翻译器 -> 新增测试用例”的路线扩展。

### 二、实验内容

项目是一个 Java 11 Maven 工程。实验三相关代码主要位于 `src/main/java/org/harvey/vie/theory/semantic`、`src/main/java/org/harvey/vie/theory/demo/program`、`src/main/java/org/harvey/vie/theory/syntax/bu` 等目录。

本实验最终支持的 Program 语言特性包括：

| 类别 | 已支持内容 |
| --- | --- |
| 基本类型 | `boolean`、`char`、`int32`、`float64`、`string`、`void` |
| 引用类型 | 结构体类型、数组类型、`null` |
| 声明与赋值 | 普通声明、带初始化声明、左值赋值 |
| 表达式 | 算术、关系、相等、逻辑、一元取反、一元负号、括号表达式 |
| 控制流 | `if`、`if-else`、`while`、`do-while`、`break`、`continue` |
| 函数 | 函数定义、参数列表、实参列表、函数调用、`return`、返回路径检查 |
| 结构体 | 结构体声明、字段表、字段 offset、对象创建、成员访问 |
| 数组 | 数组类型、数组创建、显式/省略维度、数组索引 |
| 优化 | 常量折叠、常量传播、常量条件下的控制流裁剪 |
| 测试输出 | 单用例 Markdown 报告、汇总报告、命令列表、结构体表、函数段、符号表、错误列表 |

实验三的重点不是词法自动机或 LR 表本身，而是如何在 LR 分析的 shift/reduce 事件上搭建一个语义系统。项目中最重要的设计点可以概括为：语法分析器只负责驱动，语义模块通过回调观察同一套事件，各自维护一个清晰的属性维度，最后再由结果回调收束为 `SemanticAnalysisResult`。

## 第2章 程序设计

### 一、相关文法或语言定义

#### 1. 词法定义

Program 语言的词法入口为 `ProgramLexicalDemo`。项目没有手写一个巨大 `switch` 扫描器，而是用 `LexicalPattern` 统一描述“正则表达式 + token 类型”，再由词法导演器构造 NFA、DFA、最小化 DFA，并持久化为词法状态表。

这种设计的直接好处是：词法规则和扫描过程分离。新增关键字、运算符或字面量时，主要修改 token 枚举和正则模式集合，而不是修改扫描器核心循环。当前 token 类型由 `ProgramTokenType` 定义，主要包括：

| 类别 | token 示例 |
| --- | --- |
| 标识符 | `IDENTIFIER`、`TYPE_IDENTIFIER` |
| 空白与注释 | `SPACE`、`COMMENT_LINE`、`COMMENT_BLOCK` |
| 字面量 | 整数、浮点、布尔、字符、字符串、`null` |
| 类型关键字 | `boolean`、`char`、`int32`、`float64`、`string`、`void` |
| 对象与结构体 | `new`、`struct` |
| 运算符 | `+`、`-`、`*`、`/`、`!`、`&&`、`||`、`==`、`!=`、`<`、`<=`、`>`、`>=`、`=`、`.`、`,`、`;` |
| 括号 | `(`、`)`、`[`、`]`、`{`、`}` |
| 控制流关键字 | `if`、`else`、`while`、`do`、`break`、`continue`、`return` |

空白和注释在词法层仍然会被识别成 token，但进入语法分析前由 `ProgramSyntaxDemo.SHOULD_BE_FILTERED` 过滤掉。这样做不是多余的：它让词法阶段保持可观察，便于调试和错误定位，同时让语法文法不需要为无意义 token 留位置。

结构体类型名有一个特殊处理。用户声明：

```text
struct Point { int32 x; }
```

之后，`Point p;` 中的 `Point` 应当被视为类型名，而不是普通变量名。项目用 `ProgramStructAwareTokenIterator` 在 token 流层面记录已出现的结构体名，并在类型位置把普通 `IDENTIFIER` 重分类为 `TYPE_IDENTIFIER`。这个设计把“类型名识别”放在词法和语法之间的薄适配层中，而不是把结构体名硬编码进文法。

#### 2. 语法定义

完整文法由 `ProgramSyntaxDemo.buildGrammar0()` 通过 builder 风格 DSL 构造，资源文件 `src/main/resources/grammar0.txt` 也保存了对应的文法文本。起始符号为 `compilation_unit`。

顶层结构支持三类项目：

```text
compilation_unit ::= program
program          ::= top_item
                   | top_item program
top_item         ::= struct_decl
                   | function_decl
                   | block_item
```

结构体声明采用字段列表形式：

```text
struct_decl       ::= struct id { struct_field_list }
struct_field_list ::= struct_fields | epsilon
struct_fields     ::= struct_fields struct_field | struct_field
struct_field      ::= type id ;
```

函数声明由函数头和函数体组成：

```text
function_decl ::= function_head block
function_head ::= type id ( param_list )
                | void id ( param_list )
param_list    ::= params | epsilon
params        ::= params , param | param
param         ::= type id
```

块、声明和语句的基本结构如下：

```text
block       ::= { block_items }
block_items ::= block_items block_item | epsilon
block_item  ::= decl | stmt
decl        ::= type id ;
              | type id = bool ;
```

为了解决悬挂 `else` 问题，语句文法采用 matched/unmatched 经典拆分：

```text
stmt           ::= matched_stmt | unmatched_stmt
matched_stmt   ::= assign_stmt
                 | expr_stmt
                 | matched_while_stmt
                 | do_while_stmt
                 | break ;
                 | continue ;
                 | return_stmt
                 | block
                 | matched_if_stmt
unmatched_stmt ::= unmatched_if_stmt
                 | unmatched_while_stmt

matched_if_stmt   ::= if ( bool ) matched_stmt else matched_stmt
unmatched_if_stmt ::= if ( bool ) stmt
                    | if ( bool ) matched_stmt else unmatched_stmt
```

表达式文法按照优先级分层：

```text
bool     ::= bool || join | join
join     ::= join && equality | equality
equality ::= equality == rel | equality != rel | rel
rel      ::= expr < expr | expr <= expr | expr >= expr | expr > expr | expr
expr     ::= expr + term | expr - term | term
term     ::= term * unary | term / unary | unary
unary    ::= ! unary | - unary | factor
factor   ::= ( bool )
           | new_struct_expr
           | new_array_expr
           | call_expr
           | loc
           | integer
           | float
           | true
           | false
           | null
```

左值既可以是普通标识符，也可以继续派生为数组元素或结构体字段：

```text
loc ::= loc [ bool ]
      | loc . id
      | id
```

数组和结构体相关文法如下：

```text
type ::= type [ ]
       | type_identifier
       | boolean
       | character
       | int32
       | float64
       | string

new_struct_expr ::= new type_identifier ( )

new_array_expr   ::= new array_creation_base array_creation_dims
array_creation_base ::= type_identifier | boolean | character | int32 | float64 | string
array_creation_dims ::= array_creation_dims array_creation_dim | array_creation_dim
array_creation_dim  ::= [ bool ] | [ ]
```

函数调用和实参列表如下：

```text
call_expr ::= id ( arg_list )
arg_list  ::= args | epsilon
args      ::= args , bool | bool
```

#### 3. 语义标签定义

如果语义动作直接根据产生式字符串分发，例如判断某条产生式是否等于 `"expr -> expr + term"`，系统会很脆弱：产生式重命名、结构调整、增加中间非终结符都会影响语义模块。项目为此设计了 `ProgramSemanticTag`。

每条产生式候选体可以携带一组标签，例如：

| 标签 | 语义含义 |
| --- | --- |
| `PROGRAM` | 程序入口或顶层归约 |
| `DECLARATION`、`INITIALIZED` | 声明、带初始化声明 |
| `TYPE`、`ARRAY`、`STRUCT_TYPE` | 类型构造 |
| `IDENTIFIER`、`USE` | 标识符声明或引用 |
| `LEFT_VALUE`、`ACCESS`、`MEMBER_ACCESS` | 左值、数组访问、成员访问 |
| `FUNCTION`、`HEAD`、`DEFINITION`、`CALL`、`RETURN` | 函数相关语义 |
| `STRUCT_DECL`、`STRUCT_FIELD` | 结构体声明与字段 |
| `NEW_STRUCT`、`NEW_ARRAY` | 对象和数组创建 |
| `CONDITIONAL`、`ELSE_BRANCH`、`LOOP`、`DO_LOOP` | 控制流结构 |
| `LIST`、`EMPTY`、`SEQUENCE`、`FORWARD` | 列表结构与属性转发 |
| `OR`、`AND`、`EQUAL`、`PLUS`、`MULTIPLY` 等 | 运算符语义 |

类型构造、常量折叠、函数检查和命令生成都通过这些 tag 分发。这样语义模块依赖的是稳定的“语义意图”，而不是某条产生式的文本外观。

### 二、程序整体设计

#### 1. 总体架构

项目按职责可以分为六层：

1. 输入层：`Resource` 和 `SourceReader` 负责把源程序转为带 offset 的字符流。
2. 词法层：`ProgramLexicalDemo` 构造或加载 DFA 表，`DefaultLexicalAnalyzer` 产生 token 流。
3. 语法层：`ProgramSyntaxDemo.buildGrammar0()` 构造文法，`SyntaxDemo.buildShiftReduceParsingTable()` 构造或加载 LALR 分析表。
4. 语法驱动层：`ShiftReducePhaserImpl` 根据 ACTION/GOTO 表执行 shift、reduce、accept。
5. 语义回调层：多个 `ShiftReduceCallback` 监听同一套 shift/reduce 事件，分别维护语法树、作用域、符号表、类型、常量、结构体、函数和命令树。
6. 结果层：`SemanticResultCallback` 在 accept 前提取最终中间结果，生成 `SemanticAnalysisResult`。

其中最核心的是第 5 层。实验三没有把所有语义动作写在一个大类中，而是把语义事实拆成多个维度：

| 回调 | 职责 |
| --- | --- |
| `TreeBuildCallback` | 根据 shift/reduce 构造语法树节点 |
| `IdentifierScopeCallback` | 在 `{` 和块归约时进入/退出作用域 |
| `TypeBuildCallback` | 为表达式、类型、左值、函数调用等节点绑定类型属性 |
| `ConstantValueBuildCallback` | 为可编译期求值的节点绑定常量属性 |
| `StructSemanticCallback` | 注册结构体表和字段 offset |
| `FunctionSemanticCallback` | 注册函数表、检查参数与返回语句 |
| `IdentifierTableBuildCallback` | 注册变量、检查标识符引用 |
| `CommandBuildCallback` | 生成命令树 |
| `IdentifierConstantStateCallback` | 维护变量常量状态，处理重赋值失效 |
| `PassiveErrorCallback` | 统一处理错误传播 |
| `SemanticResultCallback` | 提取最终语义分析结果 |

这些回调共享同一个 `ShiftReduceSemanticContext`。上下文不是一个简单参数包，而是语义阶段的总控对象，保存语法树栈、命令树栈、类型上下文、常量上下文、标识符表构建器、函数表、结构体表、函数命令段和错误上下文。

#### 2. LALR 分析与语义动作触发

实验三依赖的语法分析器是自底向上的移进-归约分析器。运行时流程可以概括为：

```text
读取当前 token
查看状态栈栈顶
根据 ACTION 表决定动作
  shift：压入新状态，触发 onShift
  reduce：根据产生式归约，触发 onReduce
  accept：触发 beforeAccept/onAccept
  error：进入错误回调
```

归约时机非常适合语法制导翻译。因为一条产生式归约发生时，它的右部子节点已经全部识别完毕，子节点上的类型属性、常量属性、命令子树也已经准备好。父节点只需要根据当前产生式的语义标签，把这些子节点属性组合起来。

例如 `expr -> expr + term` 归约时：

1. 左侧 `expr` 已经有类型属性和命令树。
2. 右侧 `term` 已经有类型属性和命令树。
3. `TypeBuildCallback` 检查二者是否为数值类型，并计算公共运算类型。
4. `ConstantValueBuildCallback` 如果发现两个操作数都是常量，就直接绑定常量结果。
5. `CommandBuildCallback` 再决定是直接装载常量，还是生成左右求值、必要 cast 和 `st_plus_*` 命令。

这体现了本项目的主要设计思路：语义事实先绑定到语法节点，命令翻译器再消费这些事实，而不是每个翻译器临时重新推导全部信息。

#### 3. 语义标签驱动的翻译分发

命令生成的入口是 `CommandBuildCallback`。它在 shift 时调用 token translator，在 reduce 时调用 production translator。

shift 阶段只适合处理局部 token 事实。例如：

| token translator | 设计职责 |
| --- | --- |
| `SimpleStringTokenTranslator` | 为字面量生成装载命令 |
| `LoadIdentifierAddressTokenTranslator` | 为标识符准备地址加载形式 |
| `TypeTokenTranslator` | 类型 token 不直接产生运行命令 |
| `BreakTokenTranslator` | 生成目标未决的 break 跳转 |
| `ContinueTokenTranslator` | 生成目标未决的 continue 跳转 |
| `DoNothingTokenTranslator` | 标点和无命令 token 不产生代码 |

reduce 阶段才适合处理组合语义。`TagStrategyCompose` 根据 `ProgramSemanticTag` 组合选择 translator，例如：

| 语义标签 | translator |
| --- | --- |
| `DECLARATION` | `DeclarationWithoutInitializationTranslator` |
| `DECLARATION + INITIALIZED` | `DeclarationWithInitializationTranslator` |
| `ASSIGNMENT` | `AssignStatementTranslator` |
| `ACCESS` | `ArrayAtExpressionTranslator` |
| `MEMBER_ACCESS` | `MemberAccessTranslator` |
| `NEW_STRUCT` | `NewStructTranslator` |
| `NEW_ARRAY` | `NewArrayTranslator` |
| `FUNCTION + CALL` | `FunctionCallTranslator` |
| `FUNCTION + DEFINITION` | `FunctionDefinitionTranslator` |
| `RETURN` | `FunctionReturnTranslator` |
| `CONDITIONAL` | `IfStatementTranslator` |
| `CONDITIONAL + ELSE_BRANCH` | `IfElseStatementTranslator` |
| `LOOP` | `WhileStatementTranslator` |
| `LOOP + DO_LOOP` | `DoWhileStatementTranslator` |
| `PLUS`、`MINUS` 等 | `InSuffixExpressionTranslator` |
| `LOGICAL_NOT`、`NEGATE` | `UnaryExpressionTranslator` |

这种分发方式比根据孩子个数或产生式字符串判断更稳定。比如 `if-else` 对应的语义是 `CONDITIONAL + ELSE_BRANCH`，即使文法中为了处理悬挂 `else` 拆成 matched/unmatched 两套产生式，只要标签语义一致，就可以复用同一类设计。

#### 4. 中间代码总体设计

本项目生成的是“栈式三地址风格”的中间代码。它不像传统四元式那样显式写出 `t1 = a + b`，而是通过求值栈表达中间值，通过类型化命令表达运算和存取。例如：

```text
load_st_int32_address 0
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
assign_from_st_top_to_addr_int32
```

这些命令的设计原则是：

1. 命令名携带操作类型，例如 `int32`、`float64`、`boolean`、`ref`。
2. 变量槽位用局部 offset 表示，而不是用变量名表示。
3. 函数调用使用函数表 index，而不是使用函数名。
4. 结构体创建使用结构体表 index，字段访问使用字段 offset。
5. 数组和结构体内部位置统一视为 reference，局部变量槽位视为 address。
6. 控制流通过 label 先结构化表示，最后拍平成具体指令下标。

常见命令如下：

| 命令 | 含义 |
| --- | --- |
| `load_st_int32_static 7` | 装载 int32 常量 7 |
| `load_st_float64_static 2.5` | 装载 float64 常量 |
| `load_st_ref_address 0` | 装载 offset=0 的引用变量地址 |
| `st_top_addr_to_val_int32` | 把栈顶地址解引用为 int32 值 |
| `st_top_ref_to_val_boolean` | 把栈顶对象引用解引用为 boolean 值 |
| `st_plus_int32` | int32 加法 |
| `st_less_float64` | float64 小于比较 |
| `st_top_int32_cast_float64` | int32 到 float64 的隐式转换 |
| `assign_from_st_top_to_addr_int32` | 把栈顶值写入局部变量地址 |
| `assign_from_st_top_to_ref_int32` | 把栈顶值写入对象/数组内部引用 |
| `bias_from_st_top_to_ref_int32 1` | 按结构体字段 offset 偏移到 int32 字段 |
| `bias_from_st_top_to_ref_ref` | 按数组下标偏移到引用元素 |
| `new_struct 0` | 创建结构体表 index=0 的对象 |
| `new_array_int32 3 2` | 创建 int32 三维数组，其中二维长度显式给出 |
| `ifn_goto 12` | 栈顶条件为 false 时跳转 |
| `if_goto 3` | 栈顶条件为 true 时跳转 |
| `goto 6` | 无条件跳转 |
| `call 2` | 调用函数表 index=2 的函数 |
| `return` | 函数返回 |

本项目特别区分 address 和 reference。普通局部变量的位置是 address；数组元素、结构体字段的位置是 reference。这个区分直接影响赋值命令：普通变量赋值使用 `assign_from_st_top_to_addr_*`，数组元素或结构体字段赋值使用 `assign_from_st_top_to_ref_*`。

### 三、数据结构设计

#### 1. 语法树节点与属性绑定

语法树节点包括 token 节点和 head 节点。shift 时压入 token 节点，reduce 时根据产生式右部构造 head 节点。语义属性不直接写进节点类本身，而是由上下文维护映射：

| 属性上下文 | 作用 |
| --- | --- |
| `TypeContext` | 记录某个语法节点对应的 `TypeRegister` |
| `ConstantValueContext` | 记录某个语法节点可折叠出的 `ConstantValue` |
| `CommandContext` | 记录命令节点栈 |
| `TreeContext` | 记录语法树节点栈 |

这种设计避免了语法树节点过度膨胀。语法树只表达结构，类型、常量、命令分别由对应模块维护。不同模块可以在同一个 reduce 事件上观察同一个节点，但互不污染内部状态。

#### 2. 类型系统

类型系统的核心类是 `SemanticType`。它记录三件事：

| 字段 | 含义 |
| --- | --- |
| `kind` | 基本种类，如 `BOOLEAN`、`INT32`、`FLOAT64`、`STRUCT`、`NULL` |
| `dimensions` | 数组维度层数 |
| `namedTypeKey` | 结构体类型的稳定名称键 |

这里有几个重要设计点：

第一，数组长度不进入类型本身。`int32[11]` 和 `int32[12]` 都是 `int32[]` 类型，长度是数组创建表达式的运行时信息，而不是静态类型的一部分。

第二，结构体类型通过 `IdentifierKey` 而不是简单字符串比较。这是为了让结构体名在 token 层有稳定身份，减少字节串、编码和显示名之间的混乱。

第三，`null` 是一个独立类型。`null` 可以隐式赋给结构体或数组这类引用类型，但不能赋给 `int32`、`boolean` 等值类型。

第四，`SemanticType` 只描述“是什么类型”，但一次表达式翻译还需要知道更多信息。因此项目又设计了 `TypeRegister`：

| 字段 | 含义 |
| --- | --- |
| `type` | 节点作为值时的结果类型 |
| `instructionType` | 运算指令实际采用的类型 |
| `anchorToken` | 报错定位使用的 token |
| `locationKind` | 左值位置种类，可能是 address 或 reference |

`type` 和 `instructionType` 的区分非常关键。例如：

```text
1 < 2.0
```

这个表达式的结果类型是 `boolean`，但比较指令需要采用 `float64`，因为 `int32` 会先提升为 `float64`。如果只保存一个类型，就无法同时表达“结果是布尔值”和“比较按浮点执行”这两件事。

隐式转换规则由 `TypeConversionRule` 表达：

| 转换 | 是否允许 |
| --- | --- |
| 相同类型 | 允许 |
| `int32 -> float64` | 允许，并需要插入 cast |
| `float64 -> int32` | 不允许 |
| `null -> struct/array` | 允许，不需要 cast |
| `null -> int32/boolean/float64` | 不允许 |
| 非数值类型之间任意转换 | 不允许 |

#### 3. 符号表与作用域

标识符表由 `IdentifierTableBuilder` 维护。它内部是一个作用域栈，每个作用域是一张从 `IdentifierKey` 到 `IdentifierRecord` 的表。进入块时压入新作用域，退出块时弹出作用域并把当前块的记录保存到语法树块节点中。

`IdentifierRecord` 保存：

| 字段 | 含义 |
| --- | --- |
| `no` | 全局唯一记录编号 |
| `offset` | 当前局部作用域中的存储槽位 |
| `typeHeadNode` | 声明类型对应的语法节点 |
| `declaredType` | 声明类型 |
| `lexeme` | 标识符词素 |
| `initialized` | 是否声明时初始化 |
| `ownerFunction` | 所属函数，为空表示全局入口段 |
| `constantValue` | 当前可传播的常量值 |

作用域设计有一个细节：子作用域从父作用域当前 offset 开始分配槽位，兄弟作用域退出后可以复用 offset。测试 `text5-sibling-scope` 专门验证了这一点：两个兄弟块中的变量有不同的记录编号，但可以复用相同局部 offset。这符合栈帧局部存储的设计直觉。

函数参数的注册也复用同一套符号表机制。函数头归约后先登记函数，等函数体块的 `{` 被 shift 时，`IdentifierScopeCallback` 发现当前有 pending function，于是进入函数体作用域，并把形参注册为已初始化的局部变量。

#### 4. 常量属性与常量状态

常量系统使用 `ConstantValue` 表示编译期可确定的值，目前主要覆盖 `boolean`、`int32`、`float64` 等可直接参与折叠的标量。`ConstantValueBuildCallback` 在 reduce 时尝试为节点绑定常量值。

常量系统有两类用途：

1. 表达式常量折叠。例如 `1 + 2 * 3` 直接折叠为 `7`。
2. 控制流常量裁剪。例如 `if (false) { ... }` 不生成 then 分支命令，`while (false)` 不生成循环体命令。

变量常量传播不是简单地“声明时有初值就永远是常量”。`IdentifierConstantStateCallback` 会在变量重新赋值后更新或清空它的常量状态。例如：

```text
int32 a = 1;
a = 2;
int32 b = a + 1;
```

如果 `a` 的重赋值不能保持可确定常量，那么后续使用 `a` 时不能再错误地传播旧值。

#### 5. 函数表与返回流分析

函数由 `FunctionRecord` 表示，包含：

| 字段 | 含义 |
| --- | --- |
| `tableIndex` | 函数表下标 |
| `FunctionSignature` | 函数名和返回类型 |
| `parameters` | 参数列表 |
| `headNode` | 函数头语法节点 |

函数调用的中间代码不直接写函数名，而是写函数表 index，例如 `call 0`。这样中间代码与源码名字解耦，后续如果做解释器或目标代码生成，可以直接根据函数表定位函数段。

函数参数和实参都通过 `SyntaxTreeListIterator` 收集。因为文法中的列表是左递归结构，如果直接按归约顺序读取，顺序很容易反转。`SyntaxTreeListIterator` 用“沿左侧 tail 继续走，把右侧 item 延后发出”的方式，保证最终参数顺序与源码顺序一致。`text48-function-multi-arg-order` 和 `text50-function-nested-struct-array-params` 都验证了这一点。

非 `void` 函数还需要检查是否保证返回。项目用 `FunctionReturnFlowAnalyzer` 根据语义 tag 做路径分析：

| 结构 | 返回判断 |
| --- | --- |
| `return` | 一定返回 |
| 顺序语句 | 任一前序语句保证返回，则后续不可达，不影响已成立结果 |
| 普通块 | 由内部语句序列决定 |
| `if-else` 且条件非常量 | then 和 else 都保证返回才算保证 |
| `if-else` 且条件为常量 | 只检查可达分支 |
| 不带 else 的 `if` | 不能单独保证函数返回 |

因此：

```text
int32 f(boolean c) {
  if (c) return 1;
  else return 2;
}
```

可以通过返回检查，而：

```text
int32 f(boolean c) {
  if (c) return 1;
}
```

会被拒绝。

#### 6. 结构体表与字段布局

结构体由 `StructRecord` 表示，包含结构体表下标、结构体名、字段列表和语法节点。字段由 `StructField` 表示，包含字段名、字段类型和 offset。

字段 offset 按源码声明顺序从 0 开始分配。例如：

```text
struct Point {
    int32 x;
    int32 y;
}
```

会生成：

```text
index=0 name=Point
  offset=0 type=int32 name=x
  offset=1 type=int32 name=y
```

成员访问 `p.y` 的中间代码不是按字段名访问，而是先得到 `p` 的引用，再根据 offset 生成偏移命令：

```text
load_st_ref_address 0
bias_from_st_top_to_ref_int32 1
```

这样结构体字段名只在语义分析阶段用于查表，中间代码阶段只依赖结构体表 index 和字段 offset。

#### 7. 命令树与 label

项目没有在 reduce 时直接把命令追加到最终 `List<String>` 中，而是先构造命令树。原因有三点：

1. label 的最终行号只有在整棵命令树拍平后才知道。
2. `if`、`while`、`do-while` 天然是嵌套结构。
3. `break` 和 `continue` 的目标依赖外层循环，shift 到关键字时还不知道该跳到哪里。

命令树节点主要包括：

| 节点 | 作用 |
| --- | --- |
| `TerminalNode` | 包装一条真实命令 |
| `LabelNode` | 表示一个尚未确定最终行号的 label |
| `HeadNode` | 表示一组子命令节点 |

`CommandNodeRegister` 不仅能把命令注册到外层 builder 中，还携带当前子树中未解决的 `break` 和 `continue` 跳转。循环 translator 归约到完整循环结构时，才把这些未决跳转绑定到当前循环的 continue 目标和 break 目标。

这个设计对嵌套循环尤其重要。内层循环归约时，只绑定内层 body 中尚未解决的跳转；外层循环归约时，只绑定外层剩余的未决跳转。测试 `text19-nested-break-continue-binding` 和 `text20-double-break-binding` 验证了内外层目标不会混淆。

### 四、主要函数代码与设计

本节不大量粘贴代码，而是按核心流程说明主要类和函数的设计。

#### 1. `ProgramSyntaxDemo.buildGrammar0()`

这是 Program 语言的文法入口。它的职责不是执行语法分析，而是用 builder 方式构造 `ProductionSetContext`。每个 `define(...)` 创建一个非终结符定义，每个 `alternate...` 创建候选体，每个 `concatenate...` 追加右部符号，最后通过 `tagLast(...)` 给候选体绑定语义标签。

设计重点有三个：

1. 文法结构和 token 类型直接对接，不再从外部文本临时解析。
2. 每条关键候选体都带语义 tag，为后续类型构造、常量折叠和命令翻译提供稳定分发依据。
3. 通过 matched/unmatched 结构解决悬挂 `else`，使语法层先消除歧义，语义层不需要猜测 `else` 归属。

#### 2. `SemanticDemo.buildShiftReduceTestRegister()`

这个函数负责组装实验三真正使用的语义回调链。顺序是设计的一部分：

1. 先构造语法树，因为后续模块需要访问当前归约节点。
2. 再处理作用域，因为标识符声明和使用依赖可见性。
3. 再构造类型和常量属性。
4. 再处理结构体、函数、标识符表。
5. 再收集最终结果和命令树。
6. 最后处理常量状态和错误传播。

这里的关键不是“回调越多越好”，而是把不同语义事实拆开维护。类型模块不负责输出命令，命令模块不负责重新建立符号表，函数模块不负责结构体字段 offset。每个模块只处理自己能明确负责的事情。

#### 3. `TypeBuildCallback`

`TypeBuildCallback` 是类型系统的核心。它用 `ProductionTagStrategy<TypeRule>` 把语义标签映射到类型规则。

主要类型规则包括：

| 规则 | 设计说明 |
| --- | --- |
| `TYPE_DECLARATION` | 基本类型 token 转为 `SemanticType` |
| `ARRAY_TYPE` | 在基础类型上追加数组维度 |
| `NAMED_STRUCT_TYPE` | 把结构体类型名转为结构体类型 |
| `DECLARED_IDENTIFIER` | 声明节点继承类型，并标记为 address |
| `IDENTIFIER_REFERENCE` | 查符号表，得到变量声明类型和 address |
| `ARRAY_ACCESS` | 检查左侧为数组、下标为 `int32`，结果为 reference |
| `MEMBER_ACCESS` | 检查左侧为结构体、字段存在，结果为 reference |
| `FUNCTION_CALL` | 查函数表，结果为函数返回类型 |
| `NEW_STRUCT` | 检查结构体已声明，结果为结构体引用 |
| `NEW_ARRAY` | 检查元素类型和维度，结果为数组引用 |
| `BOOLEAN_BINARY` | 要求左右都是 boolean |
| `NUMERIC_BINARY` | 要求左右都是数值，计算公共指令类型 |
| `RELATION` | 结果为 boolean，指令类型为公共数值类型 |
| `EQUALITY` | 支持同类型比较和数值比较 |
| `ASSIGNMENT` | 赋值语句整体沿用左值类型 |

`TypeBuildCallback` 的重点是提前把语义事实绑定到节点。例如数组访问 `a[i]` 在类型阶段就会被标记为 `LocationKind.REFERENCE`，后续赋值翻译器只需要读取这个位置种类，就知道应该使用 `assign_from_st_top_to_ref_*`。

#### 4. `IdentifierTableBuildCallback` 与 `IdentifierScopeCallback`

`IdentifierScopeCallback` 负责块作用域的进入和退出。进入 `{` 时，如果不是结构体体，就创建新作用域；归约到完整 block 时，弹出作用域并把局部变量记录保存到 block 节点中。

`IdentifierTableBuildCallback` 负责两类事情：

1. 标识符使用：检查当前可见作用域中是否存在该标识符。
2. 标识符声明：检查当前作用域是否重复声明，读取声明类型，登记 `IdentifierRecord`。

这两个回调分开是合理的：作用域的生命周期由块结构决定，而标识符登记由声明产生式决定。把二者拆开可以避免一个类同时理解所有语句结构。

#### 5. `StructSemanticCallback`

`StructSemanticCallback` 在 `STRUCT_DECL` 归约时注册结构体。它通过 `StructFieldStepper` 和 `SyntaxTreeListIterator` 收集字段列表，逐个检查：

1. 字段类型不能是 `void`。
2. 字段名不能重复。
3. 字段结构体类型必须已经声明。
4. 字段 offset 按源码顺序递增。

结构体创建和成员访问都不直接依赖源码名称。`new Point()` 生成 `new_struct 0`，`p.y` 生成带 offset 的 `bias_from_st_top_to_ref_*`。这使结构体表成为源码名称和中间代码之间的稳定桥梁。

#### 6. `FunctionSemanticCallback`

`FunctionSemanticCallback` 在函数头归约时注册函数记录，在 `return` 归约时检查返回语句，在函数调用归约时检查实参。

函数头处理包括：

1. 检查函数名是否重复。
2. 解析返回类型，包括 `void`。
3. 收集参数列表并保持源码顺序。
4. 检查参数不能为 `void`。
5. 检查参数名不能重复。
6. 登记函数表，并标记 pending function，等待函数体块进入时注册形参。

函数调用检查包括：

1. 函数必须先定义再调用。
2. 实参数量必须等于形参数量。
3. 每个实参类型必须可赋给对应形参类型。

返回语句检查包括：

1. `return` 只能出现在函数体内部。
2. 非 `void` 函数必须返回值。
3. `void` 函数不能返回值。
4. 返回值类型必须可赋给函数返回类型。

#### 7. `FunctionReturnFlowAnalyzer`

函数返回路径检查不是简单地搜索是否出现过 `return`。如果只看是否出现 `return`，下面的函数会被错误接受：

```text
int32 f(boolean c) {
  if (c) {
    return 1;
  }
}
```

实际上当 `c` 为 false 时函数没有返回。因此项目设计了 `FunctionReturnFlowAnalyzer`，按语义标签分析所有可达路径是否保证返回。

它的设计亮点是支持常量条件。如果条件已经在常量折叠阶段确定为 true 或 false，返回流分析只检查实际可达的分支。例如：

```text
int32 f() {
  if (true) {
    return 1;
  } else {
    int32 x;
  }
}
```

此时只需要 then 分支保证返回即可。

#### 8. `AssignStatementTranslator`

赋值翻译器是“类型属性”和“命令生成”协作的典型例子。它不重新分析左右两边是什么表达式，而是读取 `TypeBuildCallback` 已经绑定好的属性：

1. 读取左值类型和右值类型。
2. 调用赋值兼容性检查。
3. 先生成左值定位命令。
4. 再生成右值求值命令。
5. 如果需要 `int32 -> float64`，插入栈顶 cast 命令。
6. 根据左值位置是 address 还是 reference，选择写回命令。

例如：

```text
float64 x;
x = 1;
```

会在写回前插入：

```text
st_top_int32_cast_float64
```

而结构体字段赋值：

```text
p.x = 1;
```

会使用：

```text
assign_from_st_top_to_ref_int32
```

不是普通局部变量的 `assign_from_st_top_to_addr_int32`。

#### 9. `InSuffixExpressionTranslator`

中缀表达式翻译器处理算术、逻辑、关系和相等运算。它的基本流程是：

1. 先询问 `ConstantCommandSupport` 当前表达式是否已经有常量结果。如果有，直接生成装载常量命令。
2. 读取左右操作数类型。
3. 根据运算符类别检查类型是否合法。
4. 计算指令类型。
5. 生成左操作数命令，必要时插入 cast。
6. 生成右操作数命令，必要时插入 cast。
7. 生成最终运算命令。

例如 `int32 + float64` 的指令类型是 `float64`，左操作数会插入 `st_top_int32_cast_float64`。而 `boolean + int32` 会在类型检查阶段或翻译阶段被拒绝。

#### 10. 控制流 translator

`IfStatementTranslator` 把不带 else 的 if 翻译为：

```text
condition
ifn_goto ifEnd
then
ifEnd:
```

`IfElseStatementTranslator` 把 if-else 翻译为：

```text
condition
ifn_goto elseStart
then
goto elseEnd
elseStart:
else
elseEnd:
```

如果条件在编译期已经是常量，这两个 translator 会裁剪不可达分支。但项目仍然保留一个重要约束：死分支中的非法 `break/continue` 不能被静默吞掉。相关未决跳转会继续通过 `CommandNodeRegister` 传递，最终在顶层或错误回调中被诊断。

`WhileStatementTranslator` 生成首部判断循环：

```text
whileStart:
condition
ifn_goto whileEnd
body
goto whileStart
whileEnd:
```

当条件恒为 false 时，while 循环体整体省略。

`DoWhileStatementTranslator` 生成先执行后判断循环：

```text
whileStart:
body
beforeTest:
condition
if_goto whileStart
whileEnd:
```

当条件恒为 false 时，do-while 仍然保留一次循环体，因为语言语义要求先执行一次。

#### 11. `FunctionDefinitionTranslator` 与 `FunctionCallTranslator`

函数定义归约时，`FunctionDefinitionTranslator` 不把函数体命令混入全局入口命令，而是把函数体拍平成独立命令段，注册到 `FunctionCommandSegmentContext`。函数定义自身返回占位节点。

因此最终 `SemanticAnalysisResult` 分成：

| 结果字段 | 含义 |
| --- | --- |
| `entryCommands` | 程序入口段命令 |
| `functionSegments` | 函数命令段，每段绑定一个 `FunctionRecord` |
| `structTable` | 结构体表 |
| `identifierRecords` | 所有标识符记录 |

函数调用翻译器先按源码顺序生成实参求值命令，再生成 `call index`。这个 index 来自函数表，而不是函数名文本。

#### 12. `NewArrayTranslator` 与 `MemberAccessTranslator`

数组创建翻译器的设计重点是区分“总维度”和“显式长度维度”。例如：

```text
new int32[11][12][]
```

类型是三维数组，但只有前两维长度显式给出，因此命令为：

```text
new_array_int32 3 2
```

成员访问翻译器的设计重点是字段 offset。它先生成左侧对象引用，再通过结构体表找到字段 offset，最后生成：

```text
bias_from_st_top_to_ref_<fieldType> <offset>
```

这说明结构体成员访问在中间代码层面已经脱离字段名，变成“引用 + 固定偏移”。

## 第3章 程序测试

### 一、测试用例的设计

测试用例位于 `src/main/resources/program-tests`。当前共有 50 个 `.txt` 程序用例，测试入口是 `AppTest.testProgramSemanticCases()`，内部调用 `ProgramSyntaxTestRunner.run()` 跑完整链路。

测试框架的判断规则为：

1. 文件名包含 `invalid` 的用例期望被拒绝。
2. 文件名不包含 `invalid` 的用例期望被接受。
3. 如果执行中抛出异常，视为拒绝。
4. 如果 `ErrorContext` 中存在错误，也视为拒绝。
5. 合法程序必须成功生成 `SemanticAnalysisResult`。

测试覆盖面如下：

| 类别 | 代表用例 | 测试重点 |
| --- | --- | --- |
| 综合语法 | `text1`、`text2`、`text3` | 基础声明、表达式、数组、循环、悬挂 else |
| 作用域 | `text5-sibling-scope` | 兄弟作用域 offset 复用和记录编号区分 |
| 类型错误 | `text7`、`text8`、`text9`、`text10`、`text11`、`text13` | 条件、数组下标、赋值、逻辑、算术、收窄转换 |
| 隐式转换 | `text12`、`text14` | `int32 -> float64` cast 插入位置 |
| break/continue | `text15` 到 `text20` | while/do-while/嵌套循环/循环外非法跳转 |
| 常量优化 | `text21` 到 `text30` | 常量折叠、传播、失效、常量条件裁剪 |
| 函数 | `text31` 到 `text40`、`text48`、`text50` | 返回值、调用、参数顺序、返回路径、函数段拆分 |
| 结构体 | `text41` 到 `text44`、`text49`、`text50` | 结构体表、字段 offset、空引用、字段错误 |
| 数组 | `text45` 到 `text47`、`text49`、`text50` | 数组创建维度、尾部省略、多维嵌套访问 |

测试不仅检查“是否接受”，还直接检查中间代码细节。例如：

- `assertDanglingElseControlFlow` 检查外层/内层 `ifn_goto` 目标是否正确。
- `assertWideningCastPlacement` 检查 `int32` 到 `float64` 的 cast 是否出现在正确位置。
- `assertNestedLoopBinding` 检查内层 `break/continue` 是否绑定到内层循环。
- `assertFunctionSegmentation` 检查函数体命令是否没有混入全局入口段。
- `assertStructDeclarationAndAccess` 检查结构体字段 offset 和 `new_struct` index。
- `assertArrayCreationInstructions` 检查 `new_array_* totalDimensions specifiedDimensions`。
- `assertFunctionStructAndArrayParameters` 检查结构体数组作为函数参数时的命令顺序。

这种测试设计更适合中间代码生成实验。因为很多错误不会导致程序被拒绝，却会导致中间代码语义错误，例如跳转目标错一行、函数实参顺序反了、结构体字段 offset 错了。如果只检查“测试通过/失败”，无法发现这些问题。

#### 2. 常量折叠测试分析

用例 `text21-constant-folding`：

```text
{
int32 a = 1 + 2 * 3;
boolean ok = !(false || false);
}
```

生成的核心命令为：

```text
load_st_int32_static 7
load_st_boolean_static true
```

可以看到，`1 + 2 * 3` 没有生成乘法和加法命令，而是直接装载常量 `7`；`!(false || false)` 也直接折叠为 `true`。符号表中 `a` 和 `ok` 的 `constant` 字段分别记录为 `7` 和 `true`。

该用例证明：

1. 表达式优先级正确，先乘后加。
2. 常量属性能沿表达式树向上传播。
3. 命令生成阶段能识别常量属性并直接生成常量装载命令。

#### 3. 隐式类型转换测试分析

用例 `text12-int32-to-float64-implicit-cast` 验证 `int32` 到 `float64` 的拓宽转换。测试断言要求出现如下顺序：

```text
load_st_float64_address 1
load_st_int32_address 0
st_top_addr_to_val_int32
st_top_int32_cast_float64
assign_from_st_top_to_addr_float64
```

这说明赋值时不是简单地把 `int32` 值写进 `float64` 变量，而是在写回前显式插入 cast。相反，用例 `text13-float64-to-int32-invalid` 被拒绝，说明收窄转换没有被错误接受。

#### 4. 控制流测试分析

`text2` 验证悬挂 `else` 绑定到最近的 `if`。测试中外层 `if` 的 false 跳转、内层 `if` 的 false 跳转、then 分支跳过 else 的 `goto` 都被精确断言。结果说明 matched/unmatched 文法拆分生效，中间代码也没有把 `else` 错误绑定到外层 `if`。

`text15-continue-in-while` 验证 while 中的 `continue` 跳回条件检查点。  
`text16-continue-in-do-while` 验证 do-while 中的 `continue` 跳到条件检查点，而不是循环体开头。  
`text19-nested-break-continue-binding` 验证嵌套循环中内层跳转目标不会绑定到外层。  
`text20-double-break-binding` 验证不同层级 break 的出口不同。

这些用例共同证明了“未决跳转延迟绑定”的设计是必要的。`break` 和 `continue` 在 shift 阶段无法知道目标，只能先携带未决 label；当归约到完整循环结构时，循环 translator 才有足够信息完成绑定。

#### 5. 结构体测试分析

用例 `text41-struct-declare-and-access`：

```text
struct Point {
    int32 x;
    int32 y;
}
{
Point p;
p = new Point();
p.x = 1;
p.y = p.x + 2;
}
```

结构体表输出为：

```text
index=0 name=Point
  offset=0 type=int32 name=x
  offset=1 type=int32 name=y
```

关键命令包括：

```text
new_struct 0
bias_from_st_top_to_ref_int32 0
bias_from_st_top_to_ref_int32 1
st_top_ref_to_val_int32
assign_from_st_top_to_ref_int32
```

分析可知：

1. `new Point()` 被翻译为 `new_struct 0`，说明对象创建依赖结构体表 index。
2. `p.x` 使用 offset 0，`p.y` 使用 offset 1，说明字段布局正确。
3. 字段读取时需要从 reference 解引用为值。
4. 字段写入时使用 reference 写回命令，而不是 address 写回命令。

非法用例 `text43-struct-duplicate-field-invalid` 和 `text44-struct-missing-field-invalid` 分别验证重复字段和不存在字段会被拒绝。

#### 6. 数组测试分析

数组创建相关用例验证三种维度情况：

| 用例 | 源码含义 | 关键命令 |
| --- | --- | --- |
| `text45-array-create-fully-specified` | 三维数组，三维都给长度 | `new_array_int32 3 3` |
| `text46-array-create-tail-omitted-one` | 三维数组，后 1 维省略 | `new_array_int32 3 2` |
| `text47-array-create-tail-omitted-two` | 三维数组，后 2 维省略 | `new_array_int32 3 1` |

这说明项目正确区分了类型维度和创建时显式长度维度。类型系统知道这是几维数组，命令系统再记录实际有几个维度长度已经入栈。

非法用例 `text8-array-index-boolean-invalid` 被拒绝，说明数组下标必须是 `int32`，不能是 `boolean`。

#### 7. 函数测试分析

用例 `text50-function-nested-struct-array-params` 覆盖了结构体、数组、嵌套数组和函数参数。程序中声明了结构体 `Student`，以及三个函数：

```text
boolean readStudent(Student s)
boolean readStudentArray(Student[] students, int32 index)
boolean pickFromSchool(Student[] direct, Student[][] groups, Student one)
```

报告显示函数表 index 分别为 0、1、2。入口命令中调用 `pickFromSchool` 生成：

```text
call 2
```

`readStudentArray` 函数段中，访问 `students[index]` 并调用 `readStudent` 的命令为：

```text
load_st_ref_address 0
load_st_int32_address 1
st_top_addr_to_val_int32
bias_from_st_top_to_ref_ref
st_top_ref_to_val_ref
call 0
return
```

这段命令说明：

1. `students` 是引用类型参数，先加载其地址。
2. `index` 是 int32 参数，需要从地址取值。
3. 数组索引定位到数组元素 reference。
4. 元素本身是结构体引用，因此再取值为 ref。
5. 调用函数表 index 0 的 `readStudent`。

该测试同时验证了参数顺序、实参求值顺序、结构体数组元素访问和函数段拆分。

#### 8. 错误诊断测试分析

18 个非法用例全部按预期被拒绝，覆盖：

- 条件表达式不是 `boolean`。
- 数组下标不是 `int32`。
- `boolean` 赋给 `int32`。
- 逻辑运算使用非布尔操作数。
- 算术运算使用布尔操作数。
- `float64` 赋给 `int32`。
- 循环外 `break` 或 `continue`。
- 非 `void` 函数缺少返回。
- `void` 函数返回值。
- 函数外 `return`。
- 函数实参数量错误。
- 常量死分支中的非法 `break/continue`。
- 非 `void` 函数只有条件返回。
- 结构体字段重复。
- 结构体字段不存在。

其中部分错误会写入 `ErrorContext`，部分通过异常路径拒绝。当前测试也显式检查了这两种错误路径。这说明错误处理虽然还有统一化空间，但从验收角度看已经能稳定拒绝非法程序。

## 第4章 实验总结

### 一、实验总结

本次实验完成了一套较完整的语法制导翻译和中间代码生成系统。项目以 LALR 移进-归约分析器为驱动，通过多个语义回调并行维护语法树、符号表、类型属性、常量属性、函数表、结构体表和命令树。最终输出不只是一串命令，还包括入口命令段、函数命令段、结构体表和标识符记录，具备较好的可审计性。

本项目最重要的设计成果有四点。

第一，语义标签机制降低了文法和语义动作之间的脆弱耦合。语义模块不直接依赖产生式字符串，而是依赖 `ProgramSemanticTag` 所表达的语义意图。这样后续调整文法结构时，只要语义标签保持一致，很多语义逻辑就能继续复用。

第二，类型系统区分了结果类型、指令类型和位置种类。`TypeRegister` 中的 `type`、`instructionType` 和 `LocationKind` 解决了数值提升、关系表达式、数组元素、结构体字段和赋值写回等问题。如果只保存一个简单类型，很多中间代码命令都会难以正确选择。

第三，命令系统先构造命令树，再统一拍平。这个设计使 label、跳转目标、嵌套控制流和 `break/continue` 延迟绑定都能自然表达。尤其是 `break/continue`，只有归约到完整循环结构时才知道目标，因此未决跳转列表是必要设计。

第四，测试报告不仅验证接受/拒绝，还输出源程序、中间代码、结构体表、函数段、局部变量表和错误列表。这样可以直接检查某个语义规则是否真正落到了中间代码中，例如字段 offset、函数表 index、数组维度、cast 位置和跳转目标。

从最终测试结果看，50 个 Program 全链路用例全部符合预期，其中 32 个合法程序成功生成中间代码，18 个非法程序被拒绝。测试覆盖了基础表达式、类型检查、控制流、常量优化、函数、结构体、数组和复杂嵌套访问，说明当前实现已经达到实验三要求，并且具有继续扩展到解释执行或目标代码生成的基础。

### 二、心得体会

通过本次实验，可以明显感受到语法制导翻译的难点不只是“在归约时写动作”。真正困难的是如何设计清楚各类语义事实之间的边界：哪些事情属于类型系统，哪些属于符号表，哪些属于函数管理，哪些属于命令生成。如果这些逻辑混在一起，短期也许能跑通几个例子，但很快会在函数、数组、结构体和控制流组合时变得难以维护。

项目中最有价值的经验是“先绑定事实，再生成命令”。例如赋值语句并不直接重新判断左值是什么，而是读取类型阶段已经绑定好的 `LocationKind`；函数调用并不重新解析参数树，而是复用列表迭代器和函数表；结构体成员访问不再保留字段名到命令阶段，而是在语义阶段转换为字段 offset。这种分层让每个模块的职责更清楚。

另一个体会是测试必须深入到中间代码细节。编译器前端中很多错误并不会表现为“程序无法通过”，而是表现为生成了错误但看似合理的中间代码。例如参数顺序反转、`continue` 跳错位置、结构体 offset 错一位、函数体命令混进全局入口段，这些都必须通过命令级断言才能发现。当前测试体系把这些细节写入 Markdown 报告，对定位问题非常有帮助。

后续可以继续改进的方向包括：

1. 将更多当前通过异常拒绝的语义错误统一写入 `ErrorContext`，使错误报告更一致。
2. 在现有中间代码基础上增加解释器，验证命令不仅结构正确，而且运行结果正确。
3. 增加变量使用前初始化检查、不可达代码检查等数据流分析。
4. 进一步完善字符串、字符类型的常量折叠和运行语义。
5. 对语法表和词法表缺失时的提示做得更友好，必要时自动重建。

总体而言，本实验不仅实现了语法制导翻译和中间代码生成，也完成了一个可测试、可扩展、结构清晰的编译前端设计实践。
