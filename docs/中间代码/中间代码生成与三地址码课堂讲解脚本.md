# 中间代码生成与三地址码课堂讲解脚本

这份文档是给汇报时直接使用的讲稿。目标是：你照着打开文件、照着指代码、照着念，就能把“我们编译器怎样实现中间代码生成和三地址码”讲清楚。

建议演示时长：15 到 25 分钟。

讲解核心顺序：

```text
程序入口
  -> shift/reduce 事件
  -> 语义回调链
  -> 类型/常量/符号表准备
  -> CommandBuildCallback 生成命令包
  -> translator 生成命令树
  -> CommandFactory 生成三地址码命令对象
  -> label / break / continue 延迟绑定
  -> 函数段隔离
  -> flatten 得到最终中间代码
  -> ThreeAddressCodePrinter 和测试报告展示
```

## 2. 讲语法分析主循环：中间代码由 shift/reduce 驱动

### 2.1 打开 `ShiftReducePhaserImpl.java`

指向 `phase(...)` 方法。

你要说：

> 这是整个 LR 分析的主循环。它每次取当前 token 和状态栈栈顶，然后查 ACTION 表。如果查到 shift，就调用 `onShift`；如果查到 reduce，就调用 `onReduce`；如果是 accept，就先 `beforeAccept` 再 `onAccept`。

指向这几处：

```text
element.isShift()
element.isReduce()
element.isAccept()
context.onShift(...)
context.onReduce(...)
context.beforeAccept(...)
```

你要说：

> 中间代码生成不是最后统一遍历源码，而是被这几个事件驱动。shift 读进 token，命令模块就生成 token 级命令包；reduce 归约产生式，命令模块就把孩子命令包合成父命令包。

### 2.2 指向 `onShift(...)`

你要说：

> 这里的 `onShift` 很短，只是调用 `context.onShift(nextStatus, token)`。真正的语义动作不写在语法分析器里，而是交给 `ShiftReduceSemanticContext` 分发。

### 2.3 指向 `onReduce(...)`

你要说：

> reduce 时先通过产生式编号拿到 `SimpleGrammarProduction`。如果是 accept，会走 `beforeAccept`，这是我们最后收集中间代码的位置；如果不是 accept，就走普通 `context.onReduce(production)`。

老师可能问：为什么中间代码要嵌入 reduce，而不是最后遍历 AST？

回答：

> 因为我们的语义属性本来就是自底向上构造的。每次 reduce 正好拿到当前产生式的所有孩子属性，适合做语法制导翻译。这样表达式、语句、控制流、函数定义都能在归约时局部生成命令片段，不需要后面再写一套遍历器。

### 3.1 打开 `ShiftReduceSemanticContext.java`

指向字段区。

你要说：

> 这个类是整条语义链路共享的上下文。它里面有语法树栈 `treeContext`，命令栈 `commandContext`，函数命令段上下文 `functionCommandSegmentContext`，还有类型上下文、常量上下文、标识符表、结构体表、函数表和命令工厂。

照着点这些字段：

```text
treeContext
commandContext
functionCommandSegmentContext
commandFactory
typeContext
constantValueContext
identifierRecords
functionContext
structContext
```

你要说：

> 所以中间代码生成读到的类型、常量、变量 offset、函数编号、结构体字段 offset，全部来自这里。

### 3.2 指向 `onShift`、`onReduce`、`beforeAccept`

你要说：

> 这三个方法内部都调用 `invokeNext`。`invokeNext` 会把同一个事件传给注册表里的每个回调。也就是说，一次 reduce 不是只有命令生成器执行，而是建树、类型、常量、符号表、函数表、结构体表、命令生成都按顺序执行。

### 3.3 打开 `SemanticDemo.java`

指向 `buildShiftReduceTestRegister()`。

你要说：

> 这里定义了测试时的语义回调顺序。先建语法树，然后处理作用域、类型、常量、结构体、函数、标识符表，再收集语义结果和生成命令。

指向：

```text
TreeBuildCallback
TypeBuildCallback
ConstantValueBuildCallback
StructSemanticCallback
FunctionSemanticCallback
IdentifierTableBuildCallback
SemanticResultCallback
CommandBuildCallback
IdentifierConstantStateCallback
PassiveErrorCallback
```

你要说：

> 对中间代码生成来说，这个顺序很重要。`CommandBuildCallback` 生成命令时，前面的类型、常量、结构体、函数和标识符信息已经准备好了。

老师可能问：`SemanticResultCallback` 为什么看起来在 `CommandBuildCallback` 前面？

回答：

> 普通 reduce 时它不收最终结果。它真正收结果是在 accept 前的 `beforeAccept`。这个阶段命令栈已经有完整顶层 register，可以 flatten。测试能通过也说明最终结果拿到的是完整命令树。

## 4. 讲中间代码生成入口：`CommandBuildCallback`

### 4.1 打开 `CommandBuildCallback.java`

指向类声明：

```text
public class CommandBuildCallback extends BuildStackContextCallback<CommandNodeRegister>
```

你要说：

> 这就是中间代码生成的入口类。它继承了一个通用的栈式构造回调，类型参数是 `CommandNodeRegister`。也就是说，它维护的不是语法树节点栈，而是命令 register 栈。

### 4.2 打开 `BuildStackContextCallback.java`

指向 `onShift(...)`。

你要说：

> 这个通用类体现了我们语法制导翻译的基本模型。shift 时，调用 `instanceNodeOnShift` 生成一个属性对象，然后压栈。

指向 `onReduce(...)` 和 `reduceProduction(...)`。

你要说：

> reduce 时，根据产生式右部长度，从栈里弹出对应数量的孩子，顺序恢复好之后调用 `instanceNodeOnReduce`，得到父节点属性，再压回栈。

重点念：

> 这套机制对语法树构造和命令构造都能复用。语法树那边压的是 `ShiftReduceSyntaxTreeNode`，命令生成这边压的是 `CommandNodeRegister`。

### 4.3 回到 `CommandBuildCallback.java`

指向 `instanceNodeOnShift(...)`。

你要说：

> shift 时，它根据 token 类型从 `shiftStrategies` 找 token translator。比如整数常量找 `SimpleStringTokenTranslator`，break 找 `BreakTokenTranslator`，continue 找 `ContinueTokenTranslator`。

指向 `instanceNodeOnReduce(...)`。

你要说：

> reduce 时，它根据产生式从 `reduceStrategies` 找 command translator。比如赋值找 `AssignStatementTranslator`，if 找 `IfStatementTranslator`，while 找 `WhileStatementTranslator`。所以 `CommandBuildCallback` 是调度器，它自己不写具体语句的翻译规则。

老师可能问：`CommandNodeRegister` 是什么？

回答：

> 它是命令生成的中间包。它不仅能把命令节点注册到外层 builder，还能携带尚未绑定的 `break/continue`。所以它比普通命令列表更强，能服务控制流回填和错误诊断。


你要说：

> 字面量 token 会交给 `SimpleStringTokenTranslator`，它会生成静态加载命令，例如 `load_st_int32_static 1`。

```text

```

你要说：

> 标识符 token 当前先走 `LoadIdentifierAddressTokenTranslator`，但这个 translator 返回的是占位。因为单个标识符 token 还不能确定是变量使用、声明名、函数名还是类型名。真正的变量地址加载要等归约成 `IDENTIFIER + USE` 后由 `IdentifierUseTranslator` 完成。

你要说：

> break 和 continue 在 token 阶段就能确定是一条控制跳转，所以会立即生成一个目标未知的 goto，并放到未决 break 或未决 continue 列表里。

### 6.1 打开 `TagStrategyCompose.java`

指向 `stringCommand()`。

你要说：

> 这个方法就是中间代码产生式翻译器的分发表。项目不是用产生式字符串硬编码，而是用语义标签 `ProgramSemanticTag` 分派。

老师可能问：为什么叫语法制导翻译？

回答：

> 因为每个产生式归约时，都会根据这个产生式的语义标签和孩子属性，生成该语法结构对应的中间代码片段。翻译动作和语法归约同步发生。

## 7. 讲表达式生成：`b + 1` 怎么变成三地址码

### 7.1 打开 `InSuffixExpressionTranslator.java`

指向开头的 `constantOrNull`。

你要说：

> 表达式翻译第一步先看能不能常量折叠。如果当前语法节点已经被 `ConstantValueBuildCallback` 绑定了常量值，就直接生成一条 `load_st_*_static`，不再生成左右操作数和运算命令。

指向：

```text
leftType
rightType
inferInstructionType(...)
```

你要说：

> 如果不能折叠，就读取左右操作数类型，并根据运算符类别推断实际执行指令的类型。例如 `int32 + float64` 要按 `float64` 运算，关系表达式结果虽然是 boolean，但比较指令可能是 `st_less_float64`。

指向：

```text
children[0].register(thisBuilder)
children[2].register(thisBuilder)
stTopCast
stOperator
```

你要说：

> 这里就是表达式命令生成的顺序：先注册左操作数命令，必要时 cast；再注册右操作数命令，必要时 cast；最后追加运算命令，比如 `st_plus_int32`。

### 7.2 你可以举例念

照读：

> 比如 `b + 1`，如果 `b` 是 int32，`1` 是 int32，那么左边先生成 `load_st_int32_address <b_offset>` 和 `st_top_addr_to_val_int32`，右边生成 `load_st_int32_static 1`，最后生成 `st_plus_int32`。这里没有显式临时变量 t1，而是用栈顶隐式保存中间结果，所以我们叫它栈式三地址风格。

## 8. 讲赋值生成：`a = b + 1;`

### 8.1 打开 `AssignStatementTranslator.java`

指向：

```text
targetType = TypeAttributes.childType(context, 0)
sourceType = TypeAttributes.childType(context, 2)
```

你要说：

> 赋值翻译先从类型属性里读取左侧目标类型和右侧源类型。这些类型不是在这里临时推断的，而是前面的 `TypeBuildCallback` 已经绑定到语法树节点上的。

指向：

```text
SemanticDiagnostics.requireAssignable(...)
```

你要说：

> 然后检查右侧能不能赋给左侧，比如 `int32` 可以隐式转成 `float64`，但 `float64` 不能随便转回 `int32`。

指向：

```text
children[0].register(builder)
children[2].register(builder)
```

你要说：

> 命令生成顺序是先生成左值定位命令，再生成右值求值命令。这样最后写回时，栈里还保留着目标位置。

指向：

```text
requiresImplicitCast
stTopCast
```

你要说：

> 如果需要隐式类型转换，就在写回前对栈顶值插入 cast 命令。

指向：

```text
LocationKind.REFERENCE
assignFromStTopToRef
assignFromStTopToAddr
```

你要说：

> 最后根据左值位置种类选择写回命令。普通变量是 `ADDRESS`，用 `assign_from_st_top_to_addr_*`；数组元素和结构体字段是 `REFERENCE`，用 `assign_from_st_top_to_ref_*`。

### 8.2 你要总结这个例子

照读：

> 所以 `a = b + 1;` 的中间代码生成不是一句话完成，而是左值 translator 负责定位 `a`，表达式 translator 负责计算 `b + 1`，赋值 translator 负责类型检查、必要 cast 和最终写回。它们通过 `CommandNodeRegister` 接力组合成完整命令树。

## 9. 讲命令工厂：三地址码文本在哪里生成

### 9.1 打开 `TypedStringCommandFactory.java`

指向：

```text
loadLiteral
loadIdentifierAddress
loadConstant
stOperator
stTopAddrToVal
stTopRefToVal
assignFromStTopToAddr
assignFromStTopToRef
stTopCast
ifGoto

```

你要说：

> translator 不直接拼字符串，而是调用 `CommandFactory`。具体字符串格式集中在 `TypedStringCommandFactory`。比如加载变量地址生成 `load_st_<type>_address <offset>`，运算生成 `st_<operator>_<type>`，赋值生成 `assign_from_st_top_to_addr_<type>` 或 `assign_from_st_top_to_ref_<type>`。

指向 `ifGoto`、`ifnGoto`、`gotoCommand`。

你要说：

> 跳转命令这里返回的不是固定字符串，而是 `StringSupplierCommand`。它等到打印时才读取 label 的 index，这就是我们避免手工回填字符串的小设计。

### 9.2 讲 `CommandDataType`

可以切到 `CommandDataType.java`。

你要说：

> 命令层类型和源语言类型不完全一样。结构体和数组在源语言里有不同类型，但命令层统一编码为 `ref`。`forStorage` 用于存储类别，引用类型会变成 `REF`；`forValue` 用于标量运算，引用类型不能当普通值运算。这避免了类型层混乱。

## 10. 讲命令树和 flatten：为什么不是直接 List

### 10.1 打开 `LabelNode.java`

指向：

```text
label.setIndex(result.size())
```

你要说：

> `LabelNode` 不输出命令。它在 flatten 时把当前命令列表长度写进 label。这样 label 就知道自己对应第几条指令。

### 10.2 打开 `StringSupplierCommand.java`

指向 `toString()`。

你要说：

> 跳转命令打印时才调用 supplier，读取 label 当前 index。所以 label 的 index 可以在 flatten 过程中确定，跳转命令不需要回头修改字符串。

### 10.3 打开 `CommandSegmentSupport.java`

指向 `flatten(...)`。

你要说：

> 最终把命令 register 变成线性命令列表的是这里。它先让 register 注册命令节点，再递归调用每个节点的 `flat` 方法。`TerminalNode` 会加入命令，`LabelNode` 只设置编号，`HeadNode` 会递归展开孩子。

老师可能问：为什么要这么麻烦？

回答：

> 因为 if、while、break、continue、函数段隔离和常量剪枝都要求中间代码先保留结构。如果一开始直接追加字符串，后面跳转目标和死分支处理会非常麻烦。

## 11. 讲 if / while / break / continue

### 11.1 打开 `IfStatementTranslator.java`

指向：

```text
ConstantConditionSupport.booleanValue
MergedCommandNodeRegister
PlaceholderNodeRegister
```

你要说：

> if 翻译先检查条件是不是编译期常量。如果是 `if(true)`，只保留 then 分支；如果是 `if(false)`，输出空命令。但这里用了 `MergedCommandNodeRegister`，它虽然不输出死分支命令，却会保留死分支里的未决 break/continue，用于后续错误诊断。

指向：

```text
ifnGoto(ifEndLabel)
LabelNode(ifEndLabel)
```

你要说：

> 普通 if 会生成条件命令，然后 `ifn_goto ifEnd`，再生成语句体，最后放一个 `LabelNode` 作为 if 结束位置。

### 11.2 打开 `IfElseStatementTranslator.java`

指向：

```text
ifnGoto(elseStartLabel)
gotoCommand(elseEndLabel)
LabelNode(elseStartLabel)
LabelNode(elseEndLabel)
```

你要说：

> if-else 生成两个标签：一个是 else 开始，一个是整个 if-else 结束。条件为假跳到 else；then 执行完后用 goto 跳过 else；最后两个分支汇合。

### 11.3 打开 `WhileStatementTranslator.java`

指向：

```text
LabelNode(whileStartLabel)
ifnGoto(whileEndLabel)
gotoCommand(whileStartLabel)
LabelNode(whileEndLabel)
```

你要说：

> while 的中间代码结构是：循环开始标签、条件命令、条件为假跳出、循环体、跳回开始、循环结束标签。

指向 `bindLoopLabels(...)`。

你要说：

## 15. 用一个完整例子收束

你可以照着念这个例子，不需要现场跑。

源码：

```text
int32 a = 1;
int32 b = a + 2;
while (b < 10) {
    b = b + 1;
}
```

讲解：

> 第一行声明初始化，标识符表登记 `a` 的 offset 和类型。命令生成时先加载 `a` 的地址，再加载常量 1，最后 `assign_from_st_top_to_addr_int32` 写回。

> 第二行中，`a + 2` 会先经过常量分析。如果 `a` 的常量状态还有效，就可以折叠成 3，命令层直接生成 `load_st_int32_static 3`。如果不能折叠，就走表达式翻译，生成 `a` 的取值命令、常量 2 和 `st_plus_int32`。

> while 部分会创建开始和结束两个 label。先生成条件 `b < 10` 的命令，然后生成 `ifn_goto whileEnd`。循环体里 `b = b + 1` 按赋值规则生成。循环体结束后生成 `goto whileStart`。flatten 时 label 才变成具体指令编号。

> 所以我们最终得到的不是一句高级语句，而是一串小步骤命令，每条命令只做加载、取值、运算、跳转或写回中的一个动作。这就是我们的栈式三地址码。

## 16. 老师可能追问的问题

### 问题 1：你们的三地址码为什么没有 `t1 = ...`？

回答：

> 我们实现的是栈式三地址风格。传统三地址码显式命名临时变量，例如 `t1 = a + b`；我们把临时结果隐式保存在语义栈顶。这样命令仍然是细粒度中间操作，只是不需要维护显式临时变量表。比如 `a + b` 是先加载 a 的值，再加载 b 的值，最后 `st_plus_int32`，结果留在栈顶。

### 问题 2：label 是怎么回填的？

回答：

> 我们没有修改字符串。跳转命令持有 label 对象，文本用 `StringSupplierCommand` 延迟生成。`LabelNode` 在 flatten 时设置 `label.index = 当前命令数`。最后打印跳转命令时读取 label index，所以自然完成回填。

### 问题 3：break/continue 怎么知道跳到哪层循环？

回答：

> break/continue 在 token 阶段生成未决 goto，并放到 `uncertainBreaks` 或 `uncertainContinues` 列表。普通归约会向上传播这些列表。每个循环归约时只绑定自己循环体里尚未解析的 goto，所以嵌套循环中内层会先绑定内层目标，外层不会抢走。顶层还有未解析的，就说明出现在循环外，报错。

### 问题 4：常量折叠和命令生成怎么配合？

回答：

> 常量折叠由 `ConstantValueBuildCallback` 在 reduce 阶段完成，它把 `ConstantValue` 绑定到语法树节点。命令 translator 开始时调用 `ConstantCommandSupport.constantOrNull`，如果当前节点已经有常量，就直接生成 `load_st_*_static`。控制流也会通过 `ConstantConditionSupport` 读取 boolean 常量来剪枝。

### 问题 5：数组和结构体为什么都用 bias？

回答：

> 因为它们本质上都是从一个基位置定位到内部位置。数组是基引用加运行时下标偏移，结构体是基引用加编译期字段 offset。统一成 `bias_from_st_top_to_ref_*` 后，后续取值和写回都能走 `REFERENCE` 机制。

### 问题 6：函数代码为什么不在全局命令里？

回答：

> 函数定义不是程序入口立即执行的语句。`FunctionDefinitionTranslator` 会把函数体单独 flatten 成 `FunctionCommandSegment`，登记到函数命令段上下文，然后函数定义本身返回 `PlaceholderNodeRegister`。最终 `SemanticAnalysisResult` 里同时保存 entry commands 和 function segments。

### 问题 7：中间代码生成最终产物是什么？

回答：

> 最终产物是 `SemanticAnalysisResult`，它包含入口命令、函数命令段、结构体表、标识符表。三地址码文本只是 `ThreeAddressCodePrinter` 对 `SemanticCommand` 列表的展示结果。

## 17. 结尾总结

照读：

> 总结一下，我们的中间代码生成是语法制导的、事件驱动的、分层的。LR 分析负责产生 shift/reduce 事件；语义回调先构造类型、常量、符号表、结构体表和函数表；`CommandBuildCallback` 维护命令栈；具体 translator 根据产生式标签生成命令树；命令工厂统一生成三地址码命令对象；控制流通过 label 和未决 goto 延迟绑定；函数体单独进入函数命令段；最后 accept 前 flatten 成 `SemanticAnalysisResult`。所以我们实现的不只是打印三地址码，而是一套完整的中间代码生成机制。
