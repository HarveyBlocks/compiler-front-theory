## 第1章 实验概述

### 一、实验目的

本实验围绕“语法制导翻译与中间代码生成”展开，目标是在前序词法分析、语法分析基础上，把源程序从 token 流进一步翻译成可审计的中间表示。本项目不是只实现若干孤立语义动作，而是形成了一条完整的编译前端链路：

```text
源程序文本
  -> 输入资源与字符读取
  -> 正则表达式到 NFA/DFA 的词法分析
  -> LALR 移进-归约语法分析
  -> 语法制导语义回调
  -> 类型检查、符号表、常量折叠、函数表、结构体表
  -> 栈式三地址风格中间代码
  -> 测试报告与语义分析结果
```

具体目的包括：

1. 掌握语义动作在移进-归约分析中的触发时机，理解“归约产生语义节点、语义节点携带属性”的实现方式。
2. 设计并实现一套与文法绑定但可维护的语义标签机制，避免直接依赖产生式字符串进行脆弱分发。
3. 实现变量声明、赋值、表达式、控制流、数组、结构体、函数等语言结构的语义检查。
4. 生成能表达地址、引用、取值、赋值、跳转、函数调用和对象创建的中间代码。
5. 通过系统测试验证中间代码顺序、跳转目标、类型转换、作用域、返回路径和错误诊断是否正确。

## 第2章 程序设计

### 一、相关文法或语言定义

#### 1. 词法定义

Program 语言的词法入口为 `src/main/java/org/harvey/vie/theory/demo/program/ProgramLexicalDemo.java`。项目没有手写分支式扫描器，而是通过 `LexicalPattern` 描述“正则表达式 + token 类型”，再由 `DefaultLexicalDirector` 统一构造自动机：

```java
pairs.add(new RegexTypePair(regexParser.parse(pattern.getRegex()), pattern.getType()));
NfaStatusGraph<AlphabetCharacter, TokenType> nfaStatusGraph = regexNfaAdaptor.adapt(pairs);
DfaStatusGraph<AlphabetCharacter, TokenType> dfaStatusGraph = nfaDfaAdaptor.adapt(nfaStatusGraph);
return dfaMinimizer.minimize(regexDfaStatusTableFactory, dfaStatusGraph);
```

当前词法 token 由 `ProgramTokenType` 枚举定义，覆盖：

- 标识符：`IDENTIFIER`，以及结构体类型位置专用的 `TYPE_IDENTIFIER`。
- 空白与注释：`SPACE`、`COMMENT_BLOCK`、`COMMENT_LINE`。
- 字面量：整型、浮点、字符、字符串、布尔、`null`。
- 类型关键字：`boolean`、`char`、`int32`、`float64`、`string`、`void`。
- 结构与对象关键字：`struct`、`new`。
- 运算符：`+`、`-`、`*`、`/`、`!`、`&&`、`||`、`==`、`!=`、`<`、`<=`、`>`、`>=`、`=`、`.`、`,`、`;`、括号、方括号、花括号。
- 控制流关键字：`if`、`else`、`while`、`do`、`break`、`continue`、`return`。

词法阶段还保留空白与注释 token，语法分析前由 `ProgramSyntaxDemo.SHOULD_BE_FILTERED` 过滤 `SPACE`、`COMMENT_LINE`、`COMMENT_BLOCK`。这样既保留了调试与诊断信息，又不污染文法。

结构体类型名存在“普通标识符”和“类型名”的歧义。项目通过 `ProgramStructAwareTokenIterator` 解决：当发现 `struct Point { ... }` 后记录 `Point`，随后在类型声明或 `new Point()` 等类型位置，把 `IDENTIFIER` 重分类为 `TYPE_IDENTIFIER`。这使文法能够明确区分变量名和类型名。

#### 2. 完整文法定义

完整 Program 语言文法在 `src/main/resources/grammar0.txt` 和 `ProgramSyntaxDemo.buildGrammar0()` 中保持一致。起始符号为 `compilation_unit`：

```text
compilation_unit ::= program

program          ::= top_item
                   | top_item program

top_item         ::= struct_decl
                   | function_decl
                   | block_item
```

顶层结构支持结构体、函数和普通块项。结构体文法为：

```text
struct_decl       ::= struct id { struct_field_list }
struct_field_list ::= struct_fields | epsilon
struct_fields     ::= struct_fields struct_field | struct_field
struct_field      ::= type id ;
```

函数文法为：

```text
function_decl ::= function_head block
function_head ::= type id ( param_list )
                | void id ( param_list )
param_list    ::= params | epsilon
params        ::= params , param | param
param         ::= type id
```

块与语句文法为：

```text
block       ::= { block_items }
block_items ::= block_items block_item | epsilon
block_item  ::= decl | stmt

decl        ::= decl_plain | decl_init
decl_plain  ::= type id ;
decl_init   ::= type id = bool ;

stmt        ::= matched_stmt | unmatched_stmt
```

项目使用经典的 matched/unmatched 拆分消除悬挂 `else` 歧义：

```text
matched_stmt   ::= assign_stmt
                 | expr_stmt
                 | matched_while_stmt
                 | do_while_stmt
                 | break ;
                 | continue ;
                 | return_stmt
                 | block
                 | matched_if_stmt

unmatched_stmt ::= unmatched_if_stmt
                 | unmatched_while_stmt

matched_if_stmt    ::= if ( bool ) matched_stmt else matched_stmt
unmatched_if_stmt  ::= if ( bool ) stmt
                     | if ( bool ) matched_stmt else unmatched_stmt

matched_while_stmt   ::= while ( bool ) matched_stmt
unmatched_while_stmt ::= while ( bool ) unmatched_stmt
do_while_stmt        ::= do stmt while ( bool ) ;
return_stmt          ::= return bool ; | return ;
```

左值、数组和成员访问文法为：

```text
loc ::= loc [ bool ]
      | loc . id
      | id
```

表达式按优先级分层：

```text
bool     ::= bool || join | join
join     ::= join && equality | equality
equality ::= equality == rel | equality != rel | rel
rel      ::= expr < expr | expr <= expr | expr >= expr | expr > expr | expr
expr     ::= expr + term | expr - term | term
term     ::= term * unary | term / unary | unary
unary    ::= ! unary | - unary | factor
factor   ::= ( bool )
           | new_struct_expr
           | new_array_expr
           | call_expr
           | loc
           | integer
           | float
           | true
           | false
           | null
```

类型、对象创建和函数调用文法为：

```text
type ::= type [ ]
       | type_identifier
       | boolean
       | character
       | int32
       | float64
       | string

new_struct_expr ::= new type_identifier ( )

new_array_expr   ::= new array_creation_base array_creation_dims
array_creation_base ::= type_identifier | boolean | character | int32 | float64 | string
array_creation_dims ::= array_creation_dims array_creation_dim | array_creation_dim
array_creation_dim  ::= [ bool ] | [ ]

call_expr ::= id ( arg_list )
arg_list  ::= args | epsilon
args      ::= args , bool | bool
```

#### 3. 语义标签定义

为了降低文法与语义动作的脆弱耦合，项目给产生式候选体打 `ProgramSemanticTag`，例如：

- `DECLARATION`、`INITIALIZED`：声明和初始化。
- `ASSIGNMENT`：赋值。
- `CONDITIONAL`、`ELSE_BRANCH`：条件语句和带 else 分支。
- `LOOP`、`DO_LOOP`：循环。
- `FUNCTION`、`HEAD`、`DEFINITION`、`CALL`、`RETURN`：函数。
- `STRUCT_DECL`、`STRUCT_FIELD`：结构体。
- `ARRAY`、`ARRAY_CREATION_BASE`、`ARRAY_CREATION_DIM`：数组。
- `LITERAL`、`NULL_LITERAL`、`LEFT_VALUE`、`ACCESS`、`MEMBER_ACCESS`：值与寻址。
- `OR`、`AND`、`EQUAL`、`LESS`、`PLUS`、`MULTIPLY` 等运算符标签。

这些标签在 `ProgramSyntaxDemo.buildGrammar0()` 中通过 `.tagLast(...)` 绑定到具体候选体。后续类型构造、常量折叠和命令翻译都通过标签分发，而不是解析产生式字符串。

### 二、程序整体设计

#### 1. 总体架构

项目的完整编译前端流程可以分成六层：

1. 输入层：`Resource`、`SourceReader` 把源代码转为带 offset 的字符流。
2. 词法层：`ProgramLexicalDemo` 用正则集合构造 DFA 表，`DefaultLexicalAnalyzer` 输出 `SourceTokenIterator`。
3. 语法层：`ProgramSyntaxDemo.buildGrammar0()` 构建文法，`SyntaxDemo.buildShiftReduceParsingTable()` 构建或加载 LALR 分析表。
4. 移进-归约驱动层：`ShiftReducePhaserImpl` 根据 ACTION/GOTO 表执行 shift/reduce/accept。
5. 语义回调层：多个 `ShiftReduceCallback` 监听同一套 shift/reduce 事件，分别维护语法树、作用域、类型、常量、结构体、函数、命令等属性。
6. 结果层：`SemanticResultCallback` 在 accept 前收集入口命令、函数命令段、结构体表、标识符记录，生成 `SemanticAnalysisResult`。

语义回调注册入口为 `SemanticDemo.buildShiftReduceTestRegister()`：

```java
register.add(new TreeBuildCallback());
register.add(instanceIdentifierScopeCallback());
register.add(new TypeBuildCallback());
register.add(new ConstantValueBuildCallback());
register.add(new StructSemanticCallback());
register.add(new FunctionSemanticCallback());
register.add(instanceIdentifierTableBuildCallback());
register.add(new SemanticResultCallback());
register.add(instanceSyntaxDirectedTranslationCallback());
register.add(new IdentifierConstantStateCallback());
register.add(new PassiveErrorCallback());
```

这体现了本项目的核心设计：语法分析器只负责提供稳定的 shift/reduce 事件，语义模块通过回调组合形成语法制导翻译。

#### 2. LALR 分析流程

语法分析表构建在 `SyntaxDemo.buildShiftReduceParsingTable0()` 中完成：

1. `IterativeFixedPointFirstMapFactory` 计算 FIRST 集。
2. `ItemSetFamilyFactoryImpl` 构造 LR 项目集族和 GOTO 转移。
3. `LookaheadMapFactoryImpl` 计算 Lookahead 集。
4. `ShiftReduceParsingTableFactoryImpl` 填充 ACTION/GOTO 表。
5. 表通过 `ShiftReduceParsingTableImpl.store()` 持久化为 `src/main/resources/serial/syntax_table.data`。

运行时 `ShiftReducePhaserImpl.phase()` 循环执行：

```text
读取当前 token
查看栈顶状态 s
查 ACTION[s, token]
  shift: 压入新状态并触发 onShift
  reduce: 按产生式归约并触发 onReduce
  accept: 触发 beforeAccept/onAccept
  error: 进入错误回调
```

该流程保证每次归约时，当前产生式的所有子节点属性已经构造完成，正好满足语法制导翻译中“综合属性自底向上传递”的需要。

#### 3. 语义制导翻译流程

命令生成入口是 `CommandBuildCallback`。它继承 `BuildStackContextCallback<CommandNodeRegister>`，为每次 shift 和 reduce 构造命令节点：

- shift token 时，通过 `TokenTranslatorStrategy` 选择 token 翻译器。
- reduce production 时，通过 `CommandTranslatorStrategy` 选择产生式翻译器。

token 翻译器包括：

| 翻译器 | 作用 |
| --- | --- |
| `LoadIdentifierAddressTokenTranslator` | 早期把标识符 token 转为地址加载，后续也通过 `IdentifierUseTranslator` 绑定具体符号 |
| `SimpleStringTokenTranslator` | 字面量 token 生成静态加载命令 |
| `TypeTokenTranslator` | 类型 token 不直接产生运行命令 |
| `BreakTokenTranslator` | 生成未绑定 label 的 `break` 跳转 |
| `ContinueTokenTranslator` | 生成未绑定 label 的 `continue` 跳转 |
| `DoNothingTokenTranslator` | 语法符号或无需命令的 token 不产生命令 |

reduce 翻译器由 `TagStrategyCompose.stringCommand()` 按语义标签分派，例如：

| 标签 | 翻译器 |
| --- | --- |
| `DECLARATION + INITIALIZED` | `DeclarationWithInitializationTranslator` |
| `ASSIGNMENT` | `AssignStatementTranslator` |
| `LEFT_VALUE` | `PrimaryProduceLeftValueTranslator` |
| `ACCESS` | `ArrayAtExpressionTranslator` |
| `MEMBER_ACCESS` | `MemberAccessTranslator` |
| `NEW_STRUCT` | `NewStructTranslator` |
| `NEW_ARRAY` | `NewArrayTranslator` |
| `FUNCTION + CALL` | `FunctionCallTranslator` |
| `RETURN` | `FunctionReturnTranslator` |
| `CONDITIONAL` | `IfStatementTranslator` |
| `CONDITIONAL + ELSE_BRANCH` | `IfElseStatementTranslator` |
| `LOOP` | `WhileStatementTranslator` |
| `LOOP + DO_LOOP` | `DoWhileStatementTranslator` |
| `PLUS/MINUS/MULTIPLY/...` | `InSuffixExpressionTranslator` 或 `UnaryExpressionTranslator` |

#### 4. 中间代码设计

项目当前中间代码采用“栈式三地址风格”的字符串表示，由 `TypedStringCommandFactory` 和 `SimpleStringCommandFactory` 生成，最后通过 `ThreeAddressCodePrinter` 输出。典型命令包括：

| 命令形式 | 含义 |
| --- | --- |
| `load_st_int32_static 7` | 把 int32 常量 7 压入求值栈 |
| `load_st_int32_address 0` | 把局部变量表 offset=0 的 int32 地址压栈 |
| `st_top_addr_to_val_int32` | 栈顶地址解引用为 int32 值 |
| `st_top_ref_to_val_int32` | 栈顶对象引用解引用为 int32 值 |
| `st_plus_int32` | 弹出两个 int32 值相加，结果压栈 |
| `st_top_int32_cast_float64` | 把栈顶 int32 转为 float64 |
| `assign_from_st_top_to_addr_int32` | 将栈顶值写入局部变量地址 |
| `assign_from_st_top_to_ref_int32` | 将栈顶值写入对象引用位置 |
| `bias_from_st_top_to_ref_int32 1` | 对结构体引用加字段 offset 1 |
| `new_struct 0` | 根据结构体表 index=0 创建对象 |
| `new_array_int32 3 2` | 创建 int32 三维数组，其中前二维显式给长度 |
| `ifn_goto 12` | 栈顶条件为 false 时跳转 |
| `if_goto 3` | 栈顶条件为 true 时跳转 |
| `goto 6` | 无条件跳转 |
| `call 2` | 调用函数表 index=2 的函数 |
| `return` | 从函数返回 |

一个关键设计是区分 `address` 与 `reference`：

- `address` 表示局部变量表中的槽位地址，例如局部变量 `a` 的位置。
- `reference` 表示数组或结构体对象内部位置，例如 `obj.field` 或 `arr[i]`。

因此普通变量赋值使用 `assign_from_st_top_to_addr_*`，结构体字段和数组元素赋值使用 `assign_from_st_top_to_ref_*`。这避免了局部变量槽位和对象内部引用的语义混淆。

### 三、数据结构设计

#### 1. token 与词法表

`SourceToken` 表示词法单元，包含 token 类型、词素字节和 offset。`ProgramTokenType` 同时承担三种职责：

1. 为词法规则提供稳定 token 身份。
2. 为错误提示和调试输出提供可读名称。
3. 为词法表、语法表持久化提供可存储编号。

`RegexDfaStatusTable` 是由正则集合构造出的 DFA 状态表，存储在 `src/main/resources/serial/lex_table.data`。本次测试中重建后的文件大小为 49008 字节。

#### 2. 文法与分析表

`ProductionSetContext` 是文法内部表示，保存所有非终结符定义、候选体和终结符工厂。`ProgramSyntaxDemo.buildGrammar0()` 使用 builder 风格构造文法，例如：

```java
contextBuilder.define("matched_if_stmt", ProgramSemanticTag.CONDITIONAL, ProgramSemanticTag.ELSE_BRANCH)
    .alternateTerminal(ProgramTokenType.CONTROL_STRUCTURES_IF)
    .concatenateTerminalLast(ProgramTokenType.OPERATOR_PARENTHESIS_OPEN)
    .concatenateDefinitionLast("bool")
    .concatenateTerminalLast(ProgramTokenType.OPERATOR_PARENTHESIS_CLOSE)
    .concatenateDefinitionLast("matched_stmt")
    .concatenateTerminalLast(ProgramTokenType.CONTROL_STRUCTURES_ELSE)
    .concatenateDefinitionLast("matched_stmt");
```

`ShiftReduceParsingTable` 保存：

- start 状态。
- accept 状态。
- 终结符数组。
- 非终结符数组。
- ACTION 表。
- GOTO 表。
- 产生式数组。
- 终结符匹配器。

语法表存储在 `src/main/resources/serial/syntax_table.data`。本次重建后大小为 75471 字节。

#### 3. 语义上下文

`ShiftReduceSemanticContext` 是语义阶段的总上下文，集中持有：

- 语法分析上下文。
- 语义回调注册器。
- 命令工厂。
- 类型解析器。
- 常量解析器。
- 函数管理器。
- 语法树栈。
- 命令节点栈。
- 类型属性映射。
- 常量属性映射。
- 标识符表。
- 结构体表。
- 函数表和函数命令段。
- 错误上下文。

这种设计使所有语义模块都通过同一个上下文协作，避免模块间直接互相持有大量引用。

#### 4. 类型系统

`SemanticType` 表示语义类型，核心字段包括：

- `kind`：`BOOLEAN`、`CHARACTER`、`INT32`、`FLOAT64`、`STRING`、`VOID`、`STRUCT`、`NULL`。
- `dimensions`：数组维度层数，数组长度值不进入类型本身。
- `namedTypeKey`：结构体类型名的稳定 key。

重要方法包括：

- `isNumericScalar()`：判断是否为 `int32` 或 `float64` 标量。
- `isBooleanScalar()`：判断是否为 `boolean` 标量。
- `isArray()`：判断是否为数组。
- `isStruct()`：判断是否为结构体。
- `isReferenceType()`：结构体和数组都属于引用类型。
- `arrayElementType()`：数组索引后的元素类型。
- `withAppendedDimension()`：构造更高一维数组类型。

`TypeRegister` 不只保存结果类型，还保存 instruction type、锚点 token 和位置种类。关系表达式 `1 < 2.0` 的结果类型是 `boolean`，但指令类型是 `float64`，因此项目需要同时保存两种类型信息。

隐式转换由 `TypeConversionRule` 管理：

- `int32 -> float64` 允许，并会生成 `st_top_int32_cast_float64`。
- `float64 -> int32` 不允许。
- `null` 可以赋给数组或结构体等引用类型。
- 基础类型之间除数值提升外不允许隐式转换。

#### 5. 标识符表与作用域

`IdentifierTableBuilder` 用栈式作用域管理变量。每个作用域是一个 `ScopeBuilder`，内部用 `IdentifierKey -> IdentifierRecord` 映射。`IdentifierRecord` 保存：

- 全局唯一记录号 `no`。
- 当前局部表 offset。
- 类型语法节点。
- 声明类型。
- 变量名词素。
- 是否初始化。
- 所属函数。
- 编译期常量值。

进入 `{` 时，`IdentifierScopeCallback` 调用 `scopeIntoBlock()`；归约出完整 `block` 时，调用 `scopeExistBlock()` 取出当前作用域符号并关闭作用域。对于函数体，退出 block 时还会触发非 `void` 函数返回路径检查。

#### 6. 常量值

`ConstantValue` 保存编译期常量类型和值。`ConstantValueBuildCallback` 在归约时构造常量属性，支持：

- 整型、浮点、布尔、`null` 字面量。
- 一元负号、一元逻辑非。
- 算术表达式常量折叠。
- 逻辑表达式常量折叠。
- 相等与关系表达式常量折叠。
- 从仍保持常量状态的标识符读取常量。

`IdentifierConstantStateCallback` 对赋值做保守处理：普通赋值会清除被赋值标识符的常量状态，避免在缺少路径敏感分析时错误传播旧常量。

#### 7. 函数表

函数语义由 `FunctionSemanticCallback`、`FunctionRecord`、`FunctionSignature`、`FunctionParameter` 和 `FunctionReturnFlowAnalyzer` 共同完成。

`FunctionRecord` 保存：

- 函数表索引 `tableIndex`。
- 函数签名：函数名、返回类型、声明节点。
- 形参列表。
- 函数头节点。

函数调用时，中间代码使用 `call <tableIndex>`，不直接使用函数名。例如测试 `text50-function-nested-struct-array-params` 中：

```text
call 2
call 1
```

分别表示调用函数表中的 `pickFromSchool` 和 `readStudentArray`。

返回路径检查由 `FunctionReturnFlowAnalyzer` 根据语义标签完成：

- `RETURN` 节点保证返回。
- block 是否返回取决于内部语句序列。
- 语句序列只要前一段保证返回，后续对“是否保证返回”不再产生负面影响。
- 带 `else` 的 `if-else` 在条件非常量时要求 then/else 两支都保证返回。
- 条件为编译期常量时，只检查实际可达分支。

#### 8. 结构体表

结构体语义由 `StructSemanticCallback`、`StructContext`、`StructRecord`、`StructField` 完成。

`StructRecord` 保存：

- 结构体表索引。
- 结构体名 token。
- 结构体名 key。
- 字段列表。
- 声明节点。

`StructField` 保存字段名、字段类型和 offset。字段 offset 按声明顺序从 0 开始分配。例如：

```text
struct Point {
    int32 x;
    int32 y;
}
```

生成结构体表：

```text
index=0 name=Point
  offset=0 type=int32 name=x
  offset=1 type=int32 name=y
```

结构体实例化命令为 `new_struct 0`，成员访问命令为 `bias_from_st_top_to_ref_<type> <offset>`。

#### 9. 数组维度

数组创建由 `ArrayCreationDimensions` 汇总维度信息，检查规则包括：

- 至少要有一个显式长度维度。
- 显式长度维度必须在省略维度之前。
- 每个显式长度表达式类型必须是 `int32`。

例如：

```text
new int32[11][12][13] -> new_array_int32 3 3
new int32[11][12][]   -> new_array_int32 3 2
new int32[11][][]     -> new_array_int32 3 1
```

其中第一个数字是总维度数，第二个数字是显式指定长度的维度数。

#### 10. 命令节点

命令生成不是直接拼接全局字符串列表，而是先构造 `CommandNodeRegister`。主要实现包括：

- `NormalCommandNodeRegister`：保存正常命令节点和未绑定跳转。
- `PlaceholderNodeRegister`：无命令占位。
- `MergedCommandNodeRegister`：合并多个子树命令。

这种设计允许 `break`、`continue` 先生成未绑定 label 的跳转，等归约到完整循环时再由 `WhileStatementTranslator.bindLoopLabels()` 绑定实际目标。

### 四、主要函数代码与设计

#### 1. ProgramLexicalDemo.lexicalAnalyzer()

该函数是 Program 语言词法入口：

```java
RegexDfaStatusTable table = buildTable(alphabetCharacterFactory);
SourceAlphabetCharacterAdaptorImpl saca = new SourceAlphabetCharacterAdaptorImpl(alphabetCharacterFactory);
DefaultLexicalAnalyzer baseAnalyzer = new DefaultLexicalAnalyzer(table, saca);
cachedAnalyzer = (errorContext, resource) ->
        new ProgramStructAwareTokenIterator(baseAnalyzer.iterator(errorContext, resource));
```

设计重点：

- DFA 表优先从 `lex_table.data` 加载。
- `-Dlexical.flushTable=true` 时重新构造并持久化。
- 外层包装 `ProgramStructAwareTokenIterator` 解决结构体类型名识别问题。

#### 2. ProgramSyntaxDemo.buildGrammar0()

该函数是完整文法定义入口。它通过 builder DSL 同时定义文法和语义标签。以数组访问为例：

```java
contextBuilder.define("loc")
    .alternateSelf()
    .concatenateTerminalLast(ProgramTokenType.OPERATOR_SQUARE_OPEN)
    .concatenateDefinitionLast("bool")
    .concatenateTerminalLast(ProgramTokenType.OPERATOR_SQUARE_CLOSE)
    .tagLast(ProgramSemanticTag.ACCESS)
    .alternateSelf()
    .concatenateTerminalLast(ProgramTokenType.OPERATOR_DOT)
    .concatenateTerminalLast(ProgramTokenType.IDENTIFIER)
    .tagLast(ProgramSemanticTag.MEMBER_ACCESS)
    .alternateTerminal(ProgramTokenType.IDENTIFIER)
    .tagLast(ProgramSemanticTag.IDENTIFIER, ProgramSemanticTag.USE);
```

设计重点：

- 文法结构和语义意图同时绑定。
- `ACCESS`、`MEMBER_ACCESS`、`IDENTIFIER + USE` 在后续分别对应数组索引、结构体成员访问和变量引用。
- 语义模块不必再通过产生式字符串判断当前归约的含义。

#### 3. ShiftReducePhaserImpl.phase()

该函数是移进-归约分析驱动器。核心逻辑是根据 ACTION 表选择 shift/reduce/accept：

```java
ActiveTableElement element = table.activeNext(top, table.matchTerminal(current));
if (element == null) {
    context.onError(ShiftReduceErrorType.UNDEFINED_ACTION);
} else if (element.isShift()) {
    onShift(context, element, current);
} else if (element.isReduce()) {
    onReduce(context, element);
    if (element.isAccept()) {
        break;
    }
}
```

设计重点：

- 语法分析事件统一进入 `ShiftReduceSemanticContext`。
- 每个语义 callback 都能观察同一次 shift/reduce。
- accept 前通过 `SemanticResultCallback` 收敛最终结果。

#### 4. TypeBuildCallback

`TypeBuildCallback` 在每次 reduce 时根据 `ProgramSemanticTag` 计算当前归约节点的类型属性。典型规则：

- `TYPE + ARRAY`：在基础类型上追加一个数组维度。
- `IDENTIFIER + USE`：查符号表，得到变量声明类型和地址位置。
- `ACCESS`：检查左侧是数组、下标是 `int32`，结果为数组元素类型。
- `MEMBER_ACCESS`：检查左侧是结构体、字段存在，结果为字段类型。
- `FUNCTION + CALL`：查函数表，结果为函数返回类型。
- `NEW_STRUCT`：检查结构体已声明，结果为结构体引用类型。
- `NEW_ARRAY`：检查元素类型合法和维度合法，结果为数组引用类型。
- 算术、关系、逻辑、相等表达式：检查操作数类型并计算结果类型和指令类型。

以数组访问为例：

```java
if (!baseType.isArray()) {
    throw new CompilerException("subscript operator requires an array operand.");
}
if (!SemanticType.scalar(SemanticType.Kind.INT32).equals(indexType)) {
    throw new CompilerException("array index must be int32.");
}
return TypeRegister.located(baseType.arrayElementType(), baseType.arrayElementType(), childAnchor(head, 0), LocationKind.REFERENCE);
```

#### 5. AssignStatementTranslator

赋值翻译器完成类型兼容检查、必要的隐式类型转换和写回命令选择：

```java
SemanticDiagnostics.requireAssignable(context, sourceType, targetType, TypeAttributes.childAnchor(context, 1),
        "assignment requires assignable types.");
children[0].register(builder);
children[2].register(builder);
if (context.requiresImplicitCast(sourceType, targetType)) {
    builder.add(new TerminalNode(context.getCommandFactory().stTopCast(...)));
}
if (locationKind == LocationKind.REFERENCE) {
    builder.add(new TerminalNode(context.getCommandFactory().assignFromStTopToRef(...)));
} else {
    builder.add(new TerminalNode(context.getCommandFactory().assignFromStTopToAddr(...)));
}
```

设计重点：

- 先求左值定位，再求右值。
- `int32 -> float64` 自动插入 cast。
- 根据左值是局部地址还是对象引用，选择不同写回命令。

#### 6. InSuffixExpressionTranslator

该翻译器处理二元中缀表达式，包括算术、逻辑、关系和相等运算。流程为：

1. 若当前表达式已能常量折叠，直接返回 `loadConstant` 命令。
2. 读取左右操作数类型。
3. 根据运算符类别检查类型。
4. 对需要提升的操作数插入 `st_top_*_cast_*`。
5. 生成 `st_<operator>_<type>` 命令。

例如 `int32 + float64` 会把 `int32` 操作数提升为 `float64`，再生成 `st_plus_float64`。

#### 7. IfStatementTranslator 与 IfElseStatementTranslator

普通 `if` 翻译为：

```text
condition
ifn_goto end
then
end:
```

`if-else` 翻译为：

```text
condition
ifn_goto elseStart
then
goto elseEnd
elseStart:
else
elseEnd:
```

如果条件是编译期布尔常量，翻译器会裁剪不可达分支。例如 `if (false) stmt` 不生成条件跳转和语句体命令；`if (true) then else elsePart` 只保留 then 分支。

#### 8. WhileStatementTranslator 与 DoWhileStatementTranslator

`while` 翻译为：

```text
whileStart:
condition
ifn_goto whileEnd
body
goto whileStart
whileEnd:
```

如果 `while` 条件为常量 `false`，翻译器直接返回空占位节点，不生成循环体命令。

`do-while` 翻译为：

```text
whileStart:
body
beforeTest:
condition
if_goto whileStart
whileEnd:
```

如果 `do-while` 条件为常量 `false`，仍保留一次循环体，因为 do-while 语义要求先执行一次。

循环翻译器还负责绑定 `break` 和 `continue`：

- `while` 中 `continue` 指向条件检查起点，`break` 指向循环出口。
- `do-while` 中 `continue` 指向条件检查点，`break` 指向循环出口。

#### 9. FunctionSemanticCallback 与函数命令段

函数头归约时，`FunctionSemanticCallback` 注册函数记录：

- 检查函数是否重复。
- 解析返回类型。
- 收集参数列表。
- 检查参数不能为 `void`。
- 检查参数重名。
- 标记即将进入函数体。

函数调用归约时：

- 检查函数已定义。
- 检查实参数量。
- 检查实参类型可赋给形参类型。

函数定义命令翻译由 `FunctionDefinitionTranslator` 完成。它不把函数体命令混入全局入口段，而是登记到 `FunctionCommandSegmentContext`：

```java
List<SemanticCommand> commands = CommandSegmentSupport.flatten(children[1]);
context.registerFunctionCommandSegment(new FunctionCommandSegment(function, commands));
return new PlaceholderNodeRegister();
```

最终 `SemanticAnalysisResult` 中同时有：

- `entryCommands`：程序入口命令。
- `functionSegments`：每个函数独立命令段。

#### 10. StructSemanticCallback 与成员访问翻译

`StructSemanticCallback` 在 `STRUCT_DECL` 归约时注册结构体：

- 检查结构体名重复。
- 收集字段。
- 检查字段不能为 `void`。
- 检查字段重名。
- 为字段分配 offset。
- 检查字段结构体类型已声明。

成员访问由 `MemberAccessTranslator` 翻译：

```java
children[0].register(builder);
StructRecord struct = context.getStruct(baseType);
StructField field = struct.field(TypeAttributes.childAnchor(context, 2));
builder.add(new TerminalNode(context.getCommandFactory().biasFromStTopToRef(
        CommandDataType.forStorage(field.getType()),
        field.getOffset()
)));
```

即先得到对象引用，再根据结构体表中字段 offset 生成偏移访问命令。

#### 11. NewArrayTranslator

数组创建翻译器先检查元素类型不是 `void`，再用 `ArrayCreationDimensions.summarizeAndValidate()` 统计维度。显式维度表达式会先求值入栈，最后生成 `new_array_*`：

```java
children[2].register(builder);
builder.add(new TerminalNode(context.getCommandFactory().newArray(
        CommandDataType.forStorage(type),
        summary.getTotalDimensions(),
        summary.getSpecifiedDimensions()
)));
```

例如：

```text
int32[][][] a;
a = new int32[11][12][];
```

会生成：

```text
load_st_ref_address 0
load_st_int32_static 11
load_st_int32_static 12
new_array_int32 3 2
assign_from_st_top_to_addr_ref
```

#### 12. SemanticResultCallback 与测试报告

`SemanticResultCallback.beforeAccept()` 在语法分析 accept 前构造最终结果：

```java
CommandNodeRegister top = commandContext.peek();
List<SemanticCommand> entryCommands = CommandSegmentSupport.flatten(top);
return new SemanticAnalysisResult(
        entryCommands,
        context.getFunctionCommandSegmentContext().snapshot(),
        context.structRecords(),
        context.identifierRecords()
);
```

`ProgramSyntaxTestRunner` 会把结果写入 Markdown 报告，包含：

- 源程序。
- 结构体表。
- 全局入口命令。
- 全局局部变量表。
- 函数段命令。
- 函数局部变量表。
- 错误列表。
- 汇总统计。

```text
[002] st_top_addr_to_val_int32
[003] bias_from_st_top_to_ref_ref
[004] st_top_ref_to_val_ref
[005] call 0
[006] return
```

分析：结构体数组元素访问 `students[index]` 先加载数组引用，再加载下标值，随后用 `bias_from_st_top_to_ref_ref` 定位数组元素，并通过 `st_top_ref_to_val_ref` 取出结构体引用作为实参调用 `readStudent`。函数命令段与入口命令段分离，说明 `FunctionDefinitionTranslator` 的函数段登记机制正确。

#### 5. 控制流与跳转测试

项目对控制流做了细粒度断言：

- `text2` 验证悬挂 `else` 绑定，外层 `if` 的 false 跳转目标与内层 `if-else` 的 else/join 标签不同。
- `text15-continue-in-while` 验证 `continue` 跳回 while 条件检查点。
- `text16-continue-in-do-while` 验证 `continue` 跳到 do-while 的条件检查点，而不是循环体起点。
- `text19-nested-break-continue-binding` 验证嵌套循环中内层 `break/continue` 不会错误绑定到外层。
- `text20-double-break-binding` 验证同一程序中不同层级 `break` 目标不同。

这些测试说明 `UncertainLabelGotoCommand` 延迟绑定策略是必要且有效的：`break/continue` 在 shift 阶段还不知道所属循环出口，只有归约到完整循环结构时才能绑定。

这组测试验证了 `TypeBuildCallback`、`TypeConversionRule` 和各 translator 中的 `SemanticDiagnostics.requireAssignable/requireBoolean/requireNumeric` 等检查。

## 第4章 实验总结

### 一、实验总结

本项目完成了一个较完整的编译前端实践系统。与只在语法树上做简单动作不同，本项目把语法制导翻译拆成多个协作模块：语法树构造、作用域、符号表、类型属性、常量属性、结构体表、函数表、命令生成和结果输出。各模块通过同一个移进-归约事件流驱动，既保持了语法制导翻译的时机正确性，又避免把所有逻辑堆到一个巨大回调中。

实验三最核心的成果是中间代码生成体系。项目目前可以生成表达式求值、变量读写、数组索引、结构体字段访问、对象创建、条件跳转、循环跳转、函数调用和返回等命令。命令虽然以字符串形式展示，但其背后已经区分了类型、地址、引用、函数索引和结构体索引，因此具备继续接后端解释器或目标代码生成的基础。

项目的另一个重要成果是测试报告体系。`ProgramSyntaxTestRunner` 不仅判断程序是否被接受，还把每个用例的源代码、命令、符号表、结构体表、函数段和错误输出写入 Markdown。这样可以直接审计某条语义规则是否真正落到中间代码中，而不是只看 JUnit 是否通过。

本次实测结果为：50 个程序测试全部符合预期，32 个合法程序成功生成语义结果，18 个非法程序被拒绝。测试覆盖了类型系统、常量优化、控制流、函数、结构体、数组和错误路径，说明当前语法制导翻译与中间代码生成实现具有较好的完整性。

### 二、心得体会

通过本次实验可以明显体会到，语法制导翻译的难点不只是“在产生式上写动作”，而是如何管理文法、属性、符号表和命令之间的依赖关系。项目采用 `ProgramSemanticTag` 把产生式候选体映射为语义意图，是一个很关键的设计：语义模块仍然依赖文法结构，但依赖的是稳定标签，而不是脆弱的产生式字符串。

另一个收获是类型属性必须设计得足够细。一个表达式的结果类型、运算指令类型、左值位置类型、错误锚点并不是同一件事。如果只保存“结果类型”，在处理 `int32 < float64`、数组元素、结构体字段、赋值隐式转换时都会变得混乱。`SemanticType`、`TypeRegister` 和 `LocationKind` 的组合较好地解决了这个问题。

控制流翻译也体现了中间代码设计的重要性。`break/continue` 不能在 token 出现时立即确定目标，只能先生成未绑定跳转，再由循环归约时统一绑定。这个延迟绑定机制使嵌套循环和 do-while 的 continue 语义都能正确表达。

最后，测试报告对调试帮助很大。像常量折叠、函数命令段拆分、结构体字段 offset、数组维度统计这类逻辑，仅靠“程序接受”无法证明正确；必须查看具体命令和语义表。当前测试体系把这些结果稳定输出，降低了后续扩展和回归验证成本。

后续可以继续完善的方向包括：

- 将部分仍通过异常拒绝的语义错误统一写入 `ErrorContext`，使错误报告更一致。
- 为语法表和词法表的缺失提供自动重建或更友好的提示。
- 在现有中间代码基础上增加解释执行器，验证命令不仅结构正确，而且运行语义正确。
- 增加更完整的数据流分析，例如不可达代码、变量初始化使用检查、路径敏感常量传播等。
