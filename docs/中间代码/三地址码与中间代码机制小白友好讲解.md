# 三地址码与中间代码机制小白友好讲解

这份文档用尽量直观的方式讲清楚本项目里的三地址码和中间代码机制。它和《三地址码与中间代码机制设计详解》讲的是同一套东西，只是换成更容易理解的说法。

如果你完全不了解编译器，可以先记住一句话：

> 中间代码就是编译器把源码翻译成机器码之前，先写出来的一份“简单动作清单”。

比如源码里有一句：

```text
a = b + 1;
```

人看起来很简单，但编译器会把它拆成很多小动作：

```text
找到 a 的位置
找到 b 的位置
读出 b 的值
准备数字 1
做加法
把结果写回 a
```

本项目输出的三地址码，就是把这些小动作写成统一格式的命令。

## 0. 小白先按这条路线点代码

如果你第一次打开这个项目，不建议一上来就看 `AssignStatementTranslator`、`IfStatementTranslator` 这些类。它们确实重要，但你会不知道它们什么时候被调用。

建议先按下面顺序点：

```text
AppTest
  -> ProgramSyntaxTestRunner
  -> ShiftReducePhaserImpl
  -> ShiftReduceSemanticContext
  -> SemanticDemo.buildShiftReduceTestRegister()
  -> CommandBuildCallback
  -> TagStrategyCompose
  -> 各种 Translator
  -> CommandFactory
  -> CommandNodeRegister / CommandNode
  -> SemanticResultCallback
  -> ThreeAddressCodePrinter
```

这条路线就是“三地址码从哪里来”的主线。

### 0.1 第一步：`AppTest` 是测试入口

`AppTest` 会跑一堆程序测试用例。你可以把它理解成老师按下“开始测试”按钮。

它会调用：

```text
ProgramSyntaxTestRunner.run()
```

然后 `ProgramSyntaxTestRunner` 会去读：

```text
src/main/resources/program-tests
```

里面的每个 `.txt` 都是一段小程序。项目会把每段小程序编译一遍，并生成测试报告。

### 0.2 第二步：`ProgramSyntaxTestRunner` 准备编译器

`ProgramSyntaxTestRunner.executeSemanticTest(...)` 会准备几样东西：

- 词法分析器：负责把源码切成 token。
- LR 语法分析表：负责决定什么时候 shift、什么时候 reduce。
- 语义回调列表：负责类型检查、常量折叠、命令生成。
- 命令工厂：负责创建三地址码命令。

然后它创建：

```text
ShiftReducePhaserImpl
```

并调用：

```text
phase(...)
```

到这里，真正的语法分析和中间代码生成就开始了。

### 0.3 第三步：`ShiftReducePhaserImpl` 像一个总导演

`ShiftReducePhaserImpl.phase(...)` 一直循环做一件事：

```text
看当前 token
看当前语法状态
查表决定下一步是 shift 还是 reduce
```

如果是 shift，意思是“读进来一个 token”。

如果是 reduce，意思是“把刚才读到的一些东西合成一个更大的语法结构”。

例如：

```text
1
```

可以归约成一个字面量表达式。

```text
b + 1
```

可以归约成一个加法表达式。

```text
a = b + 1;
```

可以归约成一个赋值语句。

每次 shift 或 reduce，它都会通知语义系统：

```text
context.onShift(...)
context.onReduce(...)
```

### 0.4 第四步：`ShiftReduceSemanticContext` 把事件分发给很多人

你可以把 `ShiftReduceSemanticContext` 想成班长。总导演说“现在 shift 了”或“现在 reduce 了”，班长就按名单通知每个同学。

名单在：

```text
SemanticDemo.buildShiftReduceTestRegister()
```

里面。重要成员包括：

```text
TreeBuildCallback              负责建语法树
TypeBuildCallback              负责算类型
ConstantValueBuildCallback     负责提前算常量
StructSemanticCallback         负责结构体表
FunctionSemanticCallback       负责函数表
IdentifierTableBuildCallback   负责变量表
CommandBuildCallback           负责三地址码
SemanticResultCallback         负责最后收结果
```

所以三地址码生成不是单独完成的。它旁边一直有类型系统、常量系统、符号表系统帮它准备信息。

### 0.5 第五步：`CommandBuildCallback` 真正开始造三地址码

`CommandBuildCallback` 就是三地址码生成入口。

它内部维护一个“命令栈”。语法分析每 shift 一个 token，它就在命令栈里压一个小东西；每 reduce 一个语法结构，它就从命令栈里弹出几个小东西，合成一个更大的东西，再压回去。

这个“小东西”叫：

```text
CommandNodeRegister
```

你可以把它理解成“还没最终打印出来的命令包”。

### 0.6 第六步：`TagStrategyCompose` 决定找谁翻译

当语法分析归约出一个赋值语句，项目怎么知道该调用 `AssignStatementTranslator`？

答案在：

```text
TagStrategyCompose.stringCommand()
```

它像一张分发表：

```text
ASSIGNMENT              -> AssignStatementTranslator
CONDITIONAL             -> IfStatementTranslator
CONDITIONAL + ELSE      -> IfElseStatementTranslator
LOOP                    -> WhileStatementTranslator
LOOP + DO_LOOP          -> DoWhileStatementTranslator
ACCESS                  -> ArrayAtExpressionTranslator
MEMBER_ACCESS           -> MemberAccessTranslator
FUNCTION + CALL         -> FunctionCallTranslator
RETURN                  -> FunctionReturnTranslator
```

所以你看 translator 时要知道：它们不是自己主动运行的，而是语法分析 reduce 到对应标签后，被 `CommandBuildCallback` 间接调用的。

### 0.7 第七步：命令工厂把动作变成命令对象

translator 不直接写字符串，而是调用：

```text
context.getCommandFactory()
```

例如赋值写回会调用：

```text
assignFromStTopToAddr(...)
```

最后经过：

```text
DefaultCommandFactory
  -> TypedStringCommandFactory
  -> StringCommand
```

变成真正的文本命令：

```text
assign_from_st_top_to_addr_int32
```

### 0.8 第八步：先存成命令树，最后才打印

命令生成出来后不会马上打印。它会先被装进：

```text
TerminalNode
NormalCommandNodeRegister
```

这些对象里。

最后程序快结束时：

```text
SemanticResultCallback
```

会调用：

```text
CommandSegmentSupport.flatten(...)
```

把命令树拍平成命令列表。

最后：

```text
ThreeAddressCodePrinter
```

把命令对象变成你在报告里看到的字符串。

## 0.9 中间代码生成到底分几步

前面讲了“点代码路线”，这里再把“中间代码生成步骤”完整摊开。你可以把它想成一条接力赛：每一棒都不直接生成最终报告，但都会给下一棒准备材料。

### 第 1 步：测试用例把源码交给编译器

入口文件是：

```text
AppTest
```

它会调用：

```text
ProgramSyntaxTestRunner.run()
```

`ProgramSyntaxTestRunner` 会读取：

```text
src/main/resources/program-tests/*.txt
```

每个 txt 都是一段小程序。比如里面可能有：

```text
int32 a = 1;
a = a + 2;
```

这一阶段的输入是源码文本，输出是“准备交给编译器处理的一段程序”。

### 第 2 步：准备词法分析器、语法分析表和语义回调

在：

```text
ProgramSyntaxTestRunner.executeSemanticTest(...)
```

里，项目会准备：

- 词法分析器：把源码切成 token。
- LR 语法分析表：决定什么时候 shift、什么时候 reduce。
- 语义回调列表：类型分析、常量分析、符号表、中间代码生成都在这里。
- 命令工厂：负责造中间代码命令。

然后创建：

```text
ShiftReducePhaserImpl
```

这一阶段的输出是一个可以开始工作的语法分析器对象。

### 第 3 步：创建语义上下文

`ShiftReducePhaserImpl.phase(...)` 开始后，会创建：

```text
ShiftReduceSemanticContext
```

你可以把它想成一个“大背包”，里面放着编译过程中所有共享资料：

- 语法树栈。
- 命令栈。
- 类型表。
- 常量表。
- 变量表。
- 函数表。
- 结构体表。
- 函数代码段。
- 命令工厂。

后面所有模块都从这个“大背包”里拿东西、放东西。

### 第 4 步：词法分析把源码变成 token

源码：

```text
a = b + 1;
```

会被词法分析器变成类似：

```text
IDENTIFIER(a)
OPERATOR_ASSIGN(=)
IDENTIFIER(b)
OPERATOR_PLUS(+)
CONSTANT_INTEGER(1)
OPERATOR_SEMICOLON(;)
```

中间代码生成不是直接读源码字符串，而是跟着这些 token 走。

### 第 5 步：语法分析不断发出 shift/reduce 事件

核心类：

```text
ShiftReducePhaserImpl
```

它会不断查 LR 表：

```text
当前状态 + 当前 token -> 下一步动作
```

动作有两种最重要：

- shift：读进一个 token。
- reduce：把若干 token 或语法结构合成一个更大的语法结构。

例如：

```text
1
```

可以 reduce 成“字面量表达式”。

```text
b + 1
```

可以 reduce 成“加法表达式”。

```text
a = b + 1;
```

可以 reduce 成“赋值语句”。

每次 shift/reduce，语法分析器都会通知语义上下文：

```text
context.onShift(...)
context.onReduce(...)
```

### 第 6 步：语义上下文把事件通知给所有回调

核心类：

```text
ShiftReduceSemanticContext
```

它会按顺序通知一串回调。可以理解成同一个事件来了，大家轮流处理：

```text
TreeBuildCallback
TypeBuildCallback
ConstantValueBuildCallback
StructSemanticCallback
FunctionSemanticCallback
IdentifierTableBuildCallback
CommandBuildCallback
...
```

每个回调负责一件事：

- 建语法树。
- 算类型。
- 算常量。
- 登记变量。
- 登记结构体。
- 登记函数。
- 生成中间代码。

所以中间代码生成不是一个孤立步骤。它依赖前面这些回调先把信息准备好。

### 第 7 步：先建语法树节点

核心类：

```text
TreeBuildCallback
```

它也维护一个栈。

shift 时：

```text
token -> TokenNode
```

reduce 时：

```text
几个孩子节点 -> HeadNode
```

例如 `b + 1` reduce 后，会得到一个表示“加法表达式”的 `HeadNode`。

后面的命令生成器经常会问：

```text
当前刚 reduce 出来的语法节点是什么？
```

它就是从这个语法树栈里拿。

### 第 8 步：给语法节点绑定类型

核心类：

```text
TypeBuildCallback
TypeContext
TypeRegister
```

比如：

```text
b + 1
```

如果 `b` 是 `int32`，`1` 是 `int32`，那么这个表达式的类型就是 `int32`。

项目会把这个信息绑到语法节点上：

```text
这个 HeadNode -> TypeRegister(int32)
```

如果是：

```text
i < f
```

结果类型是 `boolean`，但执行比较时可能要按 `float64` 比较。项目也会记录这个差别。

另外，类型信息里还会记录左值种类：

- 普通变量是 `ADDRESS`。
- 数组元素、结构体字段是 `REFERENCE`。

后面赋值和取值命令都要靠这个判断。

### 第 9 步：给语法节点绑定常量值

核心类：

```text
ConstantValueBuildCallback
ConstantValueContext
ConstantValue
```

如果表达式能提前算出来，就绑定常量值。

例如：

```text
1 + 2 * 3
```

会绑定成：

```text
ConstantValue(int32, 7)
```

后面命令生成时看到这个表达式已经是常量，就不用生成乘法、加法命令，直接生成：

```text
load_st_int32_static 7
```

if/while 也会用这个信息。如果条件是 `true` 或 `false`，就可以提前决定保留还是删除某个分支。

### 第 10 步：准备变量表、结构体表、函数表

中间代码里会出现：

```text
load_st_int32_address 0
new_struct 1
call 2
bias_from_st_top_to_ref_int32 3
```

这些数字从哪里来？来自语义表。

变量表由：

```text
IdentifierTableBuildCallback
```

负责。它记录：

- 变量名字。
- 变量类型。
- 变量 offset。
- 是否初始化。
- 属于全局还是某个函数。
- 是否有编译期常量值。

结构体表由：

```text
StructSemanticCallback
```

负责。它记录：

- 结构体编号。
- 字段列表。
- 每个字段的类型。
- 每个字段的 offset。

函数表由：

```text
FunctionSemanticCallback
```

负责。它记录：

- 函数编号。
- 函数名。
- 返回类型。
- 参数列表。

命令生成时需要这些表，才能知道变量地址、字段偏移和函数编号。

### 第 11 步：命令生成器维护“命令栈”

核心类：

```text
CommandBuildCallback
```

它维护：

```text
CommandContext
```

也就是命令栈。

shift 时，它把一个 token 翻译成一个小命令包，压栈。

reduce 时，它弹出若干孩子命令包，交给对应 translator 合成一个更大的命令包，再压回去。

这个“命令包”叫：

```text
CommandNodeRegister
```

所以中间代码不是一下子生成完整列表，而是随着语法归约慢慢合成出来。

### 第 12 步：token 级翻译

有些 token 自己就能生成命令。

例如整数 `1`：

```text
SimpleStringTokenTranslator
  -> load_st_int32_static 1
```

`break`：

```text
BreakTokenTranslator
  -> 生成一个目标暂时未知的 goto
```

`continue`：

```text
ContinueTokenTranslator
  -> 生成一个目标暂时未知的 goto
```

标识符比较特殊。标识符 token 刚出现时，先不生成真正地址命令。等它被语法归约成“变量使用”后，再由 `IdentifierUseTranslator` 查变量表生成地址加载。

### 第 13 步：产生式级翻译

当语法分析 reduce 出一个大结构，就要找对应 translator。

分发表在：

```text
TagStrategyCompose
```

例如：

```text
赋值语句       -> AssignStatementTranslator
加法表达式     -> InSuffixExpressionTranslator
if             -> IfStatementTranslator
while          -> WhileStatementTranslator
数组访问       -> ArrayAtExpressionTranslator
结构体字段访问 -> MemberAccessTranslator
函数调用       -> FunctionCallTranslator
return         -> FunctionReturnTranslator
```

translator 会做四类事情：

1. 读取孩子命令包。
2. 读取类型、常量、变量表、函数表、结构体表。
3. 做必要的语义检查。
4. 生成新的命令包。

例如 `AssignStatementTranslator` 会：

```text
生成左边位置
生成右边值
必要时做类型转换
根据左边是 ADDRESS 还是 REFERENCE 选择写回命令
```

### 第 14 步：命令工厂创建命令对象

translator 不直接写字符串，而是调用：

```text
CommandFactory
```

比如：

```text
loadIdentifierAddress(...)
stOperator(...)
assignFromStTopToAddr(...)
ifnGoto(...)
callFunction(...)
returnCommand()
```

命令工厂再交给：

```text
TypedStringCommandFactory
SimpleStringCommandFactory
```

最后创建：

```text
StringCommand
StringSupplierCommand
StringUncertainLabelGotoCommand
```

所以真正的中间代码命令先是对象，最后才打印成字符串。

### 第 15 步：命令被装进命令树

命令对象会被放进：

```text
TerminalNode
```

多个命令节点会组合成：

```text
HeadNode
```

标签会用：

```text
LabelNode
```

它不输出命令，只记录“这里是第几条命令”。

这些节点共同形成一棵命令树。

为什么不直接变成列表？

因为现在有些信息还不能确定：

- if 跳到哪里？
- while 的结束位置是哪条指令？
- break 属于哪层循环？
- 函数体应该放在函数段还是全局段？
- if(false) 的死分支要不要输出？

所以项目先用命令树保存结构。

### 第 16 步：处理 label 和跳转

if、while、do-while 都需要跳转。

普通跳转的目标用：

```text
DefaultSemanticLabel
```

先占着。等命令树最后拍平成列表时，`LabelNode` 才知道自己所在位置，然后把编号写进 label。

跳转命令本身用：

```text
StringSupplierCommand
```

它打印时才读取 label 编号，所以不需要回头改字符串。

`break/continue` 更特殊。它们刚出现时不知道目标：

```text
goto unknown
```

等归约到循环时，循环 translator 才把它们绑定到：

- `break`：循环出口。
- `continue`：条件检查点。

如果到程序顶层还有没绑定的 `break/continue`，说明它出现在循环外，要报错。

### 第 17 步：函数体单独生成函数命令段

函数定义不能直接放进全局命令。

例如：

```text
int32 inc(int32 x) {
    return x + 1;
}
```

这段代码不是程序一开始就执行，而是调用 `inc` 时才执行。

所以：

```text
FunctionDefinitionTranslator
```

会把函数体命令单独拍平成一个：

```text
FunctionCommandSegment
```

再登记到：

```text
FunctionCommandSegmentContext
```

函数定义本身在全局命令里是空的。

### 第 18 步：accept 前收集完整结果

当语法分析确认整个程序都合法，准备 accept 时：

```text
SemanticResultCallback
```

会收集：

- 全局入口命令。
- 函数命令段。
- 结构体表。
- 变量表。

它调用：

```text
CommandSegmentSupport.flatten(...)
```

把命令树拍平成真正的命令列表。

这一步得到：

```text
SemanticAnalysisResult
```

这才是完整的中间表示结果。

### 第 19 步：打印三地址码和测试报告

最后：

```text
ThreeAddressCodePrinter
```

把命令对象变成字符串。

`ProgramSyntaxTestRunner.writeReport(...)` 再把结果写进 markdown 报告，包括：

- 源码。
- 结构体表。
- 全局命令。
- 全局变量。
- 函数命令。
- 函数局部变量。
- 错误信息。

所以你在报告里看到的三地址码，是这 19 步之后的最终展示。

### 0.10 一句话总流程

完整中间代码生成流程可以记成：

```text
源码
  -> token
  -> shift/reduce
  -> 语法树节点
  -> 类型/常量/符号表/结构体表/函数表
  -> CommandBuildCallback 生成命令包
  -> translator 组合命令树
  -> CommandFactory 创建命令对象
  -> label 和 break/continue 延迟绑定
  -> 函数体单独形成函数命令段
  -> flatten 拍平成命令列表
  -> SemanticAnalysisResult
  -> ThreeAddressCodePrinter
  -> markdown 测试报告
```

### 0.11 每一步输入输出速查表

| 步骤 | 输入 | 处理者 | 输出 |
| --- | --- | --- | --- |
| 读测试 | `.txt` 源码 | `ProgramSyntaxTestRunner` | 源码字符串 |
| 词法分析 | 源码字符串 | `ProgramLexicalDemo` 相关词法分析器 | token 流 |
| 语法推进 | token + LR 表 | `ShiftReducePhaserImpl` | shift/reduce 事件 |
| 事件分发 | shift/reduce | `ShiftReduceSemanticContext` | 回调链调用 |
| 建树 | token/production | `TreeBuildCallback` | `TokenNode` / `HeadNode` |
| 算类型 | 语法节点 | `TypeBuildCallback` | `TypeRegister` |
| 算常量 | 语法节点 | `ConstantValueBuildCallback` | `ConstantValue` |
| 建变量表 | 声明/使用节点 | `IdentifierTableBuildCallback` | `IdentifierRecord` |
| 建结构体表 | 结构体声明 | `StructSemanticCallback` | `StructRecord` |
| 建函数表 | 函数头/调用/返回 | `FunctionSemanticCallback` | `FunctionRecord` |

## 1. 这个项目的三地址码长什么样

项目里的三地址码不是 `t1 = b + 1` 这种传统形式，而是“栈式”的形式。你可以把“栈”想象成一个托盘：

- 新算出来的东西放到托盘最上面。
- 下一条命令通常拿托盘最上面的东西继续操作。
- 算完以后结果也放回托盘最上面。

例如：

```text
load_st_int32_address 0
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
```

可以理解为：

1. `load_st_int32_address 0`：把编号为 0 的 `int32` 变量的位置放到托盘上。
2. `st_top_addr_to_val_int32`：托盘最上面现在是“位置”，把这个位置里的值读出来。
3. `load_st_int32_static 1`：把数字 1 放到托盘上。
4. `st_plus_int32`：把托盘上两个 `int32` 数字相加，结果放回托盘。

所以，这套中间代码虽然没有写 `t1/t2`，但它仍然表达了传统三地址码的意思：每条命令只做一个简单动作。

## 2. 为什么不用很多临时变量

传统三地址码可能写成：

```text
t1 = b + 1
a = t1
```

这里要管理 `t1`：

- `t1` 是第几个临时变量？
- `t1` 是什么类型？
- `t1` 什么时候不再使用？

项目里改成“栈式”后，临时结果直接放在栈顶，不需要取名字。这样表达式翻译会简单很多：

```text
先算左边
再算右边
最后发出运算命令
```

例如 `x + y`：

```text
生成 x 的值
生成 y 的值
生成 plus 命令
```

`plus` 命令默认拿栈上的两个值相加。

## 3. 从源码到三地址码，发生了什么

编译器不是读完整个文件后随便生成命令，而是跟着语法分析一步步生成。

整个流程可以想象成一条流水线：

1. 词法分析：把源码切成 token，例如 `int32`、`a`、`=`、`1`、`;`。
2. 语法分析：判断这些 token 能不能组成合法句子。
3. 类型分析：知道每个表达式是什么类型，比如 `int32` 或 `boolean`。
4. 常量分析：提前算出能在编译期确定的表达式，比如 `1 + 2 * 3`。
5. 符号表分析：知道变量 `a` 放在哪个 offset，函数 `inc` 是第几个函数。
6. 命令生成：把语法结构翻译成中间代码命令。
7. 结果收集：把入口代码、函数代码、结构体表、变量表整理成最终结果。

项目里这些步骤都挂在 LR 语法分析的 shift/reduce 事件上。简单说：

- shift：读进来一个 token。
- reduce：发现几个东西能合成一个更大的语法结构。

每次 shift 或 reduce，命令生成系统都会同步处理一小块中间代码。

## 4. 命令不是乱拼字符串

虽然最后看到的是字符串命令，但项目没有在各个地方手动拼字符串。它设计了一个 `CommandFactory`，也就是“命令工厂”。

你可以把它想成一个统一的造句器：

- 想加载常量，就调用 `loadConstant`。
- 想做加法，就调用 `stOperator`。
- 想跳转，就调用 `gotoCommand`。
- 想调用函数，就调用 `callFunction`。

具体输出成：

```text
load_st_int32_static 1
st_plus_int32
goto 10
call 0
```

这些格式由工厂决定。这样做的好处是：语法翻译器只说“我要做什么”，不用关心“字符串到底怎么写”。

以后如果想把文本命令换成更正式的 IR 对象，也可以主要改工厂，而不是把所有翻译器推倒重写。

## 5. 命令里的类型是怎么来的

你会看到很多命令带类型：

```text
load_st_int32_static 1
load_st_float64_address 2
st_plus_int32
st_less_float64
assign_from_st_top_to_addr_boolean
```

这是因为中间代码必须知道自己在操作什么类型的数据。

项目里有两种类型概念：

- `SemanticType`：源码里的类型，比如 `int32`、`float64`、`struct Student`、`int32[]`。
- `CommandDataType`：命令层真正需要写进命令名里的类型，比如 `int32`、`float64`、`boolean`、`ref`。

结构体和数组在源码里名字很多，比如：

```text
struct Student
int32[]
Student[]
```

但在命令层，它们都可以看成引用，所以统一写成：

```text
ref
```

例如：

```text
load_st_ref_address 0
assign_from_st_top_to_addr_ref
```

这表示这里操作的是一个引用变量，具体它是结构体还是数组，由语义类型系统另行保存。

## 6. `address` 和 `ref` 到底有什么区别

这是理解项目中间代码的关键。

变量、数组元素、结构体字段都能被赋值，所以它们都是“左值”。但是它们的位置来源不同。

### 6.1 普通变量是 address

比如：

```text
a = 1;
```

变量 `a` 在符号表里有一个 offset。命令可以直接加载它的地址：

```text
load_st_int32_address 0
```

这类位置叫 `ADDRESS`。

### 6.2 数组元素和结构体字段是 reference

比如：

```text
arr[i] = 1;
student.age = 18;
```

`arr[i]` 不是一个直接写在符号表里的变量，它要先找到数组 `arr`，再根据 `i` 偏移到某个元素。

`student.age` 也不是一个独立变量，它要先找到 `student`，再根据字段偏移找到 `age`。

这种“从一个对象内部定位出来的位置”叫 `REFERENCE`。

项目用两套命令区分它们：

```text
st_top_addr_to_val_int32
st_top_ref_to_val_int32
assign_from_st_top_to_addr_int32
assign_from_st_top_to_ref_int32
```

含义是：

- `addr_to_val`：从普通变量地址读值。
- `ref_to_val`：从数组元素或结构体字段引用读值。
- `assign_to_addr`：写回普通变量。
- `assign_to_ref`：写回数组元素或结构体字段。

这个设计让复杂左值不会混乱。

## 7. 赋值是怎么生成的

看一个简单赋值：

```text
a = b + 1;
```

项目会按这个顺序生成：

1. 先找到左边 `a` 的位置。
2. 再计算右边 `b + 1` 的值。
3. 最后把右边结果写回左边位置。

对应命令大致是：

```text
load_st_int32_address <a_offset>
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
assign_from_st_top_to_addr_int32
```

注意第一条先加载 `a` 的地址。这样做是为了记住“最终要写回哪里”。右侧表达式算完后，栈顶是结果，而更早压入的东西保存着目标位置，赋值命令就能完成写回。

如果左边是数组元素：

```text
arr[i] = x;
```

最后会用：

```text
assign_from_st_top_to_ref_<type>
```

因为 `arr[i]` 是从数组内部定位出来的引用。

## 8. 变量作为值使用时要先取值

变量出现在表达式里时，不能只拿它的位置，而要读出位置里的值。

例如：

```text
b + 1
```

`b` 先被翻译成：

```text
load_st_int32_address <b_offset>
```

这只是 `b` 的地址。为了参与加法，还要追加：

```text
st_top_addr_to_val_int32
```

如果是数组元素：

```text
arr[i] + 1
```

`arr[i]` 定位后得到的是引用，所以要追加：

```text
st_top_ref_to_val_int32
```

这就是“左值变右值”的过程。

## 9. 加减乘除和比较是怎么生成的

表达式翻译非常规律：

```text
左边命令
右边命令
运算命令
```

例如：

```text
a + b
```

变成：

```text
a 的值
b 的值
st_plus_int32
```

如果是：

```text
i < f
```

并且 `i` 是 `int32`，`f` 是 `float64`，项目会把 `i` 提升成 `float64` 再比较：

```text
load_st_int32_address <i_offset>
st_top_addr_to_val_int32
st_top_int32_cast_float64
load_st_float64_address <f_offset>
st_top_addr_to_val_float64
st_less_float64
```

这里有个容易忽略的点：这个表达式的最终结果是 `boolean`，但比较指令本身使用 `float64`，因为左右两个数要先用同一种数值类型比较。

所以项目里的类型信息不仅记录“表达式结果是什么类型”，还记录“执行这条运算时应该按什么类型执行”。

## 10. 隐式类型转换

项目支持比较保守的隐式转换：

- `int32` 可以转成 `float64`。
- `float64` 不可以自动转回 `int32`。
- `null` 可以赋给结构体或数组这种引用类型。
- 其他乱转基本不允许。

如果确实需要转换，会生成命令：

```text
st_top_int32_cast_float64
```

比如：

```text
float64 f = i;
```

其中 `i` 是 `int32`，就会先算出 `i`，再把栈顶的 `int32` 转成 `float64`，最后写回 `f`。

## 11. 常量折叠：编译器提前帮你算

如果表达式能在编译期确定，项目会直接把它算出来。

例如：

```text
int32 a = 1 + 2 * 3;
```

不会生成：

```text
load 1
load 2
load 3
multiply
plus
```

而是直接生成：

```text
load_st_int32_static 7
```

这叫常量折叠。

项目里有一个 `ConstantValueBuildCallback` 专门负责提前计算常量。它支持：

- 整数、浮点数、布尔值。
- `null`。
- 一元负号，例如 `-1`。
- 逻辑非，例如 `!false`。
- 算术运算。
- 逻辑运算。
- 相等比较。
- 大小关系比较。
- 已知常量变量的传播。

## 12. 常量传播：变量也可能被提前知道

例如：

```text
int32 a = 1;
int32 b = a + 2;
```

编译器知道 `a` 初始化为常量 `1`，如果中间没有修改 `a`，那么 `a + 2` 也可以提前算成 `3`。

所以 `b` 的初始化可以直接加载：

```text
load_st_int32_static 3
```

但是如果后面出现：

```text
a = a + 1;
```

项目会清除 `a` 的常量状态。因为当前项目没有做很复杂的路径分析，所以只要变量被重新赋值，就保守地认为它不再是可安全传播的编译期常量。

这个保守处理可以避免错误优化。

## 13. if 是怎么翻译的

普通：

```text
if (cond) {
    stmt;
}
```

会变成：

```text
cond 的命令
ifn_goto ifEnd
stmt 的命令
ifEnd:
```

`ifn_goto` 的意思是：如果条件为假，就跳到 `ifEnd`。

### 13.1 标签是什么

你可以把标签想成书签。

生成 `ifn_goto ifEnd` 的时候，编译器还不知道 `ifEnd` 最后是第几条命令。因为 `stmt` 里面可能还有很多命令。

项目的做法是：

1. 先创建一个 label 对象。
2. 跳转命令先引用这个 label。
3. 等所有命令排好队后，再给 label 填上真正的指令编号。

这就像先在文档里写“跳到书签 A”，等排版完成后，书签 A 自然知道自己在第几页。

### 13.2 if(true) 和 if(false)

如果条件在编译期就知道：

```text
if (true) stmt;
```

那就不需要跳转，直接保留 `stmt`。

如果是：

```text
if (false) stmt;
```

那 `stmt` 不可能执行，命令可以删掉。

但项目还有一个细节：即使死分支不生成命令，里面的非法 `break/continue` 也不能被偷偷忽略。

例如：

```text
if (false) {
    break;
}
```

虽然代码不会执行，但 `break` 出现在循环外，仍然应该报错。项目通过 `MergedCommandNodeRegister` 做到：命令不输出，但错误线索继续保留。

## 14. if-else 是怎么翻译的

普通：

```text
if (cond) {
    thenPart;
} else {
    elsePart;
}
```

会变成：

```text
cond 的命令
ifn_goto elseStart
thenPart 的命令
goto elseEnd
elseStart:
elsePart 的命令
elseEnd:
```

解释一下：

1. 条件为假，跳到 else。
2. 条件为真，执行 then。
3. then 执行完后，要跳过 else。
4. 两边最后汇合到 `elseEnd`。

如果条件是常量：

- `if(true)`：只输出 then 分支命令。
- `if(false)`：只输出 else 分支命令。

但不可达分支里的 `break/continue` 仍然会保留给错误检查。

## 15. while 是怎么翻译的

普通：

```text
while (cond) {
    body;
}
```

会变成：

```text
whileStart:
cond 的命令
ifn_goto whileEnd
body 的命令
goto whileStart
whileEnd:
```

也就是：

1. 到循环开头。
2. 检查条件。
3. 条件为假就跳出。
4. 条件为真就执行循环体。
5. 执行完跳回开头。

### 15.1 while 里的 continue

`continue` 的意思是跳过本轮剩余语句，进入下一轮判断。

所以在 `while` 里，`continue` 应该跳到条件检查位置，也就是 `whileStart`。

### 15.2 while 里的 break

`break` 的意思是直接跳出循环。

所以在 `while` 里，`break` 应该跳到 `whileEnd`。

### 15.3 while(false)

如果条件编译期就是 false：

```text
while (false) {
    body;
}
```

循环体一次都不会执行，所以项目直接不生成这段循环命令。

## 16. do-while 是怎么翻译的

`do-while` 和 `while` 最大的区别是：循环体至少执行一次。

```text
do {
    body;
} while (cond);
```

会变成：

```text
whileStart:
body 的命令
beforeTest:
cond 的命令
if_goto whileStart
whileEnd:
```

这里 `if_goto` 的意思是：如果条件为真，就跳回循环体开头。

### 16.1 do-while 里的 continue

这是一个容易错的点。

在 `do-while` 中，`continue` 不是跳到循环体开头，而是跳到条件检查点 `beforeTest`。

因为执行 `continue` 后应该先判断条件，如果条件为真才进入下一轮。

项目专门为 do-while 设置 `beforeTestLabel`，测试里也检查了这个行为。

### 16.2 do-while(false)

如果条件是 false：

```text
do {
    body;
} while (false);
```

循环体仍然要执行一次，所以项目保留 body 命令，但不生成回跳命令。

如果 body 里有 `continue`，它会被绑定到循环出口，因为条件恒 false，不会有下一轮。

## 17. break 和 continue 为什么要“先欠着”

当编译器刚看到：

```text
break;
```

它还不知道这个 `break` 属于哪一层循环。

例如：

```text
while (...) {
    while (...) {
        break;
    }
}
```

这个 `break` 应该跳出内层循环，不应该跳出外层循环。

所以项目的做法是：

1. 看到 `break`，先生成一条目标未知的 `goto`。
2. 把它放进“未解决 break 列表”。
3. 等归约到完整循环时，循环翻译器把循环体里还没解决的 `break` 绑定到当前循环出口。
4. 内层循环会先绑定自己的 `break`，外层循环不会抢走它。
5. 如果最终到了程序顶层还有没绑定的 `break`，说明它在循环外，报错。

`continue` 同理，只是目标是当前循环的条件检查点。

这个机制非常适合处理嵌套循环。

## 18. 数组创建怎么表示

例如：

```text
new int32[11][12][13]
```

项目会先生成三个长度值：

```text
load_st_int32_static 11
load_st_int32_static 12
load_st_int32_static 13
```

然后生成数组创建命令：

```text
new_array_int32 3 3
```

后两个数字分别表示：

- 总共有 3 个维度。
- 有 3 个维度显式写了长度。

如果是：

```text
new int32[11][12][]
```

命令是：

```text
new_array_int32 3 2
```

意思是总共 3 维，但只给了前 2 维长度。

如果是：

```text
new int32[11][][]
```

命令是：

```text
new_array_int32 3 1
```

项目要求：

1. 至少有一个维度写出长度。
2. 省略长度只能出现在尾部。
3. 长度表达式必须是 `int32`。

## 19. 数组访问怎么表示

例如：

```text
arr[i]
```

项目会：

1. 生成 `arr` 的命令，得到数组引用。
2. 生成 `i` 的命令，得到下标值。
3. 生成偏移命令：

```text
bias_from_st_top_to_ref_<elementType>
```

这个命令的意思是：根据栈顶下标，从数组引用偏移到某个元素位置。

结果不是元素值，而是元素位置。之后：

- 如果要读它，就用 `st_top_ref_to_val_<type>`。
- 如果要写它，就用 `assign_from_st_top_to_ref_<type>`。

这就是为什么数组元素属于 `REFERENCE`。

## 20. 结构体创建怎么表示

例如：

```text
new Student
```

项目会在结构体表里找到 `Student` 的编号，然后生成：

```text
new_struct 0
```

这里的 `0` 是结构体表编号。结构体真正有哪些字段、字段是什么类型、字段 offset 是多少，都存在结构体表里。

这样中间代码不需要把整个结构体布局写进每条命令，只需要引用结构体表。

## 21. 结构体字段访问怎么表示

例如：

```text
student.age
```

项目会：

1. 先生成 `student` 的命令，得到结构体引用。
2. 在结构体表里找到 `age` 字段。
3. 取出字段 offset。
4. 生成：

```text
bias_from_st_top_to_ref_int32 <field_offset>
```

字段访问本质上就是“从结构体开头偏移到某个字段”。

这和数组访问很像：

- 数组偏移：偏移量来自运行时下标。
- 结构体字段偏移：偏移量是编译期固定的字段 offset。

项目把它们都叫 bias，所以命令体系很统一。

## 22. 函数定义为什么不放进全局代码

如果源码是：

```text
int32 inc(int32 x) {
    return x + 1;
}
```

这段函数定义不应该像普通语句一样在程序入口马上执行。它应该单独放到函数代码区，等有人调用时再执行。

所以项目把函数体命令放进 `FunctionCommandSegment`，而不是放进全局入口命令。

最终结果里会有：

- Global Segment：全局入口命令。
- Function Segment：每个函数自己的命令。

一个只有函数定义、没有全局执行语句的程序，入口命令可以为空，但函数命令段不为空。

## 23. 函数调用怎么表示

例如：

```text
y = inc(x);
```

项目会：

1. 先准备实参 `x` 的值。
2. 生成函数调用：

```text
call 0
```

这里的 `0` 是函数表编号。

3. 调用结果留在栈顶。
4. 再把结果写回 `y`。

所以整体大致是：

```text
load_st_int32_address <y_offset>
load_st_int32_address <x_offset>
st_top_addr_to_val_int32
call 0
assign_from_st_top_to_addr_int32
```

多参数函数会按源码里的参数顺序依次加载实参，再发出 `call`。

## 24. return 怎么表示

返回语句：

```text
return x + 1;
```

会先生成返回值表达式命令，然后追加：

```text
return
```

如果返回值本身能在编译期算出，比如：

```text
return 1 + 2;
```

项目会直接生成：

```text
load_st_int32_static 3
return
```

返回值是否合法，比如 void 函数不能返回值、非 void 函数必须返回值，由函数语义检查模块负责。

## 25. 标签怎么最终变成数字

中间代码输出时，跳转命令需要目标编号：

```text
ifn_goto 10
goto 3
```

但前面说过，生成命令时目标编号可能还不知道。

项目的解决办法是命令树：

- 普通命令节点会输出一条命令。
- 标签节点不输出命令，只记录“我现在处在第几条命令的位置”。

最后把命令树拍平成列表时：

1. 看到普通命令，就加入列表。
2. 看到标签，就把当前列表长度写入 label。
3. 跳转命令最后打印时读取 label 的数字。

这就完成了“回填”，但没有真的回头改字符串。

这个设计很干净。

## 26. 为什么死分支里还会报 break 错误

看这个例子：

```text
if (false) {
    break;
}
```

直觉上这个分支不会执行，似乎可以删掉。但编译器的语义检查不能因为它不可达就完全忽略它。`break` 仍然写在循环外，语法语义上不合法。

项目处理这件事时分两条线：

- 命令线：死分支不输出命令。
- 错误线：死分支里的未决 `break/continue` 继续向上传播。

最后程序顶层看到还有没被循环绑定的 `break`，就报错。

这就是 `MergedCommandNodeRegister` 的作用：输出一边，诊断信息合并多边。

## 27. 最终结果里有哪些东西

项目最终不是只输出一串命令，还会整理成 `SemanticAnalysisResult`，里面包含：

- 入口命令 `entryCommands`。
- 函数命令段 `functionSegments`。
- 结构体表 `structTable`。
- 标识符表 `identifierRecords`。

测试报告会把它们分开展示：

- 源码。
- 结构体表。
- 全局命令。
- 全局变量。
- 函数命令。
- 函数局部变量。
- 错误信息。

这对实验报告很有用，因为可以清楚看到“源码被翻译成了什么中间代码”。

## 28. 读命令时的速查表

| 命令 | 可以这样理解 |
| --- | --- |
| `load_st_int32_static 1` | 把整数 1 放到栈上 |
| `load_st_float64_static 2.5` | 把浮点数 2.5 放到栈上 |
| `load_st_boolean_static true` | 把布尔值 true 放到栈上 |
| `load_st_null_static null` | 把 null 放到栈上 |

## 29. 用一个完整例子串起来

源码：

```text
int32 a = 1;
int32 b = a + 2;
while (b < 10) {
    b = b + 1;
}
```

可以这样理解：

第一句：

```text
找到 a
加载 1
写回 a
```

第二句中，`a` 是已知常量 1，所以 `a + 2` 可能被提前折叠成 3：

```text
找到 b
加载 3
写回 b
```

while：

```text
循环开始标签
读 b
加载 10
比较 b < 10
如果为假跳出循环
找到 b
读 b
加载 1
加法
写回 b
跳回循环开始
循环结束标签
```

这就是中间代码做的事情：把高级源码拆成一条条非常简单、可检查、可执行思路明确的小命令。

## 30. 再用代码对象讲一遍：`a = b + 1;` 怎么一步步变出来

这一节不讲抽象概念，只讲项目里的对象怎么接力。我们用：

```text
a = b + 1;
```

假设 `a` 和 `b` 都是 `int32` 变量。

### 30.1 读到 token 时，先进入 shift

语法分析器读源码时，会一个 token 一个 token 往前走。

读到 `1` 时，会触发：

```text
ShiftReducePhaserImpl
  -> context.onShift(...)
  -> CommandBuildCallback
  -> SimpleStringTokenTranslator
```

`SimpleStringTokenTranslator` 发现这是一个常量，就让命令工厂创建：

```text
load_st_int32_static 1
```

但它现在不是最终输出，只是被放进一个 `TokenCommandRegister`。

### 30.2 读到标识符 `b` 时，先不急着生成地址

`b` 是标识符。当前项目里，标识符 token shift 时先返回一个空占位：

```text
PlaceholderNodeRegister
```

为什么不马上生成 `load_st_int32_address`？

因为标识符可能出现在很多位置：

- 声明变量时的名字。
- 使用变量时的名字。
- 结构体类型名。
- 函数名。

只有等语法归约告诉我们“这是一次标识符使用”，才能查变量表并生成地址加载。

### 30.3 归约出“标识符使用”时，才查变量表

当语法分析器确认 `b` 是一个变量使用，会调用：

```text
IdentifierUseTranslator
```

它做三件事：

1. 从语法树节点里拿到 `b` 的 token。
2. 用 `context.getIdentifier(token)` 查标识符表。
3. 找到 `b` 的 offset，生成：

```text
load_st_int32_address <b_offset>
```

这一步得到的是 `b` 的位置。

### 30.4 `b` 要参与加法，所以还要从位置读出值

`b + 1` 里的 `b` 不是要被赋值，而是要拿它的值参与加法。

所以项目会用：

```text
PrimaryProduceLeftValueTranslator
```

把 `b` 从“位置”变成“值”：

```text
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
```

第一条找到位置，第二条读取值。

### 30.5 归约出 `b + 1` 时，调用加法翻译器

当语法分析器看到 `b + 1` 可以组成一个加法表达式，会调用：

```text
InSuffixExpressionTranslator
```

它会按顺序放入：

```text
b 的值
1 的值
加法命令
```

也就是：

```text
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
```

如果这里是 `int32 + float64`，它还会在中间插入类型转换命令。

### 30.6 归约出整个赋值语句时，调用赋值翻译器

当语法分析器确认整句是赋值语句：

```text
a = b + 1;
```

会调用：

```text
AssignStatementTranslator
```

它固定按这个顺序做：

```text
先生成左边 a 的位置
再生成右边 b + 1 的值
最后生成写回命令
```

所以最终命令是：

```text
load_st_int32_address <a_offset>
load_st_int32_address <b_offset>
st_top_addr_to_val_int32
load_st_int32_static 1
st_plus_int32
assign_from_st_top_to_addr_int32
```

第一条先把 `a` 的位置放好，是为了最后知道结果要写回哪里。

### 30.7 这些命令先组成树，不是马上打印

每个 translator 返回的不是字符串列表，而是：

```text
CommandNodeRegister
```

register 里面装着命令节点。普通命令在：

```text
TerminalNode
```

里面。多个命令会被组合成：

```text
HeadNode
```

这样做是因为有些东西现在还不能确定，比如 if/while 的跳转目标。

### 30.8 最后 `flatten` 才把命令树拍平成列表

程序分析快结束时：

```text
SemanticResultCallback
```

会拿到命令栈顶部的 register，然后调用：

```text
CommandSegmentSupport.flatten(...)
```

它会递归展开所有命令节点：

- 遇到 `TerminalNode`：把命令放入最终列表。
- 遇到 `LabelNode`：不放入列表，只记录当前指令编号。
- 遇到 `HeadNode`：继续展开孩子。

最后 `ThreeAddressCodePrinter` 才把命令对象打印成字符串。

### 30.9 这就是“代码怎么运作”的完整闭环

把上面串起来就是：

```text
源码 token
  -> shift/reduce 事件
  -> CommandBuildCallback 维护命令栈
  -> TagStrategyCompose 找 translator
  -> translator 调 CommandFactory
  -> CommandFactory 造 SemanticCommand
  -> 命令被包进 CommandNodeRegister
  -> accept 前 flatten
  -> ThreeAddressCodePrinter 输出文本
```

读懂这条链路，再去看任何一个 translator，就不会迷路。

| 源码结构 | 主要 translator | 它负责什么 |

## 33. 这套设计最值得记住的点

1. 项目用“栈式三地址码”，不用显式临时变量，但仍然是一步一命令的中间表示。
2. 命令工厂负责统一生成命令文本，翻译器只表达语义动作。
3. 普通变量用 `address`，数组元素和结构体字段用 `ref`，读值和写回都有对应命令。
4. 类型系统先算好表达式类型，命令生成时直接读取。
5. 常量系统先算好编译期常量，命令生成时可以直接加载最终值。
6. if、while、do-while 都通过 label 和 goto 表达。
7. label 的具体编号在最后拍平命令树时才确定。
8. `break/continue` 先生成目标未知的 goto，等遇到所属循环时再绑定。
9. 死分支可以不输出命令，但里面的非法 `break/continue` 仍然会被诊断。
10. 函数体代码单独放在函数命令段，不混进全局入口代码。
11. 数组和结构体都用 `ref + bias` 机制定位内部元素或字段。
12. 测试报告把命令、符号表、结构体表、函数段全部展示出来，方便验证设计是否正确。

如果能理解以上 12 点，就基本理解了本项目三地址码机制的核心设计。
